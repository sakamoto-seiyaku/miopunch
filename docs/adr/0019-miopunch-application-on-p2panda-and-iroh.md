# miopunch 应用直接使用 p2panda 和 iroh 修改版

## 应用交付边界

2026-11-19，用户确认 miopunch 是直接使用 p2panda 修改版和 iroh 修改版的应用，取消独立的 miopunch SDK 或函数库层。应用使用 p2panda 的成员授权、记录与同步能力，直接使用 iroh 的连接和流。原生和浏览器可以共用产品协议代码。合并交付入口不决定传输调度的位置。

## 原生建路的所有权

应用向融合端点提供目标身份、当前准入与资源许可、联系入口及其偏好、节点维护预算。MQTT、IRC 等适配器执行各自的收发。融合端点独占本次建连、候选交换与探测、时钟和取消、轮次名额、socket 及原连接的验证和换路。应用和各业务使用连接和流，资源撤销仍能立即生效。只有显式启用融合的端点采用这套策略。

考虑过由应用协调增强打洞、普通 UDP 全交给 QNT。它能减少 fork 代码，但原版自动 QNT 依赖合适的业务连接，首次只有受限联系时仍要交接控制权。增强候选也必须把真实绑定交回原 QUIC 连接。另一种做法是保留两个调度器，现场已经出现两端各占名额却都未探测的情况。选择融合以统一这些路径的资源寿命、取消和重试，同时接受维护较大 fork 的代价。这项决定取代 [ADR 0009](0009-unified-session-and-capability-based-paths.md) 中原生穿透调度留在核心之外的分工。

升级上游时按已记录的上游版本核对 fork 差异，保留必要的通用修复和显式融合入口，移除上游已经提供的等价实现。沿用普通库消费者验证默认契约，再以融合入口复验此次升级触及的行为。涉及共用线协议时，核对浏览器与原生端的实际互通。[普通库契约](0012-preserve-library-contracts-and-defaults.md) · [已有兼容验收](../notes/2026-10-19-fork-compatibility-convergence.md)

同一网络内，同一对已准入设备的普通业务默认共享原连接，各项业务在连接上开流。以下所说的业务连接遵循 [ADR 0020](0020-shared-member-business-connection.md)。

原生 UDP 穿透将 QNT 和 miopunch 移植自 frp 的打洞能力融合成一套流程。frp 衍生的地址分析、双方角色选择和探测安排都属于这套流程本身。两边重复的候选交换、探测和重试逻辑各由一处负责。经获准的数据中继改善已有连接，以及经 MQTT、IRC 等受限联系入口建立首条数据路径，都使用这套流程。

ping 是通过 QUIC 业务流检查对端是否在线的服务。任一方向有业务流量时均可触发改善，受本机维护预算约束。原生成员连接沿用原有每端选路、PTO 与在途 ACK 停滞判据。存在获准且取得回程确认的备用路径时，本端可在 QUIC 退休 UDP 之前换路。新路径实际承担发送后，将旧路径未确认的 STREAM 帧交回调度一次。对端仍按自己的可用路径发送。恢复与稳态评分沿用原有直连优先、档内 RTT 防抖和显式偏好。经 relay 时，待命重试继续寻找直连。

普通保活在指定路径发包，ACK 使用传输的默认回程。新绑定首次资格验证、增强 UDP 胜出路径和原连接修复按需暂时持有同路径 ACK 偏好。验证完成、失败或取消后释放作用域。自动快速回落可以复用时效窗口内同一物理绑定上的认证 ACK。备路缺乏该证据时，通过 QUIC 的 PATH_CHALLENGE 和 PATH_RESPONSE 取得独立回程确认，即使只有一端启动验证也能完成。资格仍服从当前授权、绑定归属以及换网验证规则。[历史 ACK 契约](../notes/2026-10-19-backup-ack-contract.md)


仅凭本地已有信息即可执行的探测允许一端直接发起。原生增强轮次优先在同一实际 UDP 绑定上并发向获准的 QAD 和 STUN 观察点取样，按实际目的地址去重。收齐两个有效独立样本即可推进，只有一个样本时保留基础候选。沿用已有的权限、代际、预算和取消规则。本轮受保护协调的接收端汇总双方观测，用自己的分数表计算一次适用的 `mode + index`，对端校验计划的适用范围及许可。原 QUIC 拨号角色、谁触发尝试、谁计算本轮计划分别按其职责确定。打法分数只用于选择打法，获准业务在原连接实际胜出路径上完成往返后才反馈成功。[混合观察入口](../../src/nat_connection.rs#L345) · [接收端计算计划](../../src/nat_punch.rs#L688)

获准转发业务的成员数据中继与原生 relay 同属备用档，两者按上游同档规则比较。已验证的 WebRTC 直连属于主档。两种载体都通过 `CustomTransport` 接入，选路时按各自的数据用途分档。仅转发信令的成员、MQTT 和 IRC 用于受限联系。

融合设计以 miopunch 从第一次寻找对端到原连接实际通过直连收发业务的完整行为为基线。范围包括拨号前读取和筛选候选、重启后复用成员联系记录、建立受限联系、交换当前地址、探测及原连接换路。迁移时应说明保留了哪些行为，以及具体改变了哪些行为和原因。

在相同的时间和发包上限内，若需要在平均建路稍快与让更多原本只能走中继的连接实现直连之间取舍，优先提高直连成功率。

已有共享连接能可靠传递控制消息时，默认在该连接内交换候选、协调探测及确认新路径。业务经健康的数据中继运行时，换路协商复用同一条连接，探测期间业务流继续收发。首次联系需要引导，或已有连接失去传递控制消息的能力时，才使用获准的独立联系入口。原连接仍存活时，验证和换路仍在原连接上完成。

原共享 QUIC 连接已验证一条 UDP 路径，且该路径的本地 socket、对端地址和使用许可仍然有效时，直接复用验证结果供 iroh 选路，跳过重复的候选交换和打洞。仅收到打洞回包时，须保留实际收包的 socket，由原连接验证这条路径。按需确认对端是否保留临时端口、首次业务是否满足放行条件；若对端仍在等本轮结果，通过已有控制交换告知结果并结束该轮。

仅当双方为同一对端发起的尝试实际争用同一探测名额时，才按双方已有的节点身份打破平局，让尚未开始实质探测的一次让行。尚未采样、发探测包的让行不计作一次完整探测失败。可跨连接复用的地址仅作为线索，专用 socket 和验证结果仍归各自的原连接，由原连接验证并按选路策略换路。

原生节点重启后首次向已知成员拨业务连接时，若没有当前活跃的直连路径，所有近期实际验证过且当前许可仍允许的缓存 TCP、UDP 地址和端口都可与获准的数据中继并行起拨。各路共用本次拨号预算，每条新连接重新确认身份、准入和数据路径，首个合格结果交付业务。仅由对端公告、尚未验证或已经过期的地址继续留在后续候选中。已验证但未被选中承载业务的路径也可学习为可重拨线索。此处按 MIOPUNCH-158、162 扩展了原有单个缓存 IP 的首轮资格。

同一场景下若禁用数据中继且选用获准的 MQTT 联系入口，则并行尝试这些缓存地址和 MQTT 受限联系，共用本次拨号预算。MQTT 先建立受限连接时，双方可交换当前地址并协调打洞，仍在进行的缓存地址尝试继续。任一路先取得已准入、已验证的数据路径，就交付该连接并结束本次多余尝试；预算耗尽仍无数据路径时，业务拨号失败。

原生首拨已知成员时，从第一条数据 relay 实际起拨计时。等待窗口为「本轮获准的 relay 候选数加一」乘以「本轮实际采用的 relay 错峰间隔」。候选按实际获准、去重后参与本轮拨号的集合计数。窗口届满仍无任何一路通过 QUIC 握手确认目标设备身份，就并行启用一个获准的备用信令入口，正在进行的 relay 拨号继续。所有获准 relay 提前确定不可达且仍未联系上目标时立即启用备用入口。没有数据 relay 时直接按受限联系规则执行。各路共用原绝对期限，取消或到期时结束本轮。

备用信令优先使用可达且获准的成员转发。需要公共旁信道时，MQTT 和 IRC 默认先选一个，优先复用已就绪且可用于联系该对端的入口。两者条件相同时优先 MQTT。首选入口明确不可达时立即尝试另一个获准入口。若迟迟收不到对端回应，须在原拨号期限内给另一入口留下联系时间。

浏览器与原生端、浏览器与浏览器之间，双方支持且允许 WebRTC 时，由各自的适配器完成协商和 ICE 建路，通过现有 `CustomTransport` 用 DataChannel 承载原 QUIC 连接的报文。已有可用共享连接时通过它交换 RTC 协商信息；仅有受限联系时通过受保护的控制流协商。原连接在该 DataChannel 上取得新鲜 ACK 且当前授权有效后，这条直连才可用于业务。RTC 不可用或失效时可使用获准且可达的数据中继；仅有信令入口时报告业务数据路径不可用。WebRTC 的适用范围及 TURN 约定见 [ADR 0009](0009-unified-session-and-capability-based-paths.md)。[共享 RTC 适配](../../src/rtc_transport.rs#L1198) · [原连接路径验证](../../src/rtc_transport.rs#L884) · [浏览器注册入口](../../browser-probe/src/network.rs#L2456)

先完成原生 iroh 融合版本，再按新版实际接口讨论 WebRTC 接入。原生 socket 机制限于支持的平台，浏览器仍消费的共享代码由双方保留同一份准入、恢复和取消语义。涉及共享源码的修改以 WASM 构建核对，涉及共同协议的修改还需复验既有浏览器与原生互通入口。融合前的源码观察和已有实测见 [WebRTC 接入复查记录](../notes/2026-11-19-webrtc-after-iroh-fusion.md)。
