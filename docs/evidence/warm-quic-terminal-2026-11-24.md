# 待命 QUIC、备用路径与终端回显

本次实验比较同一对成员的两种做法。在原 QUIC 上保留直连和 relay 时，原终端流可以换路。预建第二条 QUIC 时，原业务通道可以在旧承载结束后开新流续接。以客户端读到故障后第一条命令回显为业务恢复时刻，同时核对远端执行顺序、次数与 shell 状态。[共享成员连接](../adr/0020-shared-member-business-connection.md) · [业务通道续接](../adr/0021-business-channel-continuity.md)

**建议保留每对成员默认一条待命业务 QUIC，由融合端点维护其可用路径。** 在独立出口夹具中，原流能在直连中断后约 1.3–2.6 s 经 relay 继续。默认参数下多留一条连接，空闲包数约翻倍，首条回显仍由原连接送回。刻意让旧承载只能走失效直连时，预建第二条 QUIC 节省了约半秒建连，两个冷暖对照的首条回显均未提前。以下数字来自 Linux 回放及受控双出口。

## 在原连接的两条路径之外预建第二条 QUIC

生产版对同一对成员的普通业务连接做仲裁。实验版在同一 iroh 端点上使用同一对节点身份、同一 relay 登录，通过独立的实验 ALPN 和仲裁槽多保留一条已准入的 relay QUIC。两端核对了两条连接的本地标识和 TLS 导出值。首次附着使用原业务连接，旧承载结束后才允许原业务通道在第二条连接上开流。[实验源码改动生成器](</tmp/mio-warm-second/prepare.py>) · [双端实验驱动](</tmp/mio-warm-second/lab.py>)

原 QUIC 同时保留直连和独立 relay 时，单连接对照在切断直连后 1.853 s 收到首条回显。额外预建 relay QUIC 的一轮为 1.568 s，两轮均在原连接、原流上送回回显。备用 QUIC 在故障期间的 STREAM 帧计数没有增加。两组分别持续切断 40 s 和 8 s，在各自窗口内收齐全部 163 条和 35 条命令。0.285 s 的首条回显差落在生产版单连接重复测得的 1.275–2.589 s 范围内。[单连接](</tmp/mio-warm-second/single40/summary.json>) · [加一条待命连接](</tmp/mio-warm-second/additive8/summary.json>)

空闲流量在故障前测量。保留终端附件，两端停止输入 60 s，取客户端两块 veth 的收发总和，每个上行或下行包在客户端计一次。该计数包含直连、relay TCP、链路协议及同一节点的其他通信。

| 配置 | 客户端两接口收发包 | 客户端两接口收发字节 |
| --- | ---: | ---: |
| 单 QUIC，直连和 relay | 501 | 44,660 B |
| 上述配置再加一条 relay QUIC | 1,005 | 96,065 B |
| 两条 QUIC，路径重新评估周期从 1 s 调到 2 s | 491 | 46,768 B |

相同默认设置下，第二条待命连接这一轮多出 504 包、51,405 B。作为独立参照，生产版保留空闲终端附件的 60 s 为 497 包、44,396 B。关闭终端附件后的 60.12 s 待命窗口为 461 包、42,756 B，窗口前后分别用业务 ping 确认双方仍使用同一成员连接。实验没有测量手机耗电。[生产版空闲终端](</tmp/mio-warm-dual-exit/both1/measured.json>) · [生产版无附件待命](</tmp/mio-warm-dual-exit/standby1/measured.json>)

## 两条健康直连同时可用时，不同流能否各用一条

使用两对独立 veth，分别配置 `10.92.0.x` 和 `10.93.0.x`。生产版 CLI 建立一个成员 QUIC，在两个不同业务流上同时执行 TCP 转发与交互终端。依次验证两条直连同时开放、仅第一条开放、仅第二条开放。每轮均双向逐字节核对 2,293,760 B 转发数据，并收齐 26 次终端回显。

同时开放时，在客户端同一 QUIC 的同一次采样中，两条直连的 ACK 年龄均为 14 ms。第二条直连随后被关闭，双端最终 STREAM 收发计数均为零。稳定业务窗口中，只有第一条直连的 UDP 接口计数增加，客户端在该路径发送 1,869 个 STREAM 帧、接收 1,856 个。两次单路对照分别证实这两个出口都能单独完成相同业务。当前 iroh 为每个发送端的连接选一条业务路径，客户端通常会关闭多余的健康 IP 路径。noq 从待发送流的优先级队列取帧，当前调度没有为不同流各选一条直连。[双直连 CLI](</tmp/mio-healthy-direct-cli/both/result.json>) · [双路径资格与关闭观测](</tmp/mio-healthy-direct-cli/both/events.jsonl>) · [仅第一条](</tmp/mio-healthy-direct-cli/only92/result.json>) · [仅第二条](</tmp/mio-healthy-direct-cli/only93/result.json>) · [iroh 路径选择](../../vendor/iroh/src/socket/remote_map/remote_state.rs#L2180) · [noq 流帧调度](../../vendor/noq-proto/src/connection/streams/state.rs#L522)

### 同一 QUIC 内按流选路

在项目所用的 noq-proto 临时源码副本中，使用真实 QUIC 协议和加解密，通过虚拟时钟模拟两条已验证、独立排队的双向直连。一路基础 RTT 8 ms、带宽 6 Mbit/s，另一路基础 RTT 44 ms、带宽 40 Mbit/s。每 40 ms 发一个 96 B 交互请求并读取对应回显，同时让另一条流持续发送大块数据。每组收齐 100 次回显，以预热后 4 s 内接收方实际交付的字节计大流有效吞吐。

| 同一条 QUIC 的调度方式 | 交互往返 P95 | 大流有效吞吐 |
| --- | ---: | ---: |
| 两个流都用低时延直连 | 32.0 ms | 5.82 Mbit/s |
| 两个流都用高带宽直连 | 54.0 ms | 39.05 Mbit/s |
| 两条直连都开放给现有 noq 调度 | 35.5 ms | 43.64 Mbit/s |
| 交互流固定走低时延直连，大流固定走高带宽直连 | 9.5 ms | 38.90 Mbit/s |

按流分配的一组在解密后核对了每个 STREAM 帧的路径和流 ID。40 个连续的 100 ms 观察段内，都同时收到两条路径分别运送的业务数据。只提高交互流优先级时，两种单路对照的 P95 分别为 30.5 ms 和 53.5 ms。另用两条相同的 8 ms、6 Mbit/s 独立链路复核，放开两路调度时可达 11.66 Mbit/s，交互 P95 为 32.0 ms。按流固定时分别为 5.84 Mbit/s 和 9.5 ms。实验预先知道哪条路径适合哪项业务，未测试自动判断、原生产品按流分配或路径故障时的处理。[16 组协议实验输出](</tmp/miopunch-direct-stream.E425lc/results.log>) · [测试入口与链路参数](</tmp/miopunch-direct-stream.E425lc/noq-proto/src/tests/direct_stream_scheduling.rs>)

### 两个直连地址是否共用瓶颈

Linux 网络层对照使用持续发送的 TCP CUBIC 大流和每 10 ms 一次的 128 B UDP 回显。独立出口组给两对 veth 各设独立 FIFO 队列，共享出口组把两个目标 IP 配在同一对 veth 上。每条链路单向 8 ms、20 Mbit/s，2 s 预热后测量 6 s。4 种配置各重复 3 次，每个实验块打乱顺序。表中取三轮指标的中位数。

| 拓扑 | 两流同用地址 A 的交互 P95 | 回显改走地址 B 的交互 P95 | 大流有效吞吐，同路 → 分流 |
| --- | ---: | ---: | ---: |
| 两个独立出口 | 168.395 ms | 16.281 ms | 19.002 → 19.127 Mbit/s |
| 两个地址共用同一 FIFO 队列 | 167.956 ms | 168.084 ms | 19.000 → 18.998 Mbit/s |

路由和接口计数确认独立组的交互报文实际进入第二条链路，共享组的两个地址都经过第一条链路。每轮发出 600 个回显请求，共享出口分流组的一轮收回 598 个，其余各轮均收齐。这个对照单独验证了绕开排队的收益。只有一个大流持续占满链路，不能用其吞吐估计两条出口的聚合容量。[12 轮数据、路由和队列计数](</tmp/miopunch-direct-bottleneck-ab.JtDLqhhB/trials.jsonl>) · [Linux 实验夹具](</tmp/miopunch-direct-bottleneck-ab.JtDLqhhB/direct_bottleneck_ab.py>)
