- **重拨和真实候选。** Windows 用原配置和同一持久身份退出后重新启动，首次出站由 APS relay 在 14.237 秒交付。重启前缓存已保存家宽端公网 UDP `:9504`，旧静态配置仍是 `:10841`。重启后该连接的增强路径日志使用 `:9504`，原连接提交 UDP path 25，后续业务走新路径。136 的独立固定主机试验另行证明仅给旧目标时会实际拨保存的候选。 [136 验收记录](member-contact-redial-2026-11-18.md)
- **地址观察与交接。** 正常入口两端都实际采到 EU、US East、US West 三个 QAD 观察点的样本。家宽端三点映射一致为 `:9504`，Windows 三点映射各异。137 的受控 SDK 验收覆盖 QAD 样本不足后的获准 STUN 回退。139 的固定办公网顺序试验则明确采用旧 QAD 失败转 STUN 的输入，两组都完成回程和业务。 [137 验收记录](ordered-qad-2026-11-18.md) · [139 回程证据](udp-first-packet-2026-11-18/results.json)
- **慢 relay 和业务阶段。** 第一版普通 demo 的 APS 路径估计 RTT 一度约 9–10 秒，出现连续 3 秒请求超时。后续同配置观测版在 UDP 接管前，Windows 经 APS 收到了多笔 1.11–2.70 秒的匹配回复。UDP 接管后，匹配的 seq 234 从客户端发出到收到回复为 11.14 ms，服务端当时没有等待中的流，读取用 0.07 ms，2,484 字节回复在 0.41 ms 内排入发送队列。两个主机的单调时间只在各自进程内比较。当前样本无法归因早先的 relay 波动。138 的提前起拨仍是实验建议，本轮交付采用普通 SDK 的自动选区。 [138 relay 对照](mio138-relay-comparison-2026-11-18/README.md)
- **采集。** 双端 `status.jsonl` 已实际持续写入，Windows 独立重启后仍写同一历史文件。服务端记录流接收、读取及回复排队，客户端记录请求期限结算和首份有效回复的对端身份、序号、连接标识及该笔 RTT。原始文件留在两端 demo 运行目录。
- **回归和审查。** 普通 demo 测试目标串行运行，3 项通过，1 项原有的专用网络命名空间用例保持忽略。本次只调整原流隔离测试的事件过滤，继续断言原有失败与关闭序列。Standards 和 Spec 对 140 的定向只读复核均无阻断发现。

## 141 现场操作

在 Windows 打开 `http://127.0.0.1:18460/`，确认办公网下能看到业务回复。保持两端当前版本和配置，做一次 **办公网 → 手机热点 → 办公网**。热点获得地址后观察约三分钟再切回，期间让程序自行尝试恢复。

切回后告知已完成，以及大概的两次切换时间。`status.jsonl`、`stdout.log` 和 `stderr.log` 会留在各自机器，后续按两个方向核对热点地址出现到首份匹配回复的时间，分别记录热点期间恢复、切回后才恢复和仍超时的情况。
