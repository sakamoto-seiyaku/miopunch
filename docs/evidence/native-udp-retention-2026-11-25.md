# MioCube 已打通的 UDP 直连为什么被关闭

2026-11-25。原生节点用临时 UDP 端口打洞时，直连可在双方都收到验证回包后被本机主动关闭。已定位到两处代码对“何时可以留下这个端口”的要求不同。本机对照可以只改变选路结果，让同一个端口先被拒绝、再被保留。

## 现场的成功与失败

| 观察 | u22sz | r_proxy |
| --- | --- | --- |
| 首次现场实验 | 第一条候选被应用关闭。第二次使用另一个临时端口，在首个业务回复后 47.521 秒选中直连。 | 48.612 秒选中直连。随后两端各增加 103 次有效业务往返，原连接标识一致。 |
| 加入阶段日志后的实验 | 延长日志中六个可与对端配对的维护轮次，均在双方验证完成后提交临时端口失败。 | 六轮均使用原有端口，本端正常结束。路径事件随后记录到对端主动撤销。 |

六轮覆盖 u22sz 主动和应答两种角色。u22sz 从记录本地新鲜 ACK 到提交失败分别经过 594、429、445、777、246、473 毫秒。两端交换的 `SELECTED` 消息只确认对方也到了这个步骤。评选业务路径由另一段代码执行，在路径事件或周期重评时更新。默认质量策略在合格的健康候选之间优先直连。成功现场的采样能确认第二条路径实际承载了业务，无法还原是哪一次重评赶在端口检查前选中了它。 [现场基线](cloudflare-pages-http-observation-2026-11-25.md#u22sz-与-r_proxy-的-p2p-优化实验) · [阶段消息](../../vendor/iroh/src/endpoint/member_fusion/udp/execute.rs#L595) · [选路更新](../../vendor/iroh/src/socket/remote_map/remote_state.rs#L2075)

## 同一端口的对照

两个本机原生端点建立真实 QUIC 连接。先通过现有控制通道联系，再用一个临时 UDP 端口建立备用路径，双方分别在该路径上发起探测并确认回包。试验保有同一临时端口，在两次调用之间只改变测试选路器的选择。

| 提交时的状态 | 端口保留结果 |
| --- | --- |
| 双向已验证，当前仍选原路径 | 返回 `winner requires its validated original selected path` |
| 同一连接、同一 UDP 端口、同一对验证凭据，已选 UDP | 提交成功。释放临时持有者后，原连接上的业务请求收到匹配回复。 |

正式对照一次通过。初版夹具另外开启了第二条 UDP 路径，触发旧路径清理并超时，随后缩减为一条 UDP 候选。对照直接检验真实的端口保留函数，现场轮次的 NAT、重试和选路时序由上面的双机记录覆盖。原始对照源码和 Cargo 输出在本次机器的 `/tmp/miocube-udp-retention-study.v34PxN/` 中。

## 变化来源与影响

11 月 21 日的提交 `35c7bdb0`（MIOPUNCH-161）把“等待真实选中”的步骤移到了自动维护分支之后，以便 TCP 已在用时，验证成功的 UDP 也能作为备路。9 月 30 日提交 `7848afab` 引入的临时端口保留函数仍要求同一原连接已经选中使用该端口的路径。自动维护交换控制消息后立即调用这个函数。检查失败时，未提交的端口会关闭，调用方拥有的临时候选路径也会关闭。另一端使用原有端口时无需提交临时端口，因此两端可报告不同结果。现场错误还合并了连接归属、连接关闭和端口存活条件；本机对照独立证实“尚未选中”这一项足以触发同一错误。 [当时的设计目标](native-parallel-paths-161.md#L7) · [自动维护提交顺序](../../vendor/iroh/src/endpoint/member_fusion/udp/execute.rs#L311) · [临时端口检查与关闭](../../vendor/iroh/src/socket.rs#L498) · [候选路径关闭](../../vendor/iroh/src/endpoint/restricted.rs#L1610)

现场直接证实的是原生 IPv4 待命维护使用临时端口的情况。前台自动改善也走同一分支。当前节点的两轮实际探测至少间隔 32 秒，反复丢掉已验证的候选会延长中继使用时间。老的显式打洞流程会先等到选中。用原有 UDP 端口获胜也会跳过临时端口检查。 [分支范围](../../vendor/iroh/src/endpoint/member_fusion.rs#L2101) · [临时端口归属](../../vendor/iroh/src/socket.rs#L692) · [轮次冷却](../../vendor/iroh/src/endpoint/member_fusion/udp/slot.rs#L45)

修复时需要验证以下行为。业务继续使用健康的中继或 TCP 时，自动维护能在原连接上保留已验证的 UDP 备路。随后切换到它能直接完成业务往返。验证证据要绑定原连接、对端和实际端口，过期、撤销、取消及关闭后的端口要正常回收。现有 NAT 驱动分别覆盖自动固定端口和显式随机端口，需覆盖两者的交集，即自动维护使用临时端口、提交时业务仍走另一条路。 [NAT 用例入口](../../tests/support/member_fusion_nat.rs#L55)

## 修复后的实测

自动维护和前台改善在原连接上保留本轮取得双端回包的获胜路径。临时端口的归属、实际本地绑定、路径探测凭据、轮次有效性及权限在结束阶段交换前后都要有效。端口与候选路径一直由本轮持有，成功时一起交给原连接。选路策略仍决定何时使用备路，显式业务确认仍负责学习结果。 [自动维护交接](../../vendor/iroh/src/endpoint/member_fusion/udp/execute.rs#L307)

在同一个双 NAT 用例中，旧版关闭了已验证的临时路径。修复后，两组均在中继仍被选中时留下 1 个获胜端口，另外 255 个端口逐一重新绑定成功。撤下中继后，两端在原 QUIC 连接的原业务流上，从同一轮保留的 UDP 路径实际收到了业务字节。另用两端都开临时端口的连接验证了双端回包后撤路和换网，端口均可重新绑定，原 TCP 控制连接仍可通信。 [NAT 回归](../../tests/support/member_fusion_nat.rs) · [端口回收用例](../../tests/legacy_multi_socket.rs)

u22sz 与 r_proxy 保留原身份运行修复版。两端在维护轮次 `040eaccb7920c217057f758efde81940` 上均确认并保留路径 3。u22sz 用临时 socket 127，从本端 ACK 到保留耗时 194 ms；r_proxy 用主 socket 0，耗时 223 ms。两次独立状态采样之间，u22sz 的成功往返从 59 增至 354，r_proxy 从 61 增至 361，失败数分别保持 0 和 6。两端各自的连接标识、路径和物理 socket 都一致，UDP 路径的 STREAM 收发计数均增长。

本次附带运行的旧 `random-cancel` 用例在注入取消前因剩余预算不足 20 秒退出。本机 WSL2 独立测得建立并关闭 256 个 UDP socket 约需 18.4 秒；该用例的总预算为 38 秒。该次运行未验证取消后的两秒时限。
