# MIOPUNCH-21 · MQTT control to UDP data path

This is the executable result for [MIOPUNCH-21](http://192.168.4.22:2080/work/projects/aa58cd82-2afc-404b-a097-58ef553c7ca4/issues/f98160e7-4899-4961-8750-5f7b49a8074e), after [MIOPUNCH-20's real MQTT handshake](2026-09-29-mqtt-control-validation.md). The experiment uses two real iroh identities, one real Mosquitto service, and UDP loopback as the known data route. A controlled UDP forwarder is used only for the failure case. Neither experiment relies on a replacement QUIC connection, a simulated TLS result, or ciphertext string search.

## Reproduce

Run a dedicated broker with `scripts/mosquitto-test.conf`, for example:

```sh
docker run --rm -d --name miopunch-21-mqtt -p 127.0.0.1:43256:1883 \
  -v "$PWD/scripts/mosquitto-test.conf:/mosquitto/config/mosquitto.conf:ro" eclipse-mosquitto:2
MIOPUNCH_MQTT_BROKER=127.0.0.1:43256 cargo test --locked --test mqtt_upgrade -- --nocapture
docker rm -f miopunch-21-mqtt
```

`tests/mqtt_upgrade.rs` first establishes the control connection using only the MQTT route; its ALPN suppresses automatic UDP candidate sharing and QNT. A protected control stream exchanges `PING/PONG`, then the dialing node opens a known UDP path on that exact connection. Both nodes observe an established IP path, install a per-connection packet path gate, close the MQTT path, and only then use the existing control stream, a new ordinary stream, and a DATAGRAM. The stable ID on each endpoint remains unchanged. A second concurrent MQTT control connection to the same peer stays restricted; its custom path is not propagated back into the data connection. A later restricted attempt also starts on its explicitly supplied MQTT route even when the peer actor still selects IP for an older data connection.

The priority fault test places a 16 KiB business message in the bounded `ControlSession` queue (1 MiB and 64 nonempty messages) **before** UDP path establishment and checks that this queue causes no MQTT publish. `ControlSession::connect/accept` own the raw iroh connection and expose only the control stream and path setup; both sides receive a normal business handle only when `commit_data_path` succeeds. A premature commit returns the still-restricted session with its queue intact; a separately tested closed control connection returns a terminal error and no business handle. After both nodes commit, the test releases the queue, holds the resulting UDP datagrams at a forwarding boundary, then cuts that path. In one local run the forwarder held 8 UDP packets and observed 12 further retry or probe packets after the cut, before the DATAGRAM was added. Neither endpoint's MQTT publish count increased; the original client connection ended `TimedOut` **3,990 ms** after the cut with a configured 4-second QUIC idle timeout. Both nodes observed the original custom path's `Closed` event at promotion, and after promotion each data connection listed only an IP path. This test does not claim that a newly dialed connection preserves the old stream.

The real broker test also forces a **fresh remote custom path attempt**: the server commits to data-only while the client is still in its control phase, then a test-only hook closes and reopens the client's MQTT path. The server's per-connection pre-QUIC ingress rejection counter rises, and the business connection never regains a custom path. The hook is compiled only with `miopunch-test-hooks`, enabled by this package's test dependency. The client then commits and normal business proceeds on UDP. An observer additionally captures an authenticated 1-RTT MQTT packet before promotion and republishes it afterwards; the adapter accepts it, but neither the old data connection nor the parallel control connection yields a new application stream. Old connection IDs can be rejected before the per-connection ingress counter, so that replay is a separate delivery check. A local request to reopen custom on a data-only connection is rejected before path creation. The path gate also runs at egress before the carrier sender and clears a packet already buffered by noq for a forbidden path when installed; `Backup` status and asynchronous path events are not treated as permission. The `ControlSession` facade is the business handoff used in the failure test; callers that bypass it and use a raw control-phase `iroh::Connection` can still open arbitrary streams. Product connection engines must preserve this staged ownership rule.

Control-only endpoints disable TLS early data and reject the early Connection APIs. The real broker test confirms both outbound 0-RTT and inbound 0.5-RTT handle requests fail while an ordinary full handshake remains possible. This is an endpoint-wide restriction in the current fork: other ALPNs on that endpoint also lose early data. A later mixed-ALPN design may narrow it, but may not allow restricted control traffic to bypass the stage.

## Mechanism and boundary

An iroh-only H1 based on selecting UDP and closing custom paths after `Established` cannot guarantee the send-before-event window: the existing peer actor can open the selected custom path on other connections, and noq can send application data on a Backup path when no Available path survives. The smallest verified addition is a **per-connection packet path admission hook in noq**, plus one read-only incoming-address accessor in noq-proto. The hook filters transport destinations and incoming source paths before QUIC processing. It does not require frame/stream scheduling changes, because the committed data connection has no permitted control path. The iroh fork carries the stage and peer actor propagation rule. This is a local API change and does not change TLS/QUIC wire format. Fork provenance and exact file deltas are in `vendor/iroh/UPSTREAM.md`, `vendor/noq/UPSTREAM.md`, and `vendor/noq-proto/UPSTREAM.md`.

MQTT still publishes one whole QUIC datagram per message, at most 2,048 bytes, with no application fragmentation. The previous real-carrier run observed at most 1,409-byte MQTT payloads and a 127 ms control round trip. MQTT QoS 0 may lose, duplicate, or reorder delivery; QUIC handles datagram retransmission and ordering of stream bytes, while this adapter bounds its queue to 64. The prior test [record](2026-09-29-mqtt-control-validation.md) includes a real dropped publish, duplicated publish, broker disconnect, explicit cancellation, and rebind. This ticket adds deliberate **reordering**: after a real control handshake, a transparent MQTT TCP proxy reverses two complete outgoing PUBLISH frames, and the server receives the original 16,384 control-stream bytes exactly (`reversed_publish_pairs=1`). The replay and UDP cut tests add the path-transition cases. No result here establishes a throughput or latency guarantee for IRC, MQTT over a remote service, or dual NAT.

The API expects its caller to authorize the known UDP route and withhold ordinary application handles until both peers finish control checks and call `commit_data_path`. For a control-only ALPN, the dialer must provide exactly one explicit custom route and no additional ALPN; the fork binds that attempt's Initial to that route and refuses ambiguous targets. An explicit data-path request returns an error on immediate path creation failure instead of joining a peer-wide retry queue that loses the attempt binding. Full member admission, unknown-peer discovery, arbitrary NAT traversal, TCP business paths, and restoration of an old connection after its idle timeout remain separate work. A new restricted control connection can coexist and redial on its own MQTT route, but its successful handshake alone does not preserve the older data connection or its streams.
