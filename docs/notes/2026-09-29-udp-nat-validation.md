# MIOPUNCH-27: MQTT bootstrap to UDP through two kernel NATs

This is the executable validation for [MIOPUNCH-27](http://192.168.4.22:2080/work/projects/aa58cd82-2afc-404b-a097-58ef553c7ca4/issues/2cdfb6f2-d83a-4c22-8509-16f2a1ec929e). The new Rust probe and runner are [`udp_nat_probe.rs`](../../src/bin/udp_nat_probe.rs) and [`udp_nat_lab.sh`](../../scripts/udp_nat_lab.sh). They use real iroh/noq QUIC, two independently authenticated endpoints, a real Mosquitto broker, a TLS QAD observer, and Linux kernel `veth`/`netns`/conntrack/iptables. The MQTT connection carries only the restricted control exchange; ordinary business is queued by `ControlSession` until an IP path is established and committed.

## Topology and positive result

The runner creates an isolated WAN namespace with the broker and QAD observer at `100.64.27.1`. Node A (`10.27.1.2:42027`) is behind NAT A (`100.64.27.2:42027`), and node B (`10.27.2.2:43027`) is behind NAT B (`100.64.27.6:43027`). Each NAT preserves the node's UDP source port across destinations, but accepts inbound UDP from a remote IP only after the node has sent UDP to that IP. This is endpoint-independent mapping with address-dependent filtering, comparable to the old NAT2 profile. A QAD probe to the observer cannot open the filter for the peer. The exact rules are in the runner. The broker is reachable through outbound TCP, and no data relay is configured.

In the final positive capture, QAD reported A's `100.64.27.2:42027` and B's `100.64.27.6:43027` from their actual bound QUIC UDP sockets. The endpoints exchanged those addresses through the authenticated MQTT-started control connection. A's local QUIC connection ID was `94667177868096` before and after promotion; B's was `140334164268816`. Each final path list contained only the other NAT's IP address and selected `PathId(1)`. B received `NAT_DATA` on that connection. Both endpoint probes checked that MQTT publish counts did not rise during business delivery. The stricter positive case passed twice; the earlier permissive profile had passed three consecutive runs after the path-ID retry fix but was replaced for the acceptance evidence.

The independent [WAN capture](../evidence/mio27-udp-nat/miopunch27-adf-positive-final/wan.pcap) (SHA-256 `f6c43d41948419a250ac3350c3685d6c86afaa0c09295ea6c8cc4d2d0536a4c1`) shows an 11-byte UDP mapping probe in each direction, followed by QUIC UDP datagrams in both directions between those exact public addresses and ports. The paired [client](../evidence/mio27-udp-nat/miopunch27-adf-positive-final/client.log) and [server](../evidence/mio27-udp-nat/miopunch27-adf-positive-final/server.log) logs tie the public candidate, bound socket, authenticated peer ID and selected path to the capture. The evidence directory also retains QAD/broker logs and NAT rule counters.

## Failures and minimal corrections

An initial disposable MASQUERADE diagnostic showed a destination/race-sensitive remap: QAD saw A at `100.64.27.2:47032`, while A's packet toward B left at port `28949`. That run was not retained as acceptance evidence. The final fixture states its NAT semantics explicitly and pins the outgoing source port; it does not claim arbitrary MASQUERADE or symmetric NAT success.

The accepting side cannot call `open_data_path` on the existing QUIC connection: iroh lets only the dialing side open a new path. `Endpoint::prime_udp_path` sends one non-QUIC 11-byte datagram from the accepting side's actual QUIC UDP socket, only for a live restricted control connection. It opens the address-dependent NAT filter without granting data use. The paired [no-prime control](../evidence/mio27-udp-nat/miopunch27-no-prime/) skips exactly that packet: both nodes observe real QAD candidates and complete MQTT control exchange, but B's NAT drops eight inbound packets (8,635 bytes), and both nodes return `PATH_UNAVAILABLE`. This is the stable minimal scenario showing why that fork patch is needed for this NAT class.

An earlier unforced run intermittently returned `path identifiers unavailable; retry explicit path` before spare QUIC path IDs reached the dialer; that transient run was not retained as acceptance evidence. The fork classifies that exact result as `WouldBlock`, and `ControlSession` retries the same address on the same authenticated connection for at most two seconds. The [path-ID retry run](../evidence/mio27-udp-nat/miopunch27-path-id-retry/) uses the optional `nat-lab-test-hooks` build to **inject one** such transient result after the real MQTT candidate exchange. Its client reports `path_id_retries=1`; the following attempt establishes the real QUIC UDP path through both kernel NATs and delivers business. The hook forces the error branch, not network success, and does not claim a deterministic natural CID shortage. The original peer-wide retry queue was not used, so the attempt stays bound to the authenticated connection. The fork delta and test hook are recorded in [`UPSTREAM.md`](../../vendor/iroh/UPSTREAM.md).

The final negative runs passed:

| Case | Real fault and public result |
| --- | --- |
| [Blocked UDP](../evidence/mio27-udp-nat/miopunch27-adf-blocked/) | Both WAN forwarding directions DROP peer UDP while QAD and MQTT remain available. Both nodes report `PATH_UNAVAILABLE` within about 17 seconds; WAN counters record eight A→B and one B→A dropped packets. No `DATA_OK` or business handle appears. |
| [Wrong candidate](../evidence/mio27-udp-nat/miopunch27-adf-wrong/) | Client receives B's true `100.64.27.6:43027`, then deliberately attempts port `9`. Both nodes report `PATH_UNAVAILABLE` within about 17 seconds. |
| [Stale candidate](../evidence/mio27-udp-nat/miopunch27-adf-stale/) | A network-change hint invalidates a previously fresh QAD result. The probe checks `is_fresh()` and rejects it before exchange; B reports `CONTROL_UNAVAILABLE`. |
| [Control cut](../evidence/mio27-udp-nat/miopunch27-adf-control-cut/) | The runner kills Mosquitto after the authenticated control connection is ready but before candidate exchange. Both nodes report `CONTROL_UNAVAILABLE` within about 16 seconds. |

The failure probes retain the ordinary business bytes in `ControlSession` and never release a data handle. MQTT still carries QUIC control retransmissions before the terminal result, so a changing total MQTT packet count in these failure logs is expected; it is not evidence that business fell into signaling. The control/data separation after promotion is additionally covered by `tests/mqtt_upgrade.rs`, including a blocked UDP data path and post-promotion MQTT ingress rejection.

## Reproduce and limits

Build the native probes with `rtk cargo build --locked --bin udp_nat_probe --bin udp_observation_probe`. For the injected path-ID case, build `udp_nat_probe` with `rtk cargo build --locked --features nat-lab-test-hooks --bin udp_nat_probe`; the normal build has no forced-error hook. Copy both binaries and `scripts/udp_nat_lab.sh` into a disposable Debian 12 QEMU VM with root access, `iproute2`, `iptables`, `tcpdump`, and `mosquitto`. Run `sudo bash udp_nat_lab.sh CASE ./udp_nat_probe ./udp_observation_probe /tmp/CASE-evidence`, where `CASE` is `positive`, `no_prime`, `path_id_retry`, `blocked`, `wrong`, `stale`, or `control_cut`. The runner creates unique namespaces, captures WAN UDP, writes logs and counters, then removes its namespaces and processes. The old VM's NATX materials supplied topology/profile facts; its Go/OpenSpec gates were not reused as the new Rust acceptance result.

This validates one endpoint-independent mapping/address-dependent filtering dual-NAT class and bounded failure when peer UDP is blocked or candidates/control are unusable. Destination-dependent mappings, changing external ports, arbitrary carrier latency, relays, and cross-operator success rates remain unproven. QAD observation alone does not promise peer reachability; the actual selected QUIC UDP path is the success criterion here.
