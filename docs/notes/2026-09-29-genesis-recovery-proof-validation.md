# MIOPUNCH-25: root proof and recovery without the admission secret

This is the narrow, runnable result for [MIOPUNCH-25](http://192.168.4.22:2080/work/projects/aa58cd82-2afc-404b-a097-58ef553c7ca4/issues/c07f1add-ecbf-4220-b02b-e47fec769067). It uses the signed management mapping in [ADR 0007](../adr/0007-signed-management-authority-mapping.md), the [accepted recovery credential decision](../adr/0008-genesis-recovery-credential-pins-create.md), and the complete SQLite record store validated in [MIOPUNCH-24](2026-09-29-management-store-recovery-validation.md). The public seam is `recover_client` / `serve_recovery` in `src/genesis_recovery.rs`; the real two-node test is `tests/genesis_recovery.rs`.

## Fixed qualification profile

- The recovering device loads one `GenesisCredential` consisting of its original Ed25519 genesis signing key **and saved canonical Create hash**. These two fields are the trusted recovery anchor. It needs neither the old admission secret, author log tail, nor management history. The contacted member checks its own pinned anchor during the proof; the client checks the returned complete history against the backup hash. A root key alone cannot start this recovery entry.
- The client connects to a designated, known `EndpointId` using the restricted `miopunch/genesis-recovery/1` ALPN. The server must be a currently authorized real device in its local management view; an ordinary `Read` member can serve. Both sides use the authenticated TLS node IDs from the live iroh connection. 0-RTT is outside this entry: it accepts only a completed `Connection`.
- The client signs one fixed-length, domain-separated statement with the existing p2panda-core Ed25519 root key. It contains the root public key, fixed Create hash, recovering node ID, contact node ID, and the 32-byte [RFC 9266](https://www.rfc-editor.org/rfc/rfc9266.html#section-2) `tls-exporter` channel binding (`EXPORTER-Channel-Binding`, empty context) from that exact TLS connection. The member verifies it against its pinned anchor before sending any management record or secret byte. No shared admission secret, old administrator, self-reported node identity, reusable nonce, or hand-written HMAC mechanism participates in the proof.
- After proof, the member sends its locally **applied**, complete signed history and current `(network ID, secret generation, admission secret)` on the same encrypted connection. The client replays all records through `ManagementAuth`, verifies the canonical Create and that the contact is an authorized node, then signs an `Add Manage` for its own TLS node ID. This new root-author record has a fresh random 128-bit log ID, sequence zero, and dependencies on the recovered graph heads. The ordinary member ingests and applies it durably before acknowledging its hash. Neither side revokes old administrators as part of recovery.
- A single exchange has a 15-second deadline, at most 32 concurrent calls, at most 4,096 records, and at most 16 MiB of encoded recovery material. Success or failure closes the client's TLS connection. The server waits for that closure after sending its acknowledgment and closes on failure or timeout. The returned secret and records must be saved by the caller before it reports completed local recovery.

This is a technical connection proof profile assembled from the existing iroh TLS channel binding and p2panda Ed25519 verifier, not a claim that a separate standardized recovery wire protocol already exists. The interface is deliberately restricted to root recovery and does not grant anonymous history reads, normal sync, or business traffic. Product admission and general protocol routing must apply the same ALPN gate when integrated.

## Reproduce and observed behavior

Run `cargo test --locked --test genesis_recovery` with loopback sockets permitted. The first test starts two real iroh endpoints, with only an ordinary member online and a fresh recovering node holding its root key and saved canonical Create hash, but no admission secret or management history. The member serves from file-backed SQLite; the client validates the delivered Create/history against its fixed anchor, signs a new administrator grant, and receives the scoped secret. Both views retain the offline old administrator. The client writes the delivered records into its own SQLite file and reopens it; its new administrator grant and the old administrator are still present. The new grant uses a separate root author log, so no old root log tail is needed.

The priority failure test supplies a wrong root signature, the correct root signing a different Create hash, the wrong target node ID, and a signature copied from a previous TLS connection. Each is rejected before the member sends even the first history byte; no authorization record is applied. Calling the public recovery entry with a saved but wrong Create hash also fails. This verifies the actual root signature and exporter-bound peer/session context through real TLS, rather than a mocked proof result.

## Limits for follow-on implementation

The serving member proves what its **local** authorized history and configured secret generation contain. Neither party proves that this is the network's globally latest state; a later synchronization may correct it. The fixed Create hash prevents a different root-signed history from being mistaken for the original network, even when both histories use the same root public key. Losing that hash makes this recovery credential incomplete; the implementation does not silently adopt a new peer-selected anchor.

The test does not supply candidate discovery, a production endpoint handler, persistent storage for the recovered admission secret, root key backup packaging, or a general management UI. The caller must choose the trusted contact, configure the restricted ALPN without 0-RTT, and persist the returned secret securely. A production service also needs sustained rate limiting at its connection queue and an explicit credential/source policy when the local admission secret is unavailable or stale.
