# miopunch 网络场景推演

日期：2026-09-28。状态：讨论草案，不是正式规格、实现任务或测试结果。

依据：[当前主线](2026-09-27-product-mainline-draft.md)与[最新讨论约束](2026-09-27-network-repositioning-discussion-draft.md#19-2026-09-28暂停-acl按实际场景推进)。本轮暂停 ACL 设计，不引入两套访问配置；产品提供可用引导途径，普通用户不编排底层渠道。

## 0. 恢复主流程：先复用已知途径，再扩展发现

用户随后用 BT/Kad 等网络说明期望：恢复时有明确状态，先尝试已知优先级较高的联络/连接途径，例如已有 relay 路线、可直接访问的节点地址；未能接上成员时，再利用旁路查询线索、发送建连消息和协调打洞；另有长期稳定的引导途径兜底。下文 MQTT 场景只是其中一条分支，不代表每次恢复都必须先接 MQTT。

本轮研究采用成熟的引导与节点维护思路，不因此决定部署一套全网 DHT。资料与事实边界见[引导恢复调查](2026-09-28-bootstrap-recovery-research.md)。

候选恢复流程如下，具体超时、并行度与缓存策略未定：

资源约束先于以下尝试顺序：用户已明确接受官方公共 relay 的已知限制，同时要求允许禁用官方 relay、改用自建服务或受支持的扩展。被禁用的资源不参与首次建连、协商辅助或后续失败回退，不能因它是官方设施就绕过用户选择。默认交付包含可用的 STUN、MQTT 等资源配置，按可用性随客户端维护更新，具体服务实例在交付时核查；更新保留用户的禁用和替换设置，见[主线资源规则](2026-09-27-product-mainline-draft.md#4-资源来源与统一描述)。

1. 恢复本地身份与已知联系人、联系线索及过去成功记录。它们是尝试依据，不是当前可达保证。
2. 优先尝试已有、获准使用且较有希望成功的连接途径，可能经 relay，也可能直接访问节点地址。连上公共设施本身不算已接上本网成员。
3. 没有及时形成成员连接时，扩展寻址和信令途径，取得更新线索、联系对方并协调打洞。新的线索继续进入同一连接尝试过程。
4. 普通线索不能恢复联系时，使用产品支持且用户允许的长期引导入口，使当前在线成员仍有机会相互发现和交换受保护信令；没有获准入口时不能暗中启用被禁用的公共设施。
5. 获得安全成员连接后开始必要补齐，刷新线索与成功记录，继续维护和改善路径。不等待全部成员上线，也不等待全网同步完成才一概开始使用。
6. 暂时没有任何成员可联系时，保持可联络、按退避策略重试，等待新的消息或网络变化；不把未知原因的暂不可达断言成全体成员确定离线。

优先级不必实现成严格串行等待所有旧地址超时。助手建议保留优先尝试顺序，但使用有界等待、有限并行及失败退避，避免长期离线后的旧缓存拖住恢复；具体调度尚未确认。

长期引导表示联系入口或发现规则具有稳定性，不意味着临时打洞信息永不过期、某家公共服务永久在线，或对端全部离线时仍能建立实时连接。若希望固定信令入口能找到在线成员，就需要相应接收方维持或恢复可联络状态；具体采用订阅、地址发布还是其他方式未定，也不要求所有渠道同时常开。

对于“兜底使用官方 iroh”的设想，必须区分地址查询与实时 relay：前者查找已知身份的新联系线索，后者向当前接入的端点转发数据包；不能把原生 relay 当成持久离线信令邮箱。具体默认资源仍未选定。

## 1. 首个场景：老成员返回

### 场景状态

- A 是用户手机，已经加入网络，客户端停止运行三天，原身份与本地保存状态仍在。现在手机使用另一张网络。
- B 是同网电脑，当前在线，是 A 已知的成员。A、B 都可以位于 NAT 后，不预设 B 有公网监听地址。本例没有成员资格、密钥或访问授权变更。
- C 是另一台成员设备，当前离线。C 离线前发布过一条普通描述更新，例如设备名称；B 已经保存其可验证记录，A 尚未收到。
- 产品已经为该网络配置可用的初始联络途径。本例选 MQTT 消息途径，B 当前可通过它联系；不要求用户租 VPS、手填 broker/topic 或选择打洞策略。
- 本例所需的地址观察资源可用，双方经过协商可以建立 UDP 直连。这个成功条件只用于先走通正常故事，不是对真实网络成功率的承诺。

选择 C 的普通描述更新，是为了检验“原作者离线，其他副本仍能供给记录”，不把本轮重新扩展到 ACL 冲突。具体记录格式尚未决定。

### 用户目标

用户打开客户端，恢复连接到已经加入的网络，其他组网步骤由系统进行。无需重新申请成员资格，无需管理员在线，无需理解本次使用了哪种联络或打洞方式。

访问 B 的既有服务是后续可选动作，不是触发恢复组网与状态同步的必需操作。底层恢复不能等待用户先选择某项业务。

### 双方怎样先交换消息

本例的 MQTT/IRC 类消息渠道主要用于交换打洞与建连信息，不被当成已经存在的 A-B 数据连接，也不作为本例批量记录同步和业务传输的承载。

B 在自己启动或恢复网络时，也需要让自己可被联络。本例由 B 主动连接配置中的 MQTT 服务，并接收发给自己的建连消息；A 返回后同样主动接入可用入口。两边不需要先向对方开放公网端口，先通过各自到入口的连接交换受保护的消息。

```text
A --主动接入--> MQTT 服务 <--主动接入-- B
                   |
       递送受限握手，建立 A-B 安全控制会话

A <---- 协同打洞，或使用可用中继 ----> B
                   |
           为端点安全会话取得获准数据路径
                   |
             状态补齐、后续业务
```

本例使用双方能互相递送消息的同一 MQTT 入口。2026-09-28 已确认旁信道可转交受限的 iroh 握手和控制报文，先形成安全控制会话再协调路径；MQTT 是例子，也可适配 IRC 等消息渠道。具体 topic、封套与准入证明仍需核查，见[旁信道引导决议](../adr/0005-side-channel-control-bootstrap.md)。其他情形可以由已有节点转交信令，或使用双方已知且实际可达的直连地址。仅知道一个公网 IP 不代表目标端口可达，仍需尝试和验证。

两边没有固定的客户端/公网服务器分工；B 先启动时会做类似的本地恢复与联络准备。双方也可能同时发起尝试，后续需要在连接库内部处理重复与协调，不把这种情况交给用户解决。

### 系统流程

| 步骤 | 系统行为 | 这一阶段不能误认的结果 |
| --- | --- | --- |
| 1. 恢复本地状态 | 加载 A 的身份、已有成员记录及联系线索；可以先呈现已有设备列表 | 已知设备列表不等于实时在线列表，也不要求先联系全网 |
| 2. 建立安全控制会话 | A、B 各自接入可用联络途径；经消息载体转交受限 iroh 握手，认证节点身份并核对预期 B，再处理该阶段获准的私密控制 | B 不需要先有公网可达地址；知道 topic 不获得解密权；节点身份认证不等于成员准入或正常业务已可用 |
| 3. 协调数据路径 | 按本地准入状态放行必要的地址观察与候选交换，在受保护会话内协调探测及打洞；本例得到可用直连路径 | 消息递送与地址观察职责不同；受限旁信道不能自动成为业务承载路径 |
| 4. 开放正常通信 | 验证可用数据路径，满足本场景成员准入条件后开放正常同步及获准业务，目标是保持同一端点安全会话 | 获得一条 A-B 数据路径不代表全网在线或全网状态一致；新载体到数据路径的接入仍需验证 |
| 5. 补齐记录 | 经可用连接与 B 比较同步进度或差异，取得 B 持有而 A 缺少的相关记录；验证、保存并更新本地视图 | C 的记录由 B 转交，来源仍是 C；补齐 B 持有的记录不等于已知全网绝对最新状态 |
| 6. 持续组网 | 系统继续必要同步与连接维护；用户需要时再访问 B 的既有服务 | 不因为 C 离线阻塞 A-B 使用，也不要求用户发起业务来维持组网；不保证旧业务连接跨任意断网都能续接 |

本表按依赖关系叙述，不冻结线程模型或所有操作的串行顺序。全网补齐不作为服务可用的统一前置条件；具体业务需要的准入检查仍须满足，本轮不展开 ACL。复用 iroh 安全会话的方向已确认，准入证明、同步库接入方式与重试参数仍需核查。

这只是消息协商后直连的流程，不是所有连接必须经过的固定顺序。若已有可用且获准的 relay 或普通节点数据中继，也可以先经其形成端到端安全连接，开始同步并继续尝试改善路径。仅允许信令转交的节点不能因此自动承担业务数据中继。已有实际可达地址时，也不必强制先绕经 MQTT。

逻辑上的共同条件是：批量状态交换与后续业务需要一条可用的端点间安全数据连接；它可以来自直连或中继。联络入口可用、收到对端信令、已建立安全数据连接，是不同事实，不能互相代替。

### 成功标准

用户打开客户端并恢复网络后，系统能够自动建立本例 A-B 的安全数据连接并进行状态补齐；A 能从 B 获得并验证 C 的既有更新，即使 C 当前离线。B 的既有服务在用户需要时可使用，不以用户已经访问该服务作为组网成功的条件。过程不需要管理员重新批准 A 入网，也不要求用户处理 NAT、信令或复制进度。

系统对外应区分“某个设备可用”与“正在继续同步其他信息”，不把任何单次连接或同步完成显示成全网一致。具体界面尚未设计。

### 职责检查

- 本地已有状态足以开始尝试联系，不等待最新全网状态。
- 改造后的连接库负责联络、协商、建连与路径维护；同步使用其提供的连接，不反过来要求调用者手工编排打洞。
- 同步与持久化负责记录差异、保存和补齐；记录的发布者及授权含义由相应验证规则判定，不由转交节点替代。
- 持久联系线索供连接过程参考，连接过程维护实际可达性；不因为保存了地址就视其为已验证路径。

## 2. 常态运行：部分互联，按需增强

用户已确认 A 尚未直接连接 C，也可以算正常接入网络。同时补充：系统仍应尽量争取成员间互联，不将其缩减为完全被动的“有业务才打洞”。全互连不是正确运行的前提，也不要求所有节点对之间持续保活或有业务流量。

场景中 A、B、C 均在线，已有 A-B 和 B-C 安全连接，尚无 A-C 直接连接：

```text
A ---- B ---- C
```

### 没有 A-C 业务时

已有连接可用于记录传播与信令协助。A 可以经 B 获得 C 的有效记录，不要求 C 每次亲自递送；这不表示 A 与 C 已有直接连接。系统可以主动寻找、尝试新的互联机会，但不把每对节点持续打洞和保活设为硬要求，也不固定要求 A-C 一定先建立连接。

后台维护采用每节点预算：手机可偏保守，常开路由器、网关等可更积极；活动业务优先，连续失败退避，新线索、网络变化或业务需求可提升尝试积极程度。优先复用底座既有机制，具体频率、并发上限、连接数量和空闲回收参数通过验证调整，不要求普通用户配置。网络状态保存范围与实际连接图是不同问题，本场景不限制节点保存的有效状态。

### A 开始使用 C 时

1. 连接库利用已有状态和途径，尝试形成 A-C 的端到端安全连接，上层业务不手工选择 MQTT、经 B 转交或具体打洞步骤。
2. 如果 B 已启用业务数据中继，且这条路线实际可用、符合使用策略，A-C 可以先经 B 通信。不要求先证明所有直连办法都失败才允许用中继。
3. B 作为中继转发的是 A-C 端点间受保护的数据，不能用 A-B 和 B-C 分别加密来代替 A-C 的端到端保护。这是目标行为，不是声称普通节点中继已经实现。
4. 需要时继续通过可用信令途径协调直接连接。这些途径可以是已有节点转交、旁路消息渠道或已有安全连接上的协商，不强制再次使用公共入口。
5. 直连建立后，按质量和用户策略决定是否使用；不因直连能通便强制放弃效果更好的获准中继。新载体下具体会话连续性仍需实现验证。

如果 B 没有启用数据中继，它仍可以协助信令，不能因 A-C 有业务需求就自动打开其数据转发。此时需要形成其他获准路径；暂时没有 A-C 数据路径，不等于 A-B 已有连接或整个网络都失效。

### 统一过程的含义

后台改善互联与业务触发的连接需求，应共享已有联系线索、路径状态和连接维护能力，不为每种渠道重复建立一套恢复系统。它们可以有不同的尝试积极程度，但具体调度方式尚未决定。

这里没有新增固定中心：B 只是当前可提供帮助的成员。也没有承诺任意多跳自动路由；本例先讨论一个中间节点，更多中间节点的行为仍需单独验证。

## 3. 承载路径故障：尽量保留原连接

用户认可延续 iroh 的连接连续性方向：A-C 原本经 B 中继，B 突然失效；有其他路径就尽量保持原连接继续传，没有现成路径就利用可用信令重新协调。最终仍无法维持连接，则接受该连接失败，不要求组网层替所有业务恢复应用状态。

这里的“连续性”指同一条端到端连接在其存续期间更换承载路径，不是分布式记录一致性，也不是任意时长断网都不关闭连接。

### 按实际可用条件处理

1. 若已有可用的 A-C 直连路径，或经另一节点 D 的获准中继路径，并能用于同一 A-C 连接，尝试切换到合适路径，维持既有 stream 的传输。
2. 若没有现成路径，则通过可用的旁路、其他成员或中继重新交换信令、协调打洞与建立路径。在原连接仍能存活的范围内恢复传输，具体超时和尝试预算尚未决定。
3. 如果原连接最终超时、关闭或无法维持，向调用方明确报告失败，不伪装成仍可传输。客户端仍可继续执行网络恢复；之后建立的新连接不是旧连接的复活。

业务在原连接仍存活并恢复承载后可以继续传输；原连接终止后的重试、断点续传或应用状态恢复由相应业务处理。本项目不因此新增通用的上层业务恢复协议，也不为了隐藏失败无限期等待。

### 复用与验证范围

iroh 1.2.0 的 Connection 提供同一连接的路径列表、路径变化与选中路径变化事件，典型情形包括 relay 路径和打洞后的直接路径。这是复用现有多路径连接能力的依据。[Connection API](https://docs.rs/iroh/1.2.0/iroh/endpoint/struct.Connection.html#method.paths)

新的普通节点中继、TCP 或其他载体必须实际接入并验证同一连接的路径机制，不能仅因可以重新拨号就声称保留原连接。B/D 的例子表达目标行为，不表示上游已经自动提供任意普通节点中继或无限多跳路由。

## 4. 本地成员名单过时：只剩新成员在线

用户明确接受：即使 A 从未联系过 C，且本地成员名单中还没有 C，只要 C 能证明自己是本网合法成员，也可以成为 A 恢复网络的第一个联系对象。

### 场景状态

- A、B 原先已经入网，A 长期离线。
- 期间 C 合法加入网络，随后 B 离线。
- A 返回时只有 C 在线；A 不知道 C 的身份或地址，但仍保有本网身份、信任引导材料和兜底入口。
- A、C 可通过产品支持且获准使用的引导途径取得联系。本例不引入相互冲突的成员授权或撤销。

### 目标行为

1. A 不仅重试旧联系人 B，还能通过引导途径发现 C 这个候选成员。
2. A 获取并验证 C 的必要身份与成员授权材料。入口或转交者提供的是线索，不因声称“C 是成员”就能替代验证。
3. 根据可用资源形成端点间安全连接，完成必要准入检查，并从 C 补齐已有的有效记录；不要求 B、原审批者或其他老成员先上线。

身份认证、成员证明交换与安全握手的具体先后和承载方式，需按成熟机制确定。上面的步骤表达所需条件，不强制要求先通过某种自建前置握手验证完成员，再开始 QUIC；也不允许用“必须先全量同步才能验证”把恢复过程卡住。

### 对职责的影响

- 对已知 EndpointId 查询新地址，与发现本地名单尚未记录的合法成员，是不同能力。iroh 的按身份寻址可以复用，但不能单靠它推导出后者已经完成。[Address Lookup](https://docs.iroh.computer/concepts/address-lookup)
- 成员资格来自可验证的授权依据，不来自消息渠道、首次看到的公钥或中继的背书。
- 引导阶段取得必要验证材料，不等于复制完整网络状态；正常同步仍在具备适当连接与准入条件后继续。
- 此场景没有选定群广播、成员目录或 DHT 中的某一种发现机制，也没有改变旁路私密信令的端到端保护要求。

## 5. 后续逐个加入的变化

先确认上面的正常流程，再每次只改变一个条件：入口失效但其他入口可用；联络成功但 UDP 直连失败；已有连接中手机再次换网；返回节点的身份或授权发生变化。

这些是待推演案例，不代表已承诺任意故障自动恢复。第 2 节已明确可以先用获准中继再继续改善路径，第 3 节已明确路径失效时尽量保留原连接、最终失败如实报告。后续再确定具体恢复预算、错误反馈及不同载体下的验证用例，不重新引入通用业务恢复要求。
