2026-10-20。用户在 PRD 发布后指出：尚未具体讨论 UI，也没有原型图，进入正式实施拆票前需要审视其他类似缺口。本文是对现有材料的准备度分析与流程建议，不新增产品范围，不代替 Plane 中的工作项，也不把建议变成已接受的设计。

需求入口为 [MIOPUNCH-107：首版客户端 PRD](http://192.168.4.22:2080/work/projects/aa58cd82-2afc-404b-a097-58ef553c7ca4/issues/6159ec62-a03e-4eb7-9b95-4ddc19ce7a02)。当前状态应理解为：功能范围与主要行为已经确认，具体界面、部分跨模块契约及关键运行接入仍未收敛。`ready-for-agent` 允许后续开展设计和验证，不证明所有业务已具备直接编码条件。

## 当前已经明确的部分

- 首版五个业务模块，以及一对一剪贴板、文件接收与失败规则、TCP/UDP 转发、应用内网页和 tmux 多会话的主要行为。
- 三种节点角色、单一有效 ACL、来宾邀请范围与期限、创世操作逐项确认。
- 创建与加入的主要用户路径、恢复卡要求、设备管理、同一节点换机的结果语义。
- 平台范围、Vue/Tauri/Rust 分工、浏览器独立节点、桌面与 Android 的主要生命周期和网页交付方向。
- 用户确认的验收边界：真实双端业务、权限及实际平台生命周期，界面测试负责交互。

这些内容继续作为设计输入。后续工作应将其落成可评审方案，而不是重新从零询问所有功能或扩大功能清单。

仓库核查范围为当前实现与设计材料，排除 legacy 和实验构件。当前找到的 Web 页面主要是 [browser probe](../../browser-probe/network.html) 与测试入口；没有发现正式 Vue/Tauri 产品页面、产品线框图或完整的客户端交互原型。上述结论不把已有探针或历史界面当作新基线的产品方案。

## 建议先形成的最小设计产物

1. **页面地图与核心流程线框。** 先将已有设备／服务中心方向展开成可比较的整体结构，覆盖桌面和手机。重点是入口、信息层级和完成操作的路径。
2. **可点击的低保真 UI 原型。** 使用明确的演示数据，让用户实际走过关键流程并比较少量结构方案；不连接真实危险操作，不用演示状态冒充后台已实现。
3. **简短的模块接口与状态说明。** 从选定交互提炼 UI 真正需要的操作、结果和订阅，明确节点与界面的所有权边界；只固定跨端必须一致的契约。
4. **关键接入的可运行证明。** 优先覆盖应用内网页承载与隔离、Android/桌面节点宿主，以及新增权限流程。复用已有底座，验证新增接线，避免重做已经具备证据的基础连接研究。
5. **回写规格。** 将选定界面、接口及技术原型的结论更新到 MIOPUNCH-107，再据真实前提拆分相关业务实施票。

这些产物不要求一次完成所有像素、组件、异常分支或实现细节。是否能进入某个实施切片，应看该切片的用户路径、公开接口和关键接入前提是否清楚，而不是要求整个项目所有问题同时解决。

2026-10-21 的后续设计访谈明确：用户不关心具体页面层级，允许操作集中在一页，要求停止对此逐项提问。页面地图和线框由设计自行提出，用原型检验实际操作；它们不是要求用户先决定本机入口、页面数量或每层导航的问卷。继续讨论的重点应是影响功能与使用结果的未决项。

同日助手提前开展了[内网页面实验](2026-10-21-inner-web-prototype.md)，用户随后指出不应直接搭建原型。该实验保留为未经设计确认的探索，演示已停止，不作为本阶段设计已经收敛或实施验收完成的依据。当前继续整体设计访谈，再据共同理解确定原型范围与验收目标。

UI 原型回答“用户是否用得顺”；技术原型回答“这条接入在目标环境能否成立”。两类证据需要分别记录。常规内部命名、组件拆法及不改变产品行为的默认处理由实现承担，避免再次把每个工程细节变成用户选择题。
