## 1. 结论与最小复用方向

应保留 p2panda 的签名操作、作者日志、因果依赖、默认 `StrongRemove`、SQLite 操作存储及缺失日志同步。产品真正要补的是三类接线：**在因果状态上验证 miopunch 特有的创世/日常权限；把已收取、已保存、已应用区分清楚并可重启恢复；持久管理邀请、秘密交付、轮换和迁移进度。** 不必另造 CRDT、EBT、群密钥协议或全网事务。高层 API 名称与现成测试不能替代组合后的验收。

| 产品结果 | 已有实现可承担 | 必须补的应用边界 |
| --- | --- | --- |
| 原作者离线，第三方继续供给可验证记录 | 签名头、正文哈希、按作者日志存储与同步 | 权限/记录类型验证、正文与依赖完整性、成功的持久提交、重启后的供给及作用恢复 |
| 管理员并发撤权纠正既有移除 | 现成 `StrongRemove` 和因果状态重建 | 不可变创世锚、日常动作白名单、权限视图变化驱动连接关闭/重新允许新连接 |
| 普通管理员批准成员，创世任免管理员 | 上游 `Manage` 可保留为管理动作及强移除的基础角色 | 上游没有该权限分工；需要接收与重放路径一致的类型化验证 |
| 重试不重复扣码，批准中断后继续交付 | 操作 hash 去重、SQLite 事务、重放 cursor 是可复用原料 | 单核销责任、可信计数、申请与授权结果关联、两项材料接收状态 |
| 所有保留成员持久确认后轮换 | 安全端点通信、存储、签名控制记录可以承载流程 | 轮换进度、接收后提交再确认、入网暂停、提交切换条件；上游群加密轮换不是这一产品协议 |
| 先准备目标网再切换 | 可按不同状态 id 保存授权上下文，节点身份本身可独立保留 | 双网材料分区、单一活动网、真实目标成员通信验证、切换/退出阶段恢复 |

## 2. 授权接入：现成算法的边界比 `Manage` 名称更具体

### 2.1 上游已经完成的部分

`GroupCrdt::process` 先在操作声明的 dependencies 所对应的历史状态上验证，再加入图，必要时重建并发状态。作者权限不是按到达时间或本机当前视图直接判断。输入必须已经满足部分顺序；缺依赖不能当成授权成立。[处理及前提](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/group/crdt/mod.rs#L450-L679)

默认 resolver 在重新计算时清空旧过滤集，并根据并发关系重新产生结果；它能修正已经本地应用的结果。实际测试 `demote_remove_filter` 覆盖 A 降 B 权、B 并发移除 C 后保留 C；`remove_dependencies_filter` 覆盖无效授权带来的下游失权；`remove_readd_dependencies_filter` 覆盖 B 重新加入后可重新管理，同时其旧的并发批准仍不成立。后一个测试中，Eve 的新批准同时引用旧的无效 Dave 批准和重新加入操作，Eve 仍有效，所以不能把规则简写为“引用任一无效操作，所有后代永久作废”。[resolver](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/group/resolver.rs#L17-L105)、[具体测试](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/group/resolver.rs#L545-L794)

因此应把有效管理图和物化成员视图区分开：因并发而失效的动作仍可能必须保留在图中；不能在首次失效时删除记录或相关历史。`apply_action` 对这种后来不成立的动作保持状态不变，同时保留其图位置，是上游已有语义。[重建中的错误处理](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/group/crdt/mod.rs#L751-L783)

### 2.2 不能从现成 API 推出的产品保证

1. **`Manage` 不是日常管理员。** `state::add` 只检查添加者是 manager，并不禁止添加新的 manager；`modify` 只要求修改者是 manager；`remove` 允许 manager 移除其他 manager，且允许任何有效成员自移除。管理员不经创世提权直接退出在上游也是允许的。因此“日常管理员用 Manage，创世再放 Conditions”并没有完成权限限制。[add/remove/modify](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/group/crdt/state.rs#L183-L327)
2. **`Conditions` 不是验证回调。** 它只是 `Clone + Debug + PartialEq + PartialOrd`；`is_manage()` 看 access level。条件可支持访问范围比较，但不存在对每项动作执行产品策略的内置 hook。[trait](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/traits/mod.rs#L14-L15)、[Access 实现](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/access.rs#L119-L155)
3. **创世身份没有现成产品锚定。** `Create` 直接用提供的初始成员建立状态，动作本身不把 group id 与某个不可变创世验证凭证绑定。`Operation` trait 明确由应用认证原始作者。因此 canonical genesis、唯一网络锚、禁止替代创世，以及禁止伪造另一条 Create 来改变该网，都须由产品验证。[Create 分支](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/group/crdt/mod.rs#L720-L760)、[Operation trait](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/traits/operation.rs#L5-L25)
4. **验证 seam 并非已经公开完整。** `GroupCrdt::validate` 为 `pub(crate)`，其内部会临时重建操作的真实因果前态。公开 `inner.state_at(dependencies)` 只合并已保存的 states，不等同于该临时重建全过程；在含已知并发失权的图上，不能盲用它替代前态验证。`GroupCrdtState.inner` 及图虽公开，但复制整段内部验证算法到应用会扩大维护面。[validate 重建](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/group/crdt/mod.rs#L566-L679)、[state_at](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/group/crdt/mod.rs#L177-L214)
5. **不能用“管理员子组”绕开。** 上游明确拒绝赋予一个 group `Manage`，因为跨组并发撤权环尚未支持；以多个管理子组组合来实现创世/日常分权会遇到现成限制。[ManagerGroupsNotAllowed](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/group/crdt/mod.rs#L579-L593)

### 2.3 候选最小适配，应在第一个管理切片验证

保留 `StrongRemove`。优先检查能否增加一个很窄的**类型化动作验证 seam**：在操作的因果前态已经重建、进入可接受的管理图之前，传入网络创世锚、已认证的操作和该前态；所有本地创作、远端输入、恢复重放都走同样规则。验证 canonical Create；限制日常管理员只能批准普通成员及移除普通成员；任免管理员、移除仍为管理员的节点、管理员自退出必须带可验证创世权限；禁止改变创世锚。不要修改 resolver 的并发胜负规则，也不要把本机“已提权”布尔值当远端授权依据。

值得优先验证的简单表示是：**创世权威作为独立于 endpoint 的不可变授权身份，日常节点仍用自己的身份；高权限操作使用成熟签名机制证明创世权威。** 例如能否用现成签名操作承载独立创世作者，避免再发明临时授权凭证协议。具体记录形式要在接入切片中定下，不能仅因该候选简洁就视为已批准密码协议。若把创世权威放进 auth group，必须区分它与实际在线成员设备，不能要求“创世虚拟设备”参与轮换持久确认或业务连接。

当前设备的 sudo 窗口属于本地凭证使用边界：同设备会话内重复高权限操作，过期/退出后不再产生有效高权限操作；恢复同一凭证允许在新节点重新取得管理权限，且不顺带撤销旧管理员。**源于日志实现的额外验证点**：p2panda 日志按作者与 log id 区分，要求 seq/backlink 连续；若多个设备恢复同一创世签名身份，不能简单复制一个旧日志尾部并继续写，造成分叉或要求失联旧设备提供最新尾部。要明确并验证现成 log-id/作者映射如何支持恢复与独立因果管理记录，不把缺旧日志误作必须审批恢复的理由。[Header 日志字段](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-core/src/operation/header.rs#L39-L68)、[backlink 验证](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-core/src/operation/validation.rs#L82-L122)

**恢复的引导循环必须同时验证。** 新设备可能只有原创世凭证，已丢失当前准入秘密和授权历史；旧管理员全部离线，仍有普通成员可达。若历史和秘密恢复入口一律先要求共享秘密，则创世恢复被自己要取回的材料阻塞。候选接法是复用现有受限控制入口及成熟认证实现，在对端已保存的 canonical genesis 锚下验证独立创世恢复权威、目标网络和当前申请节点身份，然后仅放行恢复必需的历史/材料交付，使恢复节点能发出有效管理恢复记录，再进入普通成员流程。普通成员在这里是验证和交付已获创世授权的材料，不获得任命管理员的权力。先证明根权、后披露历史；不能先匿名下载历史来寻找根，也不能把自报 network id、知道 genesis 公钥或普通 TLS 节点认证当作根权证明。具体成熟证明的会话绑定、重放处理与现有受限入口兼容性属于下面 Q 的技术验证，不在研究文档中临时定义一套签名 challenge 协议。core 的原作者签名和可扩展头提供记录原料，auth 的 Operation trait 明确仍要求调用者认证作者；源码没有交付上述恢复入口。

## 3. 已收到不等于可供给，已存操作不等于已应用授权

### 3.1 可以复用的实际处理链

`p2panda-core` 签名头包括扩展内容，正文通过哈希和长度绑定；自定义扩展可以承载有版本的网络标识、管理动作与依赖。`validate_operation` 验证签名、头一致性，以及**在正文存在时**验证正文大小和哈希。`ingest_operation` 再检查日志连续性，在事务中保存操作并关联 topic；重复 hash 返回“已存在”。SQLite 实际保存 header 与可选 body。[签名格式](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-core/src/operation/header.rs#L20-L83)、[校验](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-core/src/operation/validation.rs#L8-L47)、[ingest](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-stream/src/ingest/operation.rs#L15-L102)、[SQLite 写入](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-store/src/operations/sqlite.rs#L31-L94)

`LogSync` 的接收端解码后发 `OperationReceived`，并不在该位置验签、应用组状态或持久提交。发送端按对端缺失的 `(author, log_id, range)` 读取存储并发送原 header/body，所以 B 可以供应 C 的操作，C 无须在线；这条能力不需要自行重写同步算法。协议双方的 `Done` 代表此次协议发送/接收边界，不是产品记录都已验证落盘的确认。[接收事件](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-sync/src/protocols/log_sync.rs#L308-L351)、[第三方日志供应与 Done](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-sync/src/protocols/log_sync.rs#L358-L455)

`Orderer` 可用依赖字段等待缺失项，`Groups` 可加载、处理、保存 `GroupCrdtState`。但 stream 的 `Groups` 是具体 `SqliteStore`、具体 `GroupsOperation` 和固定 `StrongRemove` 的组合，只有条件 C 是开放泛型；它没有产品权限 hook。高层 `p2panda::Pipeline::new` 现在只串 `Ingest → LogPrune`，没有自动接上 `Orderer → Groups`。因此票中必须明确选择哪一个真实入口接产品验证及组状态应用，不能写“开启 auth feature 即完成”。[Groups 事务](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-stream/src/groups/processor.rs#L18-L141)、[高层 pipeline](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda/src/processor/pipeline.rs#L105-L137)

### 3.2 应直接进入验收的四个边界

- **正文缺失及重复到达。** 对声明非空 payload 的操作，`body=None` 仍可通过 core 验证；先存这种头后，再送同 hash 完整正文，ingest 会先去重返回，SQLite `INSERT OR IGNORE` 也不会补正文。所读 `OperationStore` API 有删除正文，没有补入正文方法。完整控制记录应在进入 canonical store 前拒绝/暂存缺失必需正文，或明确实现验证后的补全接缝；不能只检查 `has_operation`。这是从分支组合得出的风险，尚未运行复现。[ingest 去重](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-stream/src/ingest/operation.rs#L44-L62)、[OperationStore API](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-store/src/operations/traits.rs#L7-L60)
- **Orderer 出队与授权保存之间崩溃。** `Orderer::next` 在返回操作给下游前提交出队状态；随后 `Groups::process` 又单独事务提交组状态。不能把出队当作已应用。现成 `mark_ready` 在重复输入时会把已出队项重新排队，提供恢复原料，但产品仍要有可重放的应用完成记录/提交关系。`GroupCrdt` 对重复操作返回错误，应用要辨别已处理与真正无效，不因重试中断恢复。[Orderer::next](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-stream/src/orderer/processor.rs#L79-L113)、[重排队](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-store/src/orderer/sqlite.rs#L63-L115)、[重复检查](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-auth/src/group/crdt/mod.rs#L570-L577)
- **依赖就绪不等于权限验证成功。** `CausalOrderer` 只检查依赖项是否 ready，且明确不检查依赖环；它不知道某项是否已获产品认可。产品要防止非法记录进入授权图，保留必要的待补依赖信息并驱动已有 sync 去获取；不要把拓扑队列当验证器。[Orderer 语义及限制](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-stream/src/orderer/orderer.rs#L30-L127)
- **自动 ack 与头内管理消息。** 高层 stream 会对没有 body 的事件自动 ack 并不向应用转发，即使选了显式 ack；有 body 时 Automatic 在交给应用前 ack。若管理动作存在签名扩展里而正文为空，不能依赖这个高层应用事件入口来消费它。`Acked::ack` 只是保存本地消费 cursor，不是远端收到、业务已提交或恰好一次的证明。[自动 ack 路径](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda/src/streams/stream.rs#L369-L410)、[cursor 更新](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda/src/streams/acked.rs#L116-L138)

建议建立单一可观察的处理契约：签名/日志有效且所需内容完整 → 保留操作与依赖 → 因果排序及产品授权验证 → 保存授权视图和消费进度 → 才通知上层“本次来源/范围已验证保存”。可以使用分阶段持久重放，不要求把网络交换放入一个数据库事务。引用 `SqliteStore::tx` 与 `Transaction` 时要按一个事务持有者串行完成；现成 store 用 permit 和 semaphore 串行化事务，不能外包一个 begin 后再调用会自行 begin 的 processor 并假设可嵌套。[事务 API](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-store/src/sqlite.rs#L283-L381)

## 4. 上游没有提供的产品持久流程

以下是应用适配建议，依据为已定规格与上述存储接缝，不是声称 p2panda 已实现这些流程。本次读取 auth/core/store/stream/sync 的相关 API、schema、测试，并搜索 precode/invitation/redemption/genesis/rotation/migration；没有找到满足本规格的单节点 precode 核销账本、全保留成员持久确认轮换，或单活动网迁移流程。不能把 SQL schema migration 误认成私网迁移。

**人工批准与交付：** 保存申请身份、原批准结果的操作引用、原交付者、当前进度。审批/核销成功与申请者保存授权及准入秘密是不同事实；成功响应必须以申请者验证并保存两项材料为界。重试读取原结果并检查当前授权仍有效，不再无条件 Add。上游 `state::add` 本来就会拒绝已是成员的身份；另一管理员的新码应消费新码并交付现有有效资格，只有资格无效时才按新加入处理。

**Precode：** 每个码都保存唯一核销者、有效期、可选上限、单码撤销状态及其所依赖的管理员授权来源。以经过认证的申请者身份和同次兑换标识找到原兑换结果；同一个事务/可恢复提交过程关联扣次、授权操作及待交付结果，先持久后对外确认。并发请求争用末次额度必须在 designated node 本地串行裁决；不需要分布式计数 CRDT。失权后再授予管理权不能只因 `is_manager=true` 而让旧码复活。正常重启可继续；恢复旧备份而无法信任扣次完整性时停兑，不能从当前成员人数倒推已消费次数，因为成员可已退出/移除。仍可保留、转交已经签发且有效的成员授权。

**准入秘密轮换：** 使用成熟的安全传输/证明，不另造群加密。明确持久保存轮换标识、旧/待启用秘密的本地安全引用、经授权的保留成员集合、每个成员的持久接收确认、进行中/完成阶段。确认应绑定本次轮换与本节点身份，只有接收端提交新秘密后才发送；发起端也先保存确认再计入完成。轮换中拦住人工批准、新核销及原批准的秘密交付重试，分发替换秘密仍可进行。提交切换前重检保留成员与确认条件；未确认成员必须等待或按原权限明确移除。不要用超时自动剔除，不把 TCP/QUIC 收到包或普通 sync Done 当持久确认。

`p2panda-spaces` 的确有 auth 与 group encryption 组合：成员变化时调用 encryption group 的 add/remove，产出 direct messages；这解决的是空间数据加密和成员密钥变化，不是“独立共享 bootstrap secret，移除不强制轮换，所有保留成员确认保存后才能切换”。直接把 spaces 的成员移除/密钥演进当本规格轮换，会改变已定行为。[spaces 调用关系](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-spaces/src/space.rs#L190-L249)、[按成员变化应用加密组操作](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-spaces/src/space.rs#L396-L462)

**迁移：** 持久保存 source/destination 网络身份、目标入网两项材料、准备进度、真实目标成员通信验证结果、活动网切换及 source 退出结果。目标 group state 可独立存放，group state id 本身是一个存储键而不是常态双网业务开关。[分组状态存储](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-store/src/groups/sqlite.rs#L21-L79) 准备时旧网正常运行；仅消息旁信道可达不能作为目标可用证据；真实目标成员授权连接及受控数据交换通过后再切换。source 为管理员时退出仍须创世权限。发生重启时从已保存阶段继续，正式退出后不静默恢复旧资格；两个网络不用共同提交事务。

**备份恢复验收补充：** 实际恢复一份扣次前的一致旧备份，而不是仅在最新数据库上手动设置不可信标记。计数与 `counter_trusted` 如果在同一数据库里一起回滚，该标记不能证明没有丢失扣次；受支持恢复入口须在无法证明连续性时停兑旧码，仍允许新码和已验证有效结果按既定规则处理。这是实现与验收建议，不是声称本地软件可自动检测任意未告知的全盘一致回滚；若要识别这种回滚，需要另有可信连续性依据。

**迁移历史隔离补充：** `NetworkId` 用于派生 ALPN；高层 `LogId::from_topic` 只对 topic 做散列，不自动加入网络身份。因而同一稳定节点 key 的跨网迁移，需要明确分开的网络记录、作者日志与 topic 命名空间；仅用不同 `Groups state_id` 不足以保证历史隔离。目标同步不能要求取得源网独有日志前缀，也不能传播源网独有历史或把其动作应用到目标授权视图。应在迁移票用同 key、不同网络的真实发布与补齐验收此条件。[NetworkId 与 ALPN](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda-net/src/lib.rs#L280-L325)、[LogId 派生](https://github.com/p2panda/p2panda/blob/083b48215964e92a564f3c83a1c607b00e94aa64/p2panda/src/operation.rs#L600-L615)

## 5. 建议的一个资格验证及七个端到端切片

这是供主拆票流程合并、取舍的候选边界，不是创建好的工单。每片都交付用户可观察的结果、实际接入和必要验证；共享机制在首次需要它的切片中完成，不另拆“建数据库”“写 auth 模块”之类横向占位票。外部阻塞项仅指真正缺失的通信/证明能力，不能因这里列了未知点就要求用户重新讨论产品原则。

### Q. 验证不可变创世权威、日常管理与 StrongRemove 的最窄接法

**交付：** 一个有边界的源码接线/可执行验证结论：确定现成 `GroupCrdt` 加最少验证 seam 能否保留默认强移除，同时满足创世独立、恢复与日常权限分工；产出选定的操作/日志映射、需要的最小上游修改和可供后续实现复用的验收入口。它不交付完整成员产品或新的共识协议。

**必须回答的技术问题：** typed action 校验能否在正确的因果前态执行，且覆盖接收、重放、canonical Create、日常 manager 越权、管理员自退出？独立创世作者在多设备恢复时能否使用现有签名/日志结构，不依赖失联设备提供旧 log 尾部？新节点仅持原创世凭证、无当前共享秘密/历史时，能否通过一个普通在线成员的受限入口验证根权、取得恢复材料并恢复管理，同时未经根权证明者看不到历史？采用哪个已有成熟认证机制完成会话/身份绑定，哪些改动仅属于应用记录与准入路由？

**通过条件：** 用实际 core 签名操作与 auth resolver 验证普通批准、越权 manager 任免、合法创世恢复、并发撤 B 管理权与 B 移除 T 两种到达顺序、B 重新任命后的行为；恢复路径还需实际验证所选证明机制、错误网络根/目标身份及重放，不以 mock 返回“根权有效”通过。明确产品授权状态与 endpoint 身份、非设备创世权威之间的映射。若现成方法不成立，说明具体源码限制及最小替代，保留既定产品语义供评估。

**真阻塞：** 所选版本和最小签名/auth/持久化运行入口；恢复证明部分还需要成熟认证机制及受限控制接入的资格验证，可与其他准入研究并行。此 gate 应阻塞完整创世/成员实现，不能用 `Manage` 或 Conditions 的存在提前关闭。

### A. 创建私网并用原凭证在新设备恢复管理

**交付：** 生成独立节点身份和网络创世依据，保存 canonical genesis 与第一名管理员；当前设备提权会话允许反复管理，过期/主动退出后重新验证；原设备不可用时用同一凭证在新节点恢复管理，不自动撤销旧管理员。

**接法：** 确定并验证创世签名/网络锚与节点 key 的映射，保留 core 格式和默认 StrongRemove；实现最窄的 causal-state 类型化校验，并把 action 白名单用于远端接收及重放。持久保存最小授权历史，禁止替代 Create、改变根权、无创世权限 Add/Promote manager 和管理员自移除。把恢复时同创世身份日志连续性列为实际集成检查，不能假设拿到 key 就必然能继续旧单条 log。

**验收：** 新凭证产生不同网络；同凭证恢复原网；身份换地址不变；普通管理员直接构造越权签名操作也被拒绝；普通批准可成功；恢复后旧管理员仍在；提权不传染到另一设备/会话。重启后锚和授权仍可验证，不能靠内存状态通过。

**真阻塞：** Q 的模型/恢复接线结论、首个可运行节点/存储/签名组合及被选版本的编译接线。无需等 MQTT、移动路径、浏览器或复杂邀请完成。恢复验收必须包含新节点没有当前准入秘密及历史、旧管理员均离线、只有普通成员可达的情况，不允许循环等待旧秘密或旧管理员审批。

### B. 原作者离线后，另一成员重启仍能供应完整控制历史

**交付：** C 发布有效记录，B 验证保存；C 离线，B 重启，A 仅从 B 补齐并形成正确授权/控制视图。

**接法：** 从实际 LogSync 事件接入 core validation、ingest、因果排序和 A 的产品验证，明确 Groups 状态与应用完成进度。保留控制/授权历史，不启用破坏验证链的 pruning。拒绝/暂存缺失必需正文，避免同 hash 去重吞掉后补正文。同步完成等待该来源范围内的处理提交，不复用网络 Done 直接报产品完成。

**验收：** 查 A 可供给的原作者 header/body 与必要依赖，而不只计事件；重复、乱序、缺依赖和再重启不改变最终视图；在 ingest commit 后、orderer 出队后、组状态 commit 前后分别中断，恢复不会漏应用或重复产生外部动作；某来源补齐不宣称全网最新。

**真阻塞：** A 的记录/权限接缝，以及允许成员同步的实际端点连接和协议准入。只需可靠受控数据路径，不依赖新消息载体或未知成员发现。

### C. 日常移除立即约束通信，并在并发管理员撤权补齐后正确修正

**交付：** B 可移除普通成员 T；具有权限的创世动作可撤销 B 管理员身份但保留其普通成员资格。节点本地验明移除即拒绝新连接并终止已有网络/应用通信；随后有效并发撤权使 B 的移除无效时，T 可重新建立连接，旧连接不复活。

**接法：** 直接复用 StrongRemove 的现有图和过滤，不写时间戳 LWW；将变更前后有效权限视图差异发送给连接/协议准入所有者。UI 当前权限检查仅作反馈，记录接受仍依因果前态；离线、主动退出、有效移除后新授权重入分别处理。已失效旧批准重试不能变成重新入网。

**验收：** 两种到达顺序得到相同成员结果；B 的普通移除、创世撤 B 管理身份、B 被重新任命后的新动作符合默认算法；有效重入保留 node id 但需要新授权；管理员不提权不能退出/移除自己。用真实 Connection 和受控业务流观察拒绝及关闭。

**真阻塞：** A、B 的授权传播/重放，以及所有相关协议统一使用有效权限视图的接线。无需等 precode 或秘密轮换；移除不能被后者阻塞。

### D. 人工批准后，授权与准入秘密的中断交付可恢复

**交付：** 新节点通过可信邀请联系指定管理员，批准后分别验证保存成员授权与准入秘密，两者完成才显示入网成功；中断/重启能向原交付者恢复，且当前授权已无效时拒绝旧请求复活。

**接法：** 用实际受限申请协议和已认证 node id 建立申请标识，持久关联批准操作、交付责任和结果进度。上游 add 已存在成员报错，所以重试应读原结果并检查有效状态，不能每次调用 add。申请端保存后才确认；交付节点保存结果后才报告已交付。此片同时定义后续 precode 复用的两项材料交付接口。

**验收：** 在授权生成、发送、申请端保存、秘密发送/保存和确认各点中断并重启；只有两项材料完成后正常同步/受控业务才可用；同身份重试不重复审批；身份替换、错误目标和早期数据不能越过受限入口；另一管理员持有效授权可以后续用新码补交材料。

**真阻塞：** A；可信邀请到目标身份的真实受限控制通信；成熟准入秘密持有证明及正常成员协议门禁的已验证接线。不能用“共享秘密任意拼接 HMAC”替代该技术前提，也不必等路径优化或浏览器才实现 native 交付。

### E. 单一指定节点核销 precode，末次额度与重启均不超发

**交付：** 有限次数码与仅限时间码都绑定一个核销者；相同兑换重试读原结果，不重复扣次；单码撤销、管理员失权、失权后重新授权和核销者离线均有已定结果。

**接法：** 复用 D 的入网交付；把 code、申请者、幂等兑换、消耗次数、批准结果和待交付进度纳入一个可恢复提交过程。争抢末次额度在指定节点本地事务内决定。把码与签发时有效管理员授权来源联系起来，重新获得 Manage 不能复活旧码。可信计数与备份恢复状态独立于普通成员列表。

**验收：** 不同身份同时抢最后一次只成功一个；同身份原兑换跨重启/晚响应仍只扣一次；到期阻止新兑换但不撤销已生效成员；失权后旧码永久不因重新任命复活；指定节点离线无自动接管；旧计数备份不可信时停兑。原交付者永久失联后，新管理员的新码独立扣次：已有有效成员资格则复用并交付，资格失效则走新批准，不误 Add 两次。

**真阻塞：** A 的管理员授权来源、D 的交付边界及可持久串行核销的本地存储。无需设计多节点计数共识；无法证明备份计数完整就以停兑满足当前范围。

### F. 保留成员持久确认新秘密后才完成创世轮换

**交付：** 创世提权启动单独轮换或移除并轮换；正常移除已经生效。保留成员离线时显示待确认，不提前切换；确认者重启后仍能用新秘密。未确认成员只能等待或明确移除。

**接法：** 复用 D 的安全交付与 A 的创世校验，持久记录轮换和确认进度；成员先提交秘密再确认，协调方先保存确认再计数，切换前重核当前保留集合及权限。轮换态统一阻挡人工申请、precode 新核销和旧批准秘密交付重试。沿用成熟秘密证明，控制记录不得把秘密明文放入共同复制。

**验收：** 日常管理员无提权拒绝；少一位保留成员确认就不能切换；伪造、旧轮换或旧身份确认不计入；接收后未提交崩溃不算成功，提交后确认丢失可幂等补发；协调方各边界重启后进度明确；显式移除未确认成员后可满足条件；轮换期间入网暂停且不会因重启漏掉门禁。

**真阻塞：** A、D、C 的成员移除；若应用已提供 precode，则 E 的入口也必须使用同一轮换暂停状态。不是依赖 p2panda-spaces 群加密，也不需要全网同时在线事务。

### G. 旧网继续工作时准备目标网，验证真实成员通信后切换并退出

**交付：** 单设备确认迁移后获取并保存目标授权和准入秘密；准备期间旧网可用，目标失败不切走；目标合法成员的实际授权数据通信验证通过后，切换活动网并按源网权限退出。离线设备以后独立补迁。

**接法：** 复用 A/C/D/E 的目标入网与源网退出，按网络身份分开历史、秘密和状态；明确单活动网的调度所有者。持久保存准备、验证、切换、退出的结果及重试依据。目标验证用同一正式准入/数据路径，不能只探测 MQTT 可达或收到邀请回包。源网退出结果可由其他成员保存转交。

**验收：** 目标审批前后断线及所有提交边界重启；目标仅旁信道可达但没有业务数据路径时旧网仍正常；切换后无常态双网业务；源网管理员遵守创世退出；源网正式退出后不能因重启静默恢复旧成员资格；同一 node id 在目标网获得独立授权，旧业务连接不冒充跨网续接。

**真阻塞：** 可用的目标入网交付和受控数据通信，源网自退出/管理员退出及节点单活动网调度。无需等待全网成员一起迁移，也不把秘密轮换作为必然前提。

## 6. 验证与决策边界

源码测试是输入依据，不是本产品组合已通过的证据。优先以最窄真实节点/协议入口执行上述验收；控制时钟、消息重排与崩溃注入可使用可控设施，签名、实际存储重启、目标身份与连接必须用真实实现。对 A 的因果权限 seam、B 的提交/重放、D 的受限准入及 F 的持有证明接线，首次不满足时记录具体不兼容点及最小改动；不以未证实的 hook 存在、API 注释或模拟成功把依赖标记完成。

这轮可以直接拆实施/验证票，不需再次询问“创世是否独立”“是否允许并发修正”“码是否单核销”“是否先退出旧网”等已决问题。真正还需工程选定的是记录与日志映射、最少 upstream 接缝、提交/恢复关系以及成熟证明机制；这些选择必须产生具体实现和外部可观察验证结果，遇到与已定产品契约冲突才提出最小修订。
