# Durable manual admission through native nodes

2026-10-01 Asia/Taipei. Implements [MIOPUNCH-30](http://192.168.4.22:2080/work/projects/aa58cd82-2afc-404b-a097-58ef553c7ca4/issues/c6c037cc-3e23-46d1-9fd0-db50c767f5a4) against its parent specification and ADRs 0004, 0005, 0007 and 0008. The accepted product behavior is unchanged; this records the concrete storage and delivery mapping.

`NativeNetwork::manual_invitation` returns only the canonical network anchor and designated contact identity. Its 96-byte encoding contains no admission secret or private key. `NativeNetwork::join` creates an independent durable node key, saves that trusted invitation and a random request ID, and starts with no membership or admission secret. Both created networks and incomplete applicants reopen through the same public native node entry. Only creators retain their separately pinned genesis recovery credential.

The existing restricted admission ALPN and shared endpoint gate authenticate the actual iroh TLS peer. The request's claimed applicant must equal that peer; both the intended network and contact must match. The pair of authenticated identity and request ID identifies a durable request. Receipt does not approve membership. An administrator explicitly calls `approve_manual_admission`; this API only signs ordinary `Read` membership, and cannot grant administrator status.

The SQLite `admission_deliveries` relation saves the signed Add and approved result in one transaction before applying or delivering it. Cancellation or restart can apply that same committed record, rather than produce another Add. Existing valid members can reuse a currently valid signed grant. `approved_admission` exposes the approved result and delivery phase, but rejects invalidated authorization. The shared management query checks the actual signed grant, p2panda's filtered operations and causal removals: a valid removal followed by a fresh grant cannot revive the old request's membership episode. A filtered removal remains an authorization correction.

Material delivery has two public receiver stages. `request_manual_admission` replays the complete bounded signed history against the pinned Create, verifies the contact's current administration and the applicant's grant, then ingests and applies it durably. It returns an `AdmissionDelivery` handle while local state is `PendingMaterials`. `complete_manual_admission` requests the current secret on that same authenticated connection and saves it before enabling the member gate or acknowledging completion. The sender rechecks current authorization and the durably pinned current credential at release.

The private material file contains the credential generation and secret. A complete fsynced temporary file is published atomically without replacing an existing value, and the parent directory is synced even on retry. The SQLite credential fingerprint is committed next. A crash between file publication and that commit remains pending on reopen; secret availability in memory is installed only after both durable steps. The signed authorization remains in the existing management store. Secret bytes never enter shared control-history replication or diagnostics.

Public stages are `AwaitingApproval`, `Approved`, `PendingMaterials` and `Complete`. The approved result describes the delivery node's acknowledgement progress; the applicant's own verified durable state is the admission-success authority. `PathUnavailable` is a separate error which retains durable progress. A failed acknowledgement after both local saves cannot undo local completion. Normal business uses a new member-gated connection, separately requiring current membership, admission proof and an allowed data path; the restricted request connection does not become a business carrier.

The first actual two-node check completed manual approval, both durable saves and reopening with the same applicant identity. Both nodes verified ordinary membership, then sent actual bounded business bytes on a new admitted loopback QUIC connection. The prioritized failure used a child applicant process which exited with code 77 immediately after the authorization-save API returned, before requesting the secret. Reopening reported `PendingMaterials`, and a normal business connection was rejected. The same identity and request resumed the original approved hash and completed without another Add.

Subsequent individual checks rejected a wrong network, wrong actual contact and forged claimed applicant; refused corrupted signed authorization even from the genuine authenticated contact; rejected an old result after removal and fresh re-add; and recovered after a real material-file failure across restart. A second invitation holder subscribed to the actual MQTT carrier during manual delivery and received only ciphertext, with neither invitation-private application content nor the long-lived secret appearing in captured packets. Even disclosure of the original request ID did not let that holder retrieve the original approved result: its different TLS identity received a separate pending request.

The first MQTT run exposed a test cleanup wait, not a failed admission: the fixture retained Endpoint/Connection handles while awaiting carrier destruction. The bounded reproduction demonstrated that approval, refusal of the other holder and both material saves had already completed. Dropping those owned handles before the bounded carrier wait fixed the fixture; no production transport lifecycle changed. Original RED and diagnostic logs remain in the evidence.

The initial independent Spec review found a separate recovery bug: when approval A's Add/result transaction committed before its view was applied, a different already authenticated request B from the same identity could sign a second Add. A real storage-checkpoint child exited with code 78 after the shared transaction committed and reproduced three applied records instead of two, without reusing the original grant. The fix recovers ready committed records on native reopen and before approval, approved-result queries and material-exchange authority/dedup decisions. Both restart and live-node interruption variants now reuse the original grant and complete its delivery. The shared `ManagementStore::save_admission_approval` persistence boundary is public for adapters and genuine checkpoint injection; it requires a previously authenticated recorded request, and its commit alone does not mean verified approval or admission success.

Generation 1's full-suite results, six-source snapshot and both initial reviews remain preserved. The post-fix generation 2 final receipt identifies the source and full checks actually used for completion; it does not relabel the earlier 253-pass suite as validation of this recovery fix.

Reproduction, exact checks and raw evidence are in [the evidence directory](../evidence/mio30-manual-admission/README.md). The environment was native Linux with real SQLite, Ed25519 verification, iroh TLS/QUIC, loopback UDP and an isolated Mosquitto broker. This does not claim physical power-cut durability testing, Windows/Android manual admission, browser admission, large-network throughput, global convergence, or a new NAT success rate. Precode redemption, delivery through a new code, rotation, migration, product UI, ACL and TUN remain separate scopes.
