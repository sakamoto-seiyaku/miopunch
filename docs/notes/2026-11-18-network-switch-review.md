# 切网实测复盘：问题、证据与修复方向

2026-11-18，实测版本 `9d3db16c`。讨论稿已按审核意见修订，实施与实验范围见 [Plane 父规格 MIOPUNCH-135](http://192.168.4.22:2080/work/projects/aa58cd82-2afc-404b-a097-58ef553c7ca4/issues/d99a336a-c782-49d5-90c9-30b257ba9a32)。

原始证据：[network-demo-switch-2026-11-18](../evidence/network-demo-switch-2026-11-18/)（下文简称 `E/`）。墙钟为 UTC+08:00；u22sz 进程起点约 15:44:46.31，r_proxy 约 15:44:13.06。

## 0. 环境与前提

| 节点 | 平台 | 本地 | 公网 | NAT |
| --- | --- | --- | --- | --- |
| u22sz | Windows 原生，办公网 | `172.31.0.36:56491`，单默认路由 | `182.48.107.243` | 见 §2 L2 |
| r_proxy | Debian，容器 host 网络，家宽 | `192.168.4.14:30005` | `111.197.236.230:10457` | EIM 映射 + 端口受限过滤（§2 实测） |

时间线：15:44:46 启动 → 15:55:55 u22sz 离开办公网 → 15:56:47 拿到热点地址 → 15:58:44 回到办公网。

前提（不作为待修问题）：

- 公共 n0 relay 质量差是允许的约束。relay 路径 RTT：办公网约 1.1s（`E/paired-status.jsonl` 中 1115/1087ms），热点 2.3–3.5s（`E/u22sz/stdout.log:1750` 3456ms）。
- 从国内到 `aps1-1.relay.n0.iroh.link` 的 QUIC 存在 SNI 过滤（已确认）。QAD 也是 QUIC（ALPN `/iroh-qad/0`）；aps1 的 HTTPS relay 不受影响。

本文只保留两条主线：

- **L1** 切网后，怎样尽快通过 relay 恢复业务。
- **L2** 办公网打洞时，怎样让已经到达一端的 UDP 探测形成双向通路。

两条都有现场证据，可以分别验证。

## 1. L1：切网后经 relay 恢复业务

### 事实

热点在 15:56:47 拿到地址。两端跨越这一时刻的拨号记录如下。

```
r_proxy (E/r_proxy/switch-events.txt:17-32)
15:56:57 connect-start → 15:57:27 connect-failed "connection transport failed: timed out"
15:57:29 connect-start → 15:57:59 connect-failed（同上）
15:58:03 connect-start → 15:58:29 connection-open（route-dial 25.9s）
u22sz (stderr connection-timeline)
15:56:25 经 aps1 → 15:56:55 failed(transport)；随后过期 IP 各 5s，全部失败
15:57:26 经 aps1 → 15:57:56 failed(transport)；过期 IP 同上
15:58:28 经 aps1 → 15:58:54 succeeded（此时已回到办公网）
```

两端都在采样观察到选中直连之后记录了各自出站请求的首份有效回复。选路按秒采样，这两个事件的顺序无法确定单笔回复的实际承载路径。

```
r_proxy: 15:58:36.221 selected ip:[2408:8409:...a67d]:56489 → 15:58:38.117 business-restored elapsedMs=164762
u22sz:   15:58:54.571 selected ip:111.197.236.230:10457      → 15:58:54.901 business-restored elapsedMs=182481
```

从热点出现到 r_proxy 收到首份有效回复约 110 秒。164762 ms 和 182481 ms 分别从各端首次失败请求的开始时刻计算，包含无网时间。热点下仅经 relay 的业务恢复仍待实测。

### 问题与原因

**L1-1 demo 重拨始终用旧配置；已知正确的地址进不了拨号计划【确认】**

`src/bin/miopunch-network-demo.rs:303-307` 每次都用 `peer.address`。target：

```
r_proxy → u22sz : [Relay aps1]
u22sz → r_proxy : Relay aps1, Ip 111.197.236.230:10841, 172.17.0.1:49335, ..., [2408:8207:...]:55861
```

r_proxy 实际是 `30005` / `10457`，IPv6 端口是 `46646`。`src/connection_coordinator.rs:1207-1219` 只会把 target 中、同时又在 remote_info 里活跃的 IP 提前；不在 target 里的正确地址永远不会被拨。

两个方向要分开看：

- u22sz → r_proxy：r_proxy 是稳定端，u22sz 掉线前可以学到它正确的地址，恢复网络后主动拨回。按 §2 的端口过滤实验，家宽尚未向热点的公网 IP 和端口发包时，预计冷拨 IPv4 会被过滤。IPv6 `[2408:8207:...]:46646` 的直接可达性尚未测过。
- r_proxy → u22sz：会话已经断了，r_proxy 无从得知 u22sz 后来换了 home relay。这个方向需要 u22sz 主动拨回，或者一个独立的联系入口。

**L1-2 u22sz 的 home relay 换成了 euc1【现象确认，影响为推断】**

断网期间观察到 aps1→euc1→use1→usw1 反复轮转（`E/u22sz/switch-events.txt:5,7,9,...`），15:56:46 停在 euc1，16:04 的快照仍是 euc1。relay actor 在当前 home 连接报错后会依次尝试下一个获准 relay，这与断网时的顺序吻合。恢复后停在 euc1 还可能受延迟报告或当前连接状态影响。按尝试时间对齐两端 home 状态才能判断。见 `vendor/iroh/src/socket/transports/relay/actor.rs:1161,1281`。

经 aps1 拨号失败，日志**无法区分**以下三种原因：本端没连上 relay；对端已经换到别的 relay 注册；relay 已连通但后续握手没完成。

**L1-3 原连接断开后才开始重拨【确认】**

demo 在传输层报告连接关闭（`transport_timeout`，15:56:24/25）后重拨。一次 heartbeat 超过 3 秒会结束本次业务请求，原连接继续接受后续请求。新连接上，r_proxy 在 15:58:29.075 取得出站连接，首笔请求在 15:58:32.077 超时；u22sz 在 15:58:34.418 才进入这条连接的业务接收函数。该次超时包含对端应用就绪前的等待，不能仅归因于 relay RTT。见 `E/r_proxy/switch-events.txt:32-33`、`E/u22sz/stdout.log:1750`。

**L1-4 热点地址出现后，r_proxy 有两次连续的 aps1 拨号各耗时约 30s 并失败【确认】**。下一次在 25.9s 后交付连接。

### 方案

| 项 | 内容 | 性质 |
| --- | --- | --- |
| L1-A 地址刷新 | SDK 前台重拨使用按成员身份保存的近期联系线索，结合活跃路径和经已认证会话学到的对端地址；过期 IP 降级，仍按本地资源许可筛选。demo 的 snapshot 可用作对照，SDK 应用复用同一联系人入口。展示实际拨号地址 | 直接修 |
| L1-B 固定 home relay | 在受控环境比较固定同一获准 relay 与自动选区，两组使用相同的拨号计划、资源许可和业务期限。原现场的固定候选是 aps1 | 自动对照，与 L1-C 同批 |
| L1-C 提前拨其他获准候选 | 在相同的 home 策略和候选下，对照现有与提前起拨时机，观察慢 relay 期间其他获准 relay、IP/IPv6 何时获得机会 | 自动对照，与 L1-B 同批 |
| L1-D 反向拨回 | 网络变化的一方恢复后主动拨回；评估是否需要独立的联系入口 | 设计讨论 |

**验收口径**：实验环境通过可控断路、恢复和高延迟 relay 运行 L1-B、L1-C。共用正常路径和 relay-only 基线，每次只改变选区或候选起拨时机。relay-only 下保留原有 3s 请求和一笔预先约定较长有限期限的请求，分别报告是否收到有效回复及耗时。现场使用本轮选定的一套配置，按方向从热点地址出现计到首份身份和序号匹配的回复，同时记录双方应用就绪时刻。切回办公网才恢复时，单列热点阶段和切回后的结果。

L1-A 确保已知新地址能进入真实拨号计划。地址正确仍可能不可达：u22sz 拨稳定端的 aps1 也曾超时，热点到稳定端的 IPv6 直拨尚待验证。受控对照衡量两种策略在给定故障下的表现；aps1 和现场网络的实际表现由最后一轮记录。

## 2. L2：办公网打洞——到达一端的探测形成双向通路

### 事实

按同一轮对齐（round ID 两端一致）：

| r_proxy 角色 | 轮数 | u22sz | r_proxy |
| --- | --- | --- | --- |
| Sender（每轮约 120–125 个探测） | 6 | 6 轮都收到请求，各发出 3 份响应，拿到 winner | 全部 `outcome=failed` |
| Receiver（每轮 25–26 个探测） | 7 | 未拿到 winner | 未拿到 winner |

例：`E/u22sz/stdout.log:67` `LEGACY_WINNER remote=111.197.236.230:10457`；同一轮在 `E/r_proxy/stdout.log:176-177`，`outcome=failed probes=125`。重启（u22sz 新端口 56915）后，r_proxy 的 7 轮也全部 `failed`。

注意 `responses` 统计的是**本端发出**的响应（`src/nat_scheduler.rs:310-311`）。u22sz 发出了 3 份，不能说明 r_proxy 收到了。r_proxy 作为 Sender 时 `outcome=failed`，说明它没收到有效响应。

**Receiver 在收到第一包之前就主动发过包**：

- u22sz 同一轮里，在收到请求之前先发了 ttl=7 的降级探测（`E/u22sz/stdout.log:57-59`），收到后才沿原 socket 回包（`:60-63`，其中 `:62` 仍是一个 ttl=7 探测；回包逻辑见 `src/nat_scheduler.rs:419-447`）。
- 每轮之前，iroh 原生探测也从同一个 socket 向 r_proxy 的地址发过 `PATH_CHALLENGE`（`E/u22sz/stdout.log:17-20`，发往 `111.197.236.230:10457`）。

r_proxy NAT 过滤类型实测（双方都用新端口：r_proxy 47100→`10590`，u22sz 47011→`4879`、47012→`4887`；r_proxy 在 t=10s 才开始发往 `182.48.107.243:4879`）：

```
r_proxy: t=10.3 recv 'U1' from 182.48.107.243:4879   summary {4879 'U1': 47}   (来自 4887 的 'U2' 0 个)
u22sz:   47011 <- 111.197.236.230:10590 R x43
```

结论：r_proxy 是端口受限型（开洞前什么都收不到，开洞后只接受精确的 IP:端口）。用两个新端口、u22sz 先 STUN 再发包，双向一次就通。

u22sz 映射观察（同一个 socket `0.0.0.0:56491`，QAD 和 STUN 共用）：

```
E/u22sz/stdout.log:7    NAT_DIRECT_LOCAL advertised=[..., 182.48.107.243:2244, ...]   (QAD)
E/u22sz/stdout.log:49   LEGACY_SAMPLE destination=13.115.244.15:3478 mapped=182.48.107.243:4834
E/u22sz/stdout.log:50   LEGACY_SAMPLE destination=162.159.207.0:3478 mapped=182.48.107.243:4834
E/u22sz/stdout.log:51   LEGACY_FEATURE nat_type: Easy, behavior: NoChange
```

- 旧进程（本地端口 56427）：QAD 为 2243/2267/2213/2288（u22sz 上的 `stdout.log.before-9d3db16c`）。
- 重启（56915）后：QAD 为 2245/2215，STUN 为 4888。
- 新端口只发 STUN：国内外 6 个目的地、目的端口 53 和 3478，全部映射到 `4879`。

u22sz 发往 r_proxy 的回包实际从哪个公网端口出去，**现有证据无法确定**。不能据此断定 22xx 和 48xx 两组端口都是错的。

切回办公网后：15:58:45 本机地址加入 `182.48.107.243:4834`，15:58:47 r_proxy 选中 `ip:182.48.107.243:4834`，双向打通。原因未知。

### 假设与实验

| 项 | 假设 | 实验 | 判据 |
| --- | --- | --- | --- |
| L2-A 接收方等第一包 | u22sz 在收到 r_proxy 的第一包之前就主动发包，在出口 NAT 上建立了一个映射不对的会话，回包走了这个会话 | 保持角色、候选和窗口不变；u22sz 在收到第一包之前**完全不向 r_proxy 发 UDP**（包括 ttl 降级探测和 iroh 原生探测） | 对照家宽路由器 WAN 侧看到的 u22sz 源端口，以及最终是否双向通信 |
| L2-B 单端 winner 提前验证 | 双方都等 winner、再经 relay 完成 WinnerReady（`src/nat_punch.rs:995`，`E/u22sz/stdout.log:70` 超时），错过了本来可用的路径 | 一端收到有效请求后，立即在原 QUIC 连接上启动路径验证；验证通过后再把业务切过去 | 分两项验收："回包能否到达对端"和"到达后能否及时交接"。如果回包在回程被过滤，延长交接时间也没用 |

L2-A 的先发/等待对照先在受控 NAT 环境自动运行。两组均保留 `9d3db16c` 的 QAD 失败后回退 STUN 的观测行为，从可比的新映射状态开始。QAD 成功时现有流程直接采用 QAD 候选；若一组改用了 QAD，发送端瞄准的公网端口也可能不同。按 round ID 对齐实际候选、发包目的端口、接收方首收与回包、回程源端口及主机是否接受有效响应。等待组始终收不到第一包也算实验结果。最后的现场轮只观察所选策略下 u22sz 和 r_proxy 的真实表现；家宽 WAN 证据可同步取得时才归因到公网端口。

## 3. 可直接修复：QAD 单点失败

**事实**：两端 stderr 各有 13 次 `QAD_SEQUENCE_UNAVAILABLE error_kind=TimedOut`，`observation(qad)` 耗时 3000–3176ms，然后退回 STUN。

**原因**：`vendor/iroh/src/net_report.rs:855` 起串行探测（`:833` 的注释说明串行是为了保持端口分配顺序），`:872` 超时后用 `?` 直接让整组失败。RelayMap 是 `BTreeMap<RelayUrl, _>`（`vendor/iroh-relay/src/relay_map.rs:32`），aps1 永远排第一。STUN 序列遇到失败会跳过（`vendor/iroh/src/socket/stun.rs:234`）；两者处理不一致。

r_proxy 容器内复现（`examples/qad_sequence_probe.rs`）：

```
set=["aps1-1","euc1-1","use1-1","usw1-1"] ERR 3001ms mapping observation timed out
set=["aps1-1","euc1-1"]                   ERR 3001ms
set=["euc1-1","use1-1"]                   ok 1437ms [91.99.237.97:7842->111.197.236.230:10376, 87.99.151.110:7842->...:10376]
set=["euc1-1","usw1-1"]                   ok 1041ms
set=["use1-1","usw1-1"]                   ok 2744ms
```

逐个 relay 测握手（`examples/qad_handshake_probe.rs`，独立的 noq endpoint，3 轮结果一致）：

```
aps1 5.223.65.62:7842   handshake-timeout 10s
euc1 91.99.237.97:7842  handshake=310ms observed=111.197.236.230:10534
use1 87.99.151.110:7842 handshake=498–666ms
usw1 5.78.69.43:7842    handshake=729–2338ms
```

**修复**：在本轮绝对期限和观察预算内有序串行走完可用观察点。单点超时可跳过，同一网络代际下至少两个不同目的地的有效样本可用于基础分类；后续观察点仍有预算就继续，保留四个有序独立样本用于步长判断的能力。样本不足按现有许可回退到 STUN，取消、权限撤销或网络代际失效时终止对应旧工作。连续失败观察点的降级限当前网络代际，保留后续恢复机会。

**延伸（不急）**：
- 默认 STUN 只有 2 个（`src/resources.rs:127,132`，都在国外、都是 3478），没有冗余。
- QAD 和 STUN 目前二选一（`src/nat_connection.rs:380/420`），从不交叉比较；u22sz 那种映射分裂只有在交叉比较时才看得出来。
- 两者合并采样时也要**有序采集**，不能用并发样本推算端口步长。

## 4. 待评估（现有机制为何不够）

- **探测量**：增强打洞已有 32s 冷却和实际暂缓（`E/r_proxy/stderr.log:52`）。13 轮按 §2 两种角色分别统计包量，结合每小时开销和实际改善机会评估。
- **选路抖动**：选路已有 5ms 的 RTT 滞后。u22sz 两次短暂回落在 15:59:02→03 和 15:59:15→16；r_proxy 摘录中最后一次 heartbeat 失败在 15:58:47，且是另一条出站连接。要判断回落是否影响业务，应对齐同一条连接的选择理由、ACK 与请求结果。
- **`replica` 拨号空转**：15:58:58 起两端反复 started→cancelled。demo 每次 heartbeat 获取业务租约，维护器会在业务开始时取消在途后台联系；可用同一进程内的时间线检验这是否解释了重复取消。
- **双方互拨的影响**：两端都在拨（各自累计 `connections: 2`）。是否要去重，需要先说明两条连接并存造成了什么具体问题，以及已有的业务流会如何保留。

## 5. 可观测性缺口

- demo 已采样本端 home relay、连接状态和最近错误，但快照缺少逐次变化历史。两端各记自己的状态，再按同次尝试对齐握手；注册状态无法从现有信号判定时保留未知。
- stdout 里的 `NAT_*`、`LEGACY_*`、`[DEBUG-udp-handoff]` 行没有时间戳。逐包行数随角色和轮次变化；先后手实验保留首个收发包的时序，其他重复发送可按轮汇总。
- QAD 失败只记 `TimedOut`，不区分观察点。
- `retain-winner-returned` 打印的 remote 是还没赋值的旧字段（`src/nat_punch.rs:1444`，`E/u22sz/stdout.log:66` 显示 `172.17.0.1:30005`）。

## 6. 改进与修复方向

### 原则（不变）

1. 已可用的获准直连优先；需要打洞时，获准 relay 可用即可开始业务，直连改善在后台进行。沿用 [ADR 0009](../adr/0009-unified-session-and-capability-based-paths.md)。
2. 为恶劣环境设计：预算按实测 RTT 计算；多来源步骤（观察点、relay、候选）都要容忍部分失败。
3. 后台动作有界，不能伤害业务。
4. 证据足够的才直接修；能解释现象但没坐实的，先做对照实验；每个改动都附带能判断结果的可观测性。

### 各改进点的处置

| 改进点 | 处置 | 依据 |
| --- | --- | --- |
| L1-A 地址刷新（SDK 联系人/拨号入口，两个方向分开处理） | **直接修** | 代码缺口已确认（L1-1）。主要解决 u22sz→r_proxy；r_proxy→u22sz 依赖 L1-D |
| §3 QAD 单点失败（有序串行，失败即跳过） | **直接修** | 代码和对照实验都已确认 |
| L1-B 固定 home relay / L1-C 提前拨其他获准候选 | **受控自动对照**（同批） | 日志无法区分 relay 拨号失败的三种原因 |
| L2-A 接收方等第一包 | **受控 NAT 对照**，最后一轮现场核对可取得的 WAN 证据 | 6 轮里 u22sz 都收到了请求并回包，r_proxy 均未取得有效响应。包停在哪一段、先发是否改变映射仍待测 |
| L2-B 单端 winner 提前验证路径（含交接预算随 RTT 调整） | **对照实验**（第二批） | 只有回包能到达对端时才有意义，要等 L2-A 的结果 |
| L1-D 反向拨回 / 独立联系入口 | **设计讨论** | 已断开的会话无法传递新的注册位置 |
| 探测量、选路抖动、`replica` 空转 | **评估现有机制** | 已有 32s 冷却和 5ms 滞后，要先弄清它们为什么不够 |
| STUN 扩到 3–4 个、QAD/STUN 交叉校验 | **延后** | 只能发现误判，不能打通；新端口只发 STUN 时映射一致，扩 STUN 救不了 u22sz |
| heartbeat 随 RTT 调整、旧连接存活时另建连接 | **延后决策** | 3s 是真实请求期限；先用 L1 的双期限测试量出慢 relay 的影响。原连接上的流与新连接上的请求分开验收 |
| 双方互拨去重 | **暂不做** | `connections` 是累计拨号次数；并存有害之前不处理 |
| 向对端通告 22xx 和 48xx 两组候选 | **不做** | "两组端口都错"证据不足，取决于 WAN 侧抓包 |

### 可观测性（服务于第一批实验）

- relay 侧：记录双方各自能观察到的 home 状态、错误、握手阶段和应用就绪时间。两端尝试对齐后归因，并标注仍缺失的证据。
- 拨号：每次实际使用的地址和路径（demo 也要展示）。
- 打洞：受控 NAT 按轮关联两端与回程观测；家宽 WAN 可采集时随最终现场轮留证。各观察点分别记录结果，首收、回包及验证保留时间戳。

### 执行顺序

1. 以上次现场日志为本轮起点，集中处理影响恢复的主要问题。地址刷新与 QAD 容错走 SDK 真实入口；选区与候选起拨共用一组受控 relay 实验；UDP 先后手和验证交接走受控 NAT 实验。有可用回程时再比较提前验证与现有交接。
2. 将两条链路合到同一版做自动回归，汇总仍影响业务的故障，交付一套可直接运行的双端版本和配置。提前准备自动采集，依次记录办公网初态、热点地址出现、业务恢复或超时、回到办公网后的情况。
3. **本轮唯一的办公室手动验收由用户放在最后执行**：在方便时用这一版跑一次“办公网 → 热点 → 办公网”，采集随运行完成。开发子票均在受控环境验收。现场过程中无需改参数、换版本或为不同方案重复切网。此前日志用作历史参照；只有单一现场观测的现象，保留其因果解释为待验证。
4. 根据这一轮结果集中决定下一批修改。主流程仍不稳定时先解决主要故障；主流程稳定后，再逐项处理探测量、短暂选路切换、后台同步拨号等细节。
