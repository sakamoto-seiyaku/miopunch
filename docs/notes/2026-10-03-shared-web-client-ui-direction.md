# 共享 Web 与客户端 UI 的讨论记录

日期：2026-10-03，补充讨论：2026-10-11、2026-10-20。状态：首版功能范围已收敛为[五个独立业务模块](#首版功能范围五个独立业务模块)，基本操作流程已有确认方向；Vue／Tauri 技术栈已接受，见 [ADR 0018](../adr/0018-shared-vue-ui-with-tauri-shells.md)，UI 实现尚未启动。本记录不自动安排原型、性能实验或框架迁移。下文保留讨论沿革，以后续明确确认的内容为准。

本轮讨论关注普通浏览器与安装版客户端如何复用界面代码，以及在 Rust 节点承担业务功能的前提下如何控制开发、维护和运行成本。用户已确认采用 Vue 3、TypeScript、Vite，安装版使用 Tauri 2，以满足复用和既定需求为准；具体接入接口、平台适配和性能仍需实现验证。

已确认内容现已汇总发布为 [MIOPUNCH-107：首版客户端 PRD](http://192.168.4.22:2080/work/projects/aa58cd82-2afc-404b-a097-58ef553c7ca4/issues/6159ec62-a03e-4eb7-9b95-4ddc19ce7a02)。后续产品工作以 Plane 中的规格为入口，本文保留讨论沿革。

## 已确认的取向

- UI 可以延后，当前先保存讨论结果。
- 代码复用和长期维护成本优先，不要求所有界面代码都用 Rust。
- 可以使用 WebView，但不接受为了界面造成大量无必要的内存开销；有一定性能要求，具体预算尚未给定。
- 业务功能以 Rust 节点为主体。前端负责展示、输入和交互，网络、身份、授权、存储与同步由节点处理。
- 希望最终使用一个 UI 框架，持续维护；只有遇到严重实际问题才考虑更换，不为理论上的性能差异反复选型。
- UI 的延期不改变已有浏览器节点定位，也不启动仍为低优先级的 [WebRTC 候选](2026-10-03-browser-webrtc-assessment.md)。

## 当前框架建议及依据

**已采纳此前建议：Vue 3、TypeScript、Vite，安装版配合 Tauri 2。** 用户在核查后确认采用该方向；下述依据支持选型，不代表成本、性能或完整产品能力已经实测合格。

Tauri 官方提供 `vue-ts` 模板，并推荐使用 Vite 构建普通 Web 前端，支持 Vue、Svelte、React 等多种框架；官方没有指定唯一最佳搭配。[官方模板](https://github.com/tauri-apps/create-tauri-app)、[前端集成指南](https://v2.tauri.app/start/frontend/)

Hoppscotch 提供 Vue 前端同时用于 Web 和 Tauri 桌面版的实际参考：共同代码位于共享包，入口根据 Web 或 desktop 选择平台配置后创建应用。这个实例支持代码组织方式可行，不证明 miopunch 的移动端交付或性能已经合格。[共享包依赖](https://github.com/hoppscotch/hoppscotch/blob/main/packages/hoppscotch-common/package.json)、[共享应用入口](https://github.com/hoppscotch/hoppscotch/blob/main/packages/hoppscotch-selfhost-web/src/main.ts)

此前 Svelte、Leptos 和 Dioxus 也进入了比较。GitButler 的 Svelte、TypeScript、Tauri 组合是一个实际项目参考；Leptos 与 Dioxus 可以用 Rust 编写界面。用户后来明确不追求全部 Rust，并更重视长期维护成本，因此本轮最终推荐收敛到 Vue，不安排多框架并行实现。[GitButler 开发说明](https://github.com/gitbutlerapp/gitbutler/blob/master/DEVELOPMENT.md)、[Leptos 客户端构建](https://book.leptos.dev/getting_started/index.html)、[Dioxus 平台说明](https://dioxuslabs.com/learn/0.7/guides/platforms/)

## 共享界面与两种节点接入

Tauri 提供安装版客户端的窗口、WebView、系统集成、打包和前后端通信。具体页面由 Vue 等前端代码提供；安装版前端通过 Tauri command 调用本地 Rust，普通浏览器版本则调用浏览器中的 Rust/WASM 节点。[Tauri 进程模型](https://v2.tauri.app/concept/process-model/)、[调用 Rust](https://v2.tauri.app/develop/calling-rust/)

建议采用一个前端项目、两个运行入口，复用页面和操作流程，将差异集中在节点操作 Module 的 Interface 后。Interface 包括统一的结果、错误、操作完成含义和运行能力；客户端与浏览器分别提供 Adapter。下面是建议结构，尚未实现：

```text
共享 UI 页面与操作流程
    -> 节点操作 Module 的统一 Interface
         -> 客户端 Adapter -> Tauri 通信 -> NativeNetwork
         -> 浏览器 Adapter -> WASM 调用 -> BrowserNetwork
```

当前源码已有 [NativeNetwork](../../src/native_network.rs) 和通过 `wasm_bindgen` 暴露的 [BrowserNetwork](../../browser-probe/src/network.rs)，浏览器 SDK 也[导出了节点入口](../../browser-probe/src/lib.rs)。这些是当前接入依据；统一的 UI Interface、Tauri 外壳和正式页面尚未建立，不能将现有 SDK 和测试入口当作已经交付的产品 UI。

| 范围 | 建议复用方式 |
| --- | --- |
| 页面、组件、样式、导航和表单 | 共用源码，按屏幕尺寸调整布局。 |
| 加入、审批和管理流程 | 共用展示与交互，根据节点返回的业务状态更新界面。 |
| 节点命令、状态、错误和更新订阅 | 面向同一 Interface，由两个 Adapter 接入。 |
| 文件、通知、后台运行和应用生命周期 | 由平台分别提供能力，界面据实际能力调整。 |
| 业务权限与持久状态 | 继续由 Rust 节点验证和保存，UI 不另建业务权限或存储模型。 |

普通浏览器仍是具有独立身份和成员资格的节点，不因共享 UI 变成远程原生节点的管理网页。原生侧与浏览器侧的传输、存储和生命周期能力不同，共用源码不承诺所有平台能力相同，也不要求两端使用完全相同的构建产物。现有能力依据见[桌面管理](2026-10-03-desktop-management.md)、[Android 管理与生命周期](2026-10-03-android-management.md)及[浏览器管理与复制](2026-10-02-browser-control-replica.md)。

## 性能和生命周期约束

以下是本轮建议，尚未实施或测量：

- 安装版由原生 Rust 节点处理业务，WebView 只运行界面，避免在同一客户端再启动一份浏览器 WASM 节点。
- UI 获取必要的状态和增量更新，控制更新频率与队列；业务数据路径不绕经界面，避免频繁跨进程传输整份历史或大数据。
- 按页面需要引入组件，长列表和大日志视图在实际需要时采用分页或虚拟列表。Vue 官方提供按需加载、列表虚拟化等[性能实践](https://vuejs.org/guide/best-practices/performance.html)。
- 节点运行生命周期与界面分开。Android 后台参与需要平台运行入口承接；浏览器仍遵守页面冻结、关闭和重开的限制，UI 框架不自动提供持续后台联网能力。
- 后续若恢复 UI 工作，用目标平台适合的指标比较纯节点与节点加 UI 的内存、空闲 CPU、启动和操作延迟。统计应包含 WebView 相关进程，并使用相同业务负载；小安装包、编程语言和框架名称都不是低运行内存的证据。

目前没有 miopunch UI 的内存或速度实测，也没有确定 MB 上限、延迟目标或受支持的最低设备规格。上述观察方法不是本次已经获准运行的实验；本记录只保存后续讨论所需的依据。

Vue／Tauri 技术栈与首版平台范围已经确认。恢复 UI 工作时仍需确定具体组件库、平台能力展示、统一 Interface 的操作和错误语义、Android 运行接入以及性能预算。现阶段不冻结依赖版本，不生成正式 UI 规格，也不把文档记录当作实现领取。

## 2026-10-11：恢复讨论时确认的易用性原则

用户明确，项目初衷来自 [iroh 协议：网络韧性的基础设施](https://bd.ailishi.ai/blog/iroh-network-resilience/index.html)，特别是 Brendan O’Brien 在 21:13 问答中提出的自我配置方向：软件承担底层技术组合与环境适配，减少调用方处理配置矩阵的负担。本文对演讲的引用只解释理念来源，不把演讲中的能力描述当作本项目已完成的验证。

用户回顾此前 Go 版本时指出，给用户大量自由配置逐渐变成了需要阅读长篇说明才能使用的产品。本次产品讨论以普通用户上手即用为优先原则：

- 常用流程让用户表达想完成的事情，不要求先理解联络载体、地址观察、打洞、选路或同步编排。
- 已有底层组件应由软件自动配置、组合与协同；界面设计围绕用户目标和可理解的结果。
- 易用性作为首版功能取舍与操作流程的依据，具体默认入口、页面结构和首项远端业务仍须通过场景讨论确定，尚未成为已接受的界面方案。

这延续 [产品主线](2026-09-27-product-mainline-draft.md) 的使用体验优先及普通用户无需渠道编排的共识。已有的稳定网络身份、成员授权、邀请信任，以及用户对公共资源的禁用／替换选择仍是基线；本次原则没有授权绕过这些选择或自动扩大成员权限。没有新增账户、云服务依赖、框架选型或服务 ACL 决定。

随后用户认可日常界面以设备／可用服务为中心，并明确产品面向个人与小团队，先从自己在浏览器和原生客户端中的组网需求出发。首版面向用户的业务功能仍未选定；文件传输等是用户提出的候选，不能据此认定首版已经转向文件传输产品。

用户说明，当前底层 demo 的验证先行，创建／加入网络、创世凭证的用户呈现与备份操作还没有充分考虑。业务、身份与权限验证由 Rust 节点处理的既有分工继续适用；讨论需要把这些能力映射成简单的用户操作。创世恢复凭证的具体介质、展示方式及首次备份是否阻塞开始使用，尚无新决定。其恢复语义沿用 [ADR 0008](../adr/0008-genesis-recovery-credential-pins-create.md)，不因界面简化而将恢复凭证与日常邀请或节点身份合并。

用户进一步重申：创世凭证永久丢失且没有保留副本时，无法恢复原网络的创世权限证明；可以创建另一网络并迁移，但新网络不是原网络的恢复。随后用户指出讨论过早进入凭证备份流程，产品的具体用户用途尚未确定。讨论应先明确用户要解决的真实问题，再确定首版业务功能与交互；首次备份流程的候选建议没有成为决定。

### 用户补充的项目动机沿革

用户最初受中国大陆网络环境下的 UDP 打洞及 frp XTCP 启发，希望实现点对点连接。这是用户对项目起点的回顾，不构成当前对某产品打洞成功率或完全不需要辅助服务的验证。

用户后来长期使用组网工具，个人跨网络 SSH／tmux 需求已通过现有组网与 Android 远程客户端组合满足；再次实现一个远程 shell 入口已不足以构成其切换理由。用户当前部署中的 VPS 费用和中心服务维护仍让其不满意。本记录没有将这段个人部署经历扩展为“所有 Tailscale 使用方式都要求用户自购 VPS”的结论。

iroh 访谈让用户重新重视自我配置与将复杂度留在软件内部：端点加密、环境适配与能力协同应融入自然的日常行为，技术细节可以让感兴趣的人了解，但不应成为开始使用的门槛。用户仍未确定首版应用功能，希望借此次叙述提炼产品定位。

现有主线中的个人／小团队私有组网、无需用户租管必需控制服务器、浏览器独立参与和用户掌握网络权限，提供定位讨论的候选依据。是否将这一组网能力本身作为首版产品价值、是否足以让用户替换当前方案，以及是否内置文件传输等应用，尚未被本次叙述确认为新决定；不因底层 demo 已通过而宣称已能完整替代现有 VPN 产品。

## 2026-10-12：Android 与已有 VPN 共存的候选用途

用户提出一个具体的尝试动机：Android 能通过常规 VPN 入口，或在授权 root 的情况下通过系统网络接入，访问自己的私有网络；希望已有其他 VPN 仍能正常使用，并尽量无感接入。用户同时询问按设备身份组织的网络与常规 IP 访问是否冲突。这里记录的是候选需求与可行性问题，尚未决定首版必须提供通用虚拟 IP、要求 root 或开发第二个 VPN 应用。

两层能力需要区分：当前 demo 验证了端点身份、准入、安全连接及数据交换；它尚未建立可供其他应用直接使用的虚拟 IP／系统路由接入。为现有应用提供 IP、代理或端口访问，需要额外的接入层。按稳定节点身份组织网络与提供虚拟 IP 可以组合，但不是已有 SDK 建连成功就自动得到后者。

[Android VPN 官方文档](https://developer.android.com/develop/connectivity/vpn) 规定，同一用户／工作资料只能运行一个活跃的 VPN service，启动另一个会停止已有服务。仅让两个独立应用分别使用标准 VpnService，无法满足同一资料中双 VPN 无感共存。普通应用不占用该 VPN service 位置，但其联网仍受当前 VPN 与系统策略影响；本地代理／端口入口也不等同于任意其他应用获得虚拟 IP。

授权 root 后，基于独立 TUN 与策略路由进行特定网段接入，是可研究的增强路线；[Linux TUN/TAP 文档](https://www.kernel.org/doc/html/latest/networking/tuntap.html) 提供虚拟接口及相应权限机制的依据。这不证明 Android 的具体系统、SELinux、netd、第三方 VPN 路由和锁定策略已经兼容，须在目标设备上单独验证。与已有 VPN 合作集成也依赖对方提供可用接入能力，不能承诺对任意 VPN 都通用。此次只读核查没有实现 TUN／IP 接入、启动新 VPN 或改变手机路由。

用户随后明确纠正：VPN 共存只是同一易用性理念下随口想到的例子，不是已确定的产品概念或首版硬性条件。虚拟 IP、root 增强及共存优先级均未获选择；助手提出的“优先保证不打断已有 VPN”不能作为已接受的产品决定。少配置、上手即用和多平台属于体验取向，具体用户用途及功能范围仍在探索。

## 2026-10-20：创世凭证的日常使用与备份体验

用户确认产品体验方向：设备使用本地安全存储保护凭证，使用时通过解锁和用户确认；同时提供文件／二维码形式的可外置备份。普通用户无需在日常高权限操作中手动处理原始长密钥。此处确认的是产品方向，平台存储、解锁方式、导出保护、编码格式及首次备份时机尚未选择，也尚未实现。完整恢复材料仍按 ADR 0008 同时保存根私钥和 canonical Create 哈希。

用户希望继续沿实际场景讨论，包括创建网络、加入其他设备、原设备可用时换机，以及设备损坏／丢失后的恢复；同时提出创世设备权限交接的问题。尚未决定哪些设备默认保管根凭证、是否允许多份设备副本、交接后原设备是否保留副本，或如何处理泄露后的权限替换。日常管理员、设备成员身份与创世凭证保管须保持区分；设备本地删除凭证或撤销成员资格不等于使其他根凭证副本失效。新凭证对应新网络的既有规则没有改变。

本轮为产品讨论与已确认方向记录，不自动启动 UI、平台密钥存储、凭证传递协议或权限模型变更。

用户随后认可多台指定设备分别加密保存创世凭证、配合独立外置备份的方向，以降低单设备损坏或丢失导致创世权限永久丢失的风险；举例为两台设备各自保存。日常使用无需重复输入／搬运私钥。此方向不意味着普通成员或日常管理员自动取得根凭证，也不构成强制至少两台设备的首次使用门槛。

用户同时提出高权限验证是否应每次进行。讨论须区分每条高权限记录的根签名与授权校验、设备解锁／用户确认，以及当前实现的临时提权窗口。讨论最终明确选择逐项确认，以 ADR 0015 为准；源码现有窗口机制不代表最终交互。多副本降低丢失风险，不等于已泄露副本可单独撤销；凭证分发和平台加密保管仍未实现。

用户进一步澄清，两类入口是直接提供创世凭证，以及确认使用已由设备加密保存的创世凭证；认可 TOTP、扫码确认和通知相应节点弹窗确认均可作为后一类的候选交互。无需据此引入强制双设备共同授权，也未选择必须同时交付全部方式。各方式的验证与签名接线仍须分别设计，尤其 TOTP 是额外的用户验证，不替代根签名，也不能单独解密离线备份。用户继续询问前一类能否避免手输明文私钥；加密恢复文件／二维码及其解锁交互仍处于讨论，没有新增备份格式或密码学方案决定。

随后完成[备份与恢复方式研究](2026-10-20-genesis-credential-backup-and-recovery-research.md)，用户重新审视额外加密的复杂度，并明确接受：**恢复卡不强制额外专用密码，引导打印保管或存入密码管理器，加密文件作为可选导出方式。** 这是本段讨论的最终取舍，以 [ADR 0013](../adr/0013-genesis-recovery-card-without-mandatory-password.md) 为准；此前“加密文件＋备份密码”的讨论不构成默认必须的结构。完整恢复卡仍是最高权限秘密；具体格式与保护接线尚未实现。

继续讨论首次创建流程时，用户明确要求首次创建后必须先保存恢复卡，再进入正常使用，不接受“稍后备份”作为跳过入口。随后用户表示不需要重新导入或扫码读回检查，保存后由用户确认已保存即可继续。该要求已补入 ADR 0013。

### 加入网络：扫码方向与管理员确认

用户明确纠正：本轮加入流程只讨论成员入网，是否让新设备保管创世凭证属于后续独立流程，不在加入时决定。扫码方向应适应设备条件：可以由手机扫描电脑／其他设备显示的二维码，也可以由手机显示二维码供电脑／其他设备扫描，不固定由哪端展示或扫描；具体二维码内容与交换接线尚未设计。

用户继续询问管理员节点收到入网申请时能否弹出确认。当前 Native／Browser SDK 已有申请记录、查询和人工批准入口，正式界面可据此呈现申请提示与审批；现有 demo 尚无完整产品弹窗或系统通知。这里指收到申请的管理员节点，未决定将每个申请广播给所有管理员、引入中心推送或扩展离线处理语义。普通入网审批沿用日常管理员权限，不自动授予管理身份或交付创世凭证。

用户进一步要求将此前邀请码机制纳入灵活的加入流程。既有基线包含人工批准的普通邀请，以及预先授权、受有效期和可选次数约束的 precode；两者共用已授权材料交付与持久化完成语义。二维码／链接／文本是传递入口，不决定是否需要现场审批；邀请不携带创世私钥或长期准入秘密。precode 仍由其唯一指定核销节点处理，节点不可用时不能新兑换，码到期也不自动终止已取得的成员资格。

用户认可统一加入流程方向：一个加入入口识别二维码、链接或文本传入的邀请材料，按普通邀请或预授权码进入相应授权路径。双向扫码须区分现有设备展示的网络邀请和申请设备展示的配对信息；后者要先让申请设备取得选定网络的可信邀请，再进入受限申请流程，当前尚无这层完整产品配对接线。普通邀请由收到申请的管理员提示并人工确认；预授权码校验通过后无需再次人工批准。两条路径随后共用入网材料交付、保存和成功判定；中断保留进度，同一兑换重试不重复消耗次数。是否授予管理身份或保管创世凭证仍属于后续独立流程。

用户随后明确取消手输短码：短码引入了不必要的复杂度。统一加入流程保留完整邀请，以二维码、链接或复制粘贴传递；不为短码新增查询目录、专用会合或短口令配对机制。普通邀请与预授权码的既有审批／核销规则继续适用。完整票据的具体格式仍待设计，本轮不自动启动实现。

### 完整邀请格式：待审建议与已确认范围

针对用户追问具体建议，候选为一份带版本和用途标识的完整票据，复用现有网络锚、联系节点、可更新的连接线索及可选 precode 令牌；以 URL 安全文本编码（例如 Base64url）传递。建议完整邀请码形如 `mio1_…`，浏览器链接形如 `https://<可信客户端入口>/join#<完整票据>`，二维码承载同一链接。配对信息与网络邀请使用不同用途标识；不携带创世私钥或长期准入秘密。HTTP 的 fragment 在发起资源请求前分离，可减少邀请令牌随请求路径进入服务器日志，但仍可被页面代码及保存完整链接的应用读取。[RFC 3986 §3.5](https://www.rfc-editor.org/rfc/rfc3986.html#section-3.5)

此前提出的十二位短码、五分钟配对窗口及参考 Magic Wormhole 的短码交换建议，已随用户取消短码而退出当前方案；不再作为待选实现要求。双向扫码继续使用完整邀请／完整配对材料，仍需原有联络与实际核销／批准节点可用。

用户指出节点未必有公网 IP，并追问 relay 不可用时 MQTT／IRC 联络信息是否包含在邀请中。这里的“连接线索”必须具体覆盖可用于入网前引导的资源与目标路由，不能只携带公网地址或依赖 Iroh relay。拟议完整票据应能表达 MQTT 的设施／原生与 WSS 入口及联系节点路由，IRC 的设施／原生与 WSS 入口、频道与目标路由，以及可用的 relay／直连线索；使用仍受本地资源许可与禁用规则约束。若只给资源别名，需保证接收方能在入网前解析；不能依赖入网后同步才取得联系配置。此为格式建议的细化，尚未冻结字段。

当前事实：核心 `ManualInvitation` 的 96 字节仅包含根公钥、Create 哈希和联系节点身份；`Precode` 再增加 32 字节令牌，没有把 MQTT／IRC 设施描述一并编码。现有 browser demo 分别输入 invitation 与 `Configuration`（含 mqtt／irc／contact_routes）；native 也通过资源配置和地址／发现接线使用 carrier。完整自含邀请的产品包装仍需补齐，不能把 demo 的外部配置误称为已嵌入邀请。MQTT／IRC 是可用于受限引导的通道，不要求参与设备具有公网 IP，也不因邀请列出它们就自动成为普通业务中继。

### 管理员扫描新节点：已认可的理论流程

用户继续追问一次扫码能否带齐 MQTT／IRC 等路径，并认可以下流程理论上可行：新设备先用软件提供的默认或用户已有获准资源准备入网前联络，待其临时接收路由就绪后，在完整配对二维码中给出独立节点身份、本次配对校验材料，以及少量当前可用的设施入口与路由（包括原生／WSS 对应入口）。管理员一次扫码即可取得联系新设备所需材料，无需新设备拥有公网 IP；不额外引入短码目录。

管理员据此联系新设备，核对实际对端身份并确认本次配对，再通过受保护的双向会话交付所选网络的完整邀请及管理员的联系方式。新设备据此进入既有正式申请／审批／材料保存流程；回程可复用已建立会话，或按交付的联系方式建连，无需再次反向扫码。配对只允许接收所选网络的邀请，不能提前授予成员资格、业务访问或创世权限；须能校验请求确实对应本次扫码配对，不能仅凭知道节点 ID 就任意写入网络邀请。具体校验材料、作用域和消息接线仍待设计，未选择新的密码协议。

现有载体可在收到数据时取得源路由，但这不等于仅靠路由即可认证节点，也不等于新节点已实现接受未知管理员反向交付邀请的入口。现有 SDK 的申请绑定依赖事先取得的邀请／指定 contact；反向配对包装与该入网前受限入口仍需实现和验证。至少有一条双方均可用且获准的联络路径才可完成此交换；二维码携带地址不能保证其后网络永远可达。

此次确认的是理论流程方向，不代表反向配对已实现、已经测试通过或可以启动实施；具体协议和接口仍须在后续实施前明确并做最小真实验证。

### 加入中断与人工拒绝：已确认规则

用户认可按实际进度呈现与恢复加入操作：尚未联系到管理员时显示联系中或暂不可达，保留操作并允许重试；申请已收到时显示等待批准，同一申请的重试不反复弹窗；批准后材料尚未保存完整时显示正在完成加入，软件按原进度续办，不再次审批或重复消耗同一次邀请码兑换；已经加入但当前连不上时保持已加入状态，仅表达设备暂不可达，不要求重新入网。自动续办仍受现有授权有效性、资源许可和操作预算约束，不能复活已经失效的授权。

人工拒绝只针对本次申请：管理员拒绝后，申请方显示未获批准，停止该申请的自动重试；用户可以主动提交新申请，须与旧请求的传输重试区分。旧请求重试不重新触发审批提示，也不能自行撤销拒绝结果。不将一次拒绝视为永久封禁设备身份。

现有 SDK 已有持久化申请、批准结果和材料交付恢复基础；本段新确认的拒绝处理、提示去重及完整客户端自动续办交互仍须后续接线，不代表已有产品功能或本轮实现授权。

### 加入后的相关流程：讨论稿

用户要求继续梳理后续与相关流程。以下权限事实沿用 CONTEXT、ADR 0007／0008 与现有管理、撤销、恢复、轮换及迁移实现；交互组织和默认选择仍是建议，未获本轮确认，不启动实现。

| 流程 | 已有权限与结果边界 | 建议的用户操作 |
| --- | --- | --- |
| 任免日常管理员 | 任命／撤销管理员须创世权限；降权保留普通成员资格，不交付根私钥 | 在已加入设备详情中设为管理员或撤销管理身份，展示目标并验证确认 |
| 增加创世凭证保管设备 | 完整根副本拥有同样创世能力，不能单独作废；本地保护与设备间交付尚未产品化 | 从已保管设备发起，选择已加入的目标设备，双方确认后受保护交付；接收方先安全保存，发送方再显示完成 |
| 正常换机 | 已确认按同一节点身份整节点迁移，延续仍有效的权限；新增设备才使用独立身份 | 暂停旧节点、安全转移、恢复并确认成功，再清理旧端；旧端不退出网络，详见下文与 ADR 0016 |
| 设备损坏／丢失 | 其他保管设备或恢复卡可找回创世凭证；网络恢复仍需历史／合法成员；成员移除不撤销已复制 root | 区分“接回新设备”“移除丢失设备”和“根凭证可能泄露”，避免一个找回按钮暗示全部处理完成 |
| 关闭、退出与移除 | 关闭只断连；主动退出或被移除结束成员资格，重新加入需新授权；管理员自退出／移除仍是管理员的节点须创世权限 | 清楚区分关闭应用、退出网络、撤销管理身份、移除设备；不把清空本机文件当作已向网络宣布退出 |
| 邀请维护 | 普通邀请需审批；precode 有有效期及可选次数，单码撤销由指定核销节点处理，已授成员资格独立 | 发出邀请后可查看预授权码状态、撤销码、生成新邀请；联系线索刷新不延长授权 |
| 网络安全更新与迁移 | 准入秘密轮换须创世权限，留存成员需确认保存；新根是新网络，迁移先取得目标材料并验证目标业务路径再切换 | 分别表达更新入网秘密与创建新网后迁移；不把换备份密码当作换根或撤销旧副本 |

可先细化“增加保管设备”：已保管设备选择已加入目标，确认实际设备身份和交付意图，目标也确认接收并启用本地保护；凭证在受保护会话中交付，目标保存成功后双方显示完成。同一次交付中断后应能继续，不提前清除发送方材料。建议此入口默认增加保管副本，发送方保留原有能力；清除旧机凭证放在后续明确的换机／清除操作中。此处不会顺带改变普通成员的日常管理角色；具体授权检查、持久化结果、协议和平台保护仍需设计。

### 浏览器的管理身份与创世凭证保管：当前已确认取舍

用户认为上述后续流程总体方向可行，要求符合直觉、无痛且顺畅，并询问管理员／创世权限是否应平等开放给浏览器，或增加限制。用户随后明确使用习惯各异，浏览器或 PWA 也可能长期使用：当前阶段通过提醒表达环境差异，不对浏览器增加特别限制；以 [ADR 0014](../adr/0014-browser-role-parity-with-contextual-reminders.md) 为准。

当前源码与证据：Browser SDK 与 Native 共用管理动作分类、签名和授权校验，支持审批、precode、普通成员管理及管理员任免等入口；创世任免等高权限动作要求临时提权。`browser-probe/src/management.rs` 将创世 key 仅保存在本页活动管理会话，未写入 IndexedDB；结束会话／页面销毁后不能继续使用该提权。浏览器长期加密保管根凭证、与 Native 对等的公开创建／根恢复／备份入口并未全部交付，不能据管理方法存在推导能力已完全对等。

已确认方向是权限资格与保管选择沿用统一规则：浏览器／PWA 可成为管理员、可在合法创世证明与用户确认后执行重要操作，也可按统一授权流程保管创世凭证。不采用此前仅因浏览器身份而默认限于临时使用、长期保管另加特别限制的建议；用户可选择长期或临时使用。凭证保护、解锁和独立备份仍须实际实现，提醒不替代这些共同安全要求；也不能把浏览器存储称为已具备与原生 OS 密钥库相同的保护，或把仍开着的标签页等同于可靠常驻服务。

浏览器可以冻结或丢弃页面；持久存储申请能降低自动驱逐，却不能阻止用户清除数据。关闭页面只是断连，不自动撤销成员／管理员资格；如果站点身份材料丢失且无可用完整备份，新的浏览器身份须按新设备流程处理。precode 若指定浏览器为核销节点，仍受其实际在线状态约束，不自动转交其他管理员。[Chrome 生命周期说明](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)、[MDN 存储说明](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

在网页中使用创世权限还意味着信任交付该页面的代码；加密静态保存不能阻止已进入同一页面上下文的恶意代码滥用已解锁权限。这个风险应作为保管方式选择的依据，不据此自动判定全部浏览器节点低权限或强制引入额外设备审批。[W3C WebCrypto 安全说明](https://www.w3.org/TR/webcrypto/#security-considerations)

### 重要操作确认：逐项确认已确定

用户确认逐项验证，并强调这些操作非常低频但非常重要。每项创世高权限操作应明确展示具体动作、对象和影响，单独完成验证确认；不提供一次确认后执行其他危险操作的通用时间窗口。同一项操作因网络中断重试时沿用其确认和已提交结果，不重复执行或反复弹窗；动作、目标或关键影响改变则是新的确认范围。普通入网审批等日常操作仍按既有权限处理。统一规则与现有代码的窗口语义差异见 [ADR 0015](../adr/0015-confirm-each-genesis-operation.md)。

以下跨设备交互方向已在后续讨论中获得用户确认（见文末补充），具体协议仍待细化：操作发起端展示变更，向用户指定的凭证保管设备请求对这项变更的确认；持钥端核对同一网络、目标和动作，用户确认后完成签名并回传结果，不因批准操作自动复制根凭证到发起端。本地保存凭证和使用恢复卡可接入同一确认入口。跨设备请求授权、结果关联、重复处理与保存接线仍待设计，不能转移现有 `ManagementSession` 或直接声称已实现。

### 换机的 KISS 决定：区分新增设备与整节点迁移

用户指出换机包含普通节点、日常管理员、管理员兼创世凭证保管等情况，希望用 KISS 方式统一，并提到设置和身份的延续。用户随后确认采用保留原节点身份的整节点迁移方向，取代此前正常换机按新设备独立入网、再获得角色和凭证的建议；见 [ADR 0016](../adr/0016-preserve-node-identity-on-device-replacement.md)。具体安全交付、切换与跨平台格式尚未设计，不启动实现。

已确认将用户意图区分为“新增一台同时使用的设备”和“让新设备接替当前节点”。前者继续生成独立节点身份并走既有加入流程；后者通过完整节点备份恢复同一个节点身份、适用设置、授权历史及必要私有材料，有创世凭证时连同其原有保管材料迁移，按仍然有效的权限延续，不重新任命一遍管理员。用户可把这理解为一个节点换运行设备；同一节点身份不应在新旧设备上持续并行使用。若想两台同时参与，就使用新增设备流程。

源码依据为 `NativeNetwork::create_backup`／`restore_backup`：备份停止节点并 checkpoint，复制节点 key、网络锚、管理数据库、入网材料、根凭证（若有）与资源配置；`tests/precode.rs` 的 supported restore 检查恢复后节点 ID 和网络锚保持不变。恢复不会凭旧快照恢复已撤销的真实权限；当前支持的恢复还会停止旧 precode，防止回滚计数继续核销，需要重新签发。这里没有重新执行测试，只核对已有代码和记录。

建议最简形态为停止旧节点并准备完整备份，受保护交付到新设备，恢复并核对可用，确认成功后再清除旧端本地材料。不是无中断热迁移，不承诺在网络分区中让两个副本自动判断唯一活跃者。旧端退出当前运行后保留完成或失败处理所需的材料；尚未确认新端状态时不能让两端无条件重开同一身份。迁移确认可以针对一个明确的逻辑操作展示源、目标、网络、身份／角色和是否包含创世凭证，沿 ADR 0015 约束其范围，而不把每条底层记录变成独立弹窗。

此决定不是把现有目录复制功能直接宣称为跨平台产品迁移：Native／Browser／PWA 需要可互通的逻辑导出导入与本地保护，不能直接把 SQLite 目录当作浏览器快照；已有只接收入网邀请的反向配对入口也不能被默认为允许接收节点私钥。具体迁移包、交付授权、单端运行切换、失败处理和能力资格仍须设计。整节点备份与仅含创世凭证的恢复卡保持区分；只有恢复卡而无完整节点备份时，不保证可保留原节点身份。旧机不可用但存在可用的完整备份时，可按同一身份恢复的边界继续设计。

用户随后追问 p2panda／Iroh 授权是否支持。核对本项目固定版本源码与 Iroh 官方 1.2.0 API 后确认授权模型允许此方向：`vendor/iroh/src/endpoint.rs` 的 `Builder::secret_key` 和 `Endpoint::id` 以密钥公钥决定端点身份；`src/native_network.rs` 绑定端点时使用保存的节点私钥。`src/management_auth.rs` 将 p2panda-auth 的成员 ID 具体映射为 `VerifyingKey`，有效角色由签名历史推导，设备硬件不是授权对象。`src/daily_management.rs`、`src/manual_admission.rs` 和 `browser-probe/src/management.rs` 为新管理记录使用新的随机日志 ID，并引用已知因果依赖；`tests/management_auth.rs` 还覆盖同一根密钥恢复后新日志可用、旧日志 ID 冲突被拒绝。这支持保留身份与有效权限，但不提供旧机副本的自动吊销或全局单端运行保证，也不延续旧 QUIC 业务连接。[Iroh 1.2.0 密钥 API](https://docs.rs/iroh/1.2.0/iroh/endpoint/struct.Builder.html#method.secret_key)

用户在核对上述代码依据与边界后确认：从 Iroh 身份认证与本项目 p2panda 授权映射的角度，保留同一节点身份的换机方向成立。此确认收敛了授权模型的可行性问题；完整状态交付、旧端停用、新端接管及跨平台导入导出仍待后续设计与实现，不代表完整迁移流程已通过实测，也不自动启动实施。

用户随后要求结束换机讨论，转向其他流程，认为进一步展开的交互过于复杂。保留已确认的整节点迁移方向和授权模型可行性；随后提出的扫码顺序、接管阶段与中断处理交互不定稿，不作为新增要求或实施安排。

### 设备管理：已确认的交互方向

用户确认在设备详情中提供“设为管理员”“撤销管理员”和“移除设备”三个独立动作。设为管理员授予日常管理能力；撤销管理员只撤销该角色，保留普通成员资格；移除设备结束成员资格。管理员任免及移除仍具管理员身份的设备须创世权限，按 ADR 0015 针对每项操作确认；移除普通成员由日常管理员按既有权限处理。

操作展示目标设备和具体影响，确认后明确呈现结果。目标设备暂时离线不妨碍有权节点作出管理决定，但实际执行仍受有效授权与因果历史校验约束，实际生效受管理记录传播影响；界面不能将本地记录已保存表达成全网已经完成。管理员身份与创世凭证保管保持独立：任命管理员不自动交付创世凭证，撤销管理员也不清除对方已持有的凭证。

本段确认交互方向与既有权限边界，不启动界面或运行代码实现。

### 关闭应用与退出网络：已确认的交互方向

用户确认区分停止本机运行与结束成员资格。“明确退出应用”停止本机运行，保留身份和成员资格，无需确认；下次打开沿用已保存身份尝试连接，权限仍按有效授权判断。后续已明确桌面关闭窗口及 Android 切到后台／锁屏继续运行，见文末平台生命周期决定。“退出网络”放在网络设置中，明确确认“退出后重新加入需要授权”；普通成员可自行退出，仍具管理员身份的节点须创世权限，沿用逐项确认规则。

退出完成后呈现“本机已退出”，不能暗示其他设备均已收到退出记录。此处不承诺浏览器页面关闭时必定执行清理或发出消息，也不把关闭页面当作发布退出记录。本段只确认交互方向，不启动界面或运行代码实现。

### 邀请交互：KISS 与易用性优先

用户针对随后提出的邀请维护列表明确纠正：不要复杂，遵守 KISS，重点是易用性。此前助手提出的集中维护入口、剩余次数与可用／过期／用尽／撤销状态列表未获确认，不作为主界面要求。既有普通邀请审批、预授权有效期与可选次数、撤销和核销边界继续成立；这些规则不意味着用户每次邀请都要配置或管理它们。

接下来的交互建议应先覆盖最常见的“邀请设备并让对方加入”，减少必选项、页面和日常管理负担；只有用户明确需要免现场批准或处理具体问题时，再呈现相应选择与必要信息。具体默认邀请参数和精简后的界面尚未定稿，不启动实现。

用户确认精简后的默认邀请交互：“邀请设备”直接展示二维码并可分享，对方打开后进入加入申请，管理员确认加入；不要求每次先选择邀请类型、填写有效期或管理次数。用户确有免现场批准的需要时，再提供预授权选项，既有预授权边界不变。后续流程也遵守“常用操作直接完成，必要时才出现额外选择”的原则；未决定具体默认参数或实施细节。

### 日常联网与自动恢复：用户无需关心连接实现

用户进一步明确：普通用户不应关心 Iroh，连接实现应尽量自配置。用户联网后，由软件自动恢复本网联络，设备可达时自动建立或恢复可用连接，不要求用户选择载体、配置资源、手动重连或处理路径变化。日常界面围绕设备和实际可用性表达，不把底层引擎、联络资源或连接调参变成使用前提。正常恢复过程尽量自动完成、少打扰；此方向不是要求用户日常查看诊断页。

高级用户的可调项后续再讨论和满足，当前不优先设计高级设置或要求用户先配置它们。软件默认配置、发现和恢复承担主要责任，仍沿用用户已许可资源与自动恢复的既有边界。此处的自动恢复指节点联络与可用连接的恢复，不修改此前已确认的连接终止语义或增加任意上层业务会话无损续接承诺；本轮没有新增协议、固定恢复时限或展开实现。

### 重要操作：持有凭证的设备确认优先，离线凭证兜底

用户确认基本流程：在当前设备发起具体重要操作，持有创世凭证的设备核对并确认，结果返回发起端；本机持有凭证时就在本机确认。用户无需为了操作导出、复制或临时导入凭证，也不因批准操作自动成为凭证保管节点。

用户进一步明确顺序：无法走通上述流程时，才使用恢复卡等离线凭证方式。默认操作入口保持一致，不要求每次先选择凭证来源；两条路径都遵守 ADR 0015 的逐项确认和既有授权校验。这里的“离线凭证”指备用凭证来源，不新增脱离必要历史即可完成任意网络操作的承诺。跨设备请求授权、可信目标识别、签名与结果关联、保存及重复处理仍待设计和实现，本轮不启动实施。

### 增加创世凭证保管设备：已确认的交互方向

用户确认以下流程符合直觉：打开已加入设备的详情，选择“让此设备保管创世凭证”，由原保管设备确认、接收设备确认，再由软件自动完成受保护交付与保存。确认时明确告知：接收设备将能确认所有创世高权限操作。保存完成后才呈现完成结果，具体交付协议和持久化接线仍待设计、实现与验证。

此操作增加保管副本，原设备继续保管；接收设备不会因此自动成为日常管理员。普通设备加入时无需经过这个流程。此段将此前“增加保管设备”的交互建议确认为产品方向，不启动运行代码或界面实现，也不展开已结束的换机讨论。

### 停止本机保管创世凭证：确认其他成员保管，允许明确强行删除

针对“停止保管创世凭证”的建议，用户要求比单纯提醒备份更明确的保护：正常删除前，必须确认本网另有成员持有创世凭证，并向用户提示。若没有其他保管成员或无法确认，不按普通确认直接删除，而应明确提示尚未确认其他成员保管及删除风险；用户仍可主动强行确认删除，不能把此检查变成不可绕过的硬性双设备要求。

独立恢复卡仍可作为备用副本，但其存在不等于已经确认本网另有成员保管。检查须区分确认存在、没有已确认的其他保管成员以及暂时无法确认，不能把其他成员离线视为没有凭证，也不能把旧记录宣称为当前持有的确证。具体如何确认其他成员持有、确认的时效和交互措辞仍待设计，不假定当前 SDK 已提供该能力。

停止保管只删除软件保存的本机创世凭证，保留节点身份、成员资格及仍有效的日常管理员身份；后续创世操作走其他保管设备确认或离线凭证方式。此操作不作废已经存在于其他地方的同一凭证副本。本段记录用户确认的保护和强行覆盖边界，不启动实现。

### 设备丢失：沿用移除入口，明确凭证风险边界

用户确认：设备丢失时，从设备详情选择“移除设备”并确认；需要创世权限时，接入已确定的凭证保管设备确认流程，走不通时再使用离线凭证方式。不另设一套日常挂失流程，原有权限检查与记录传播边界继续适用。

若丢失设备曾保管创世凭证，在同一个移除确认页明确说明：移除成员资格不能作废它可能持有的创世凭证。用户担心凭证泄露时，再引导到更换网络的处理流程；不将“移除成功”表达成创世凭证风险已经解决，不自动换网。此段确认产品交互方向，不启动运行代码或界面实现。

用户明确继续讨论剪贴板同步、文件传递、服务转发（例如特定端口），以及从浏览器访问内网服务等基本能力，并保留其他业务能力的扩展空间。这些能力应像插件一样具有清楚的模块边界，避免混成一个无区分的库；同一个库内部有明确模块区分也可以。领域上以 Application service 表示用户使用的业务能力，与发现设施及数据中继区分。

### 首版明确加入远程 shell：复用 tmux 保留工作会话

在跨设备内容传递与远端服务访问的聚焦建议上，用户要求初版明确加入远程 shell，并采用 tmux 保留会话来应对断线和网络波动，遵守 KISS。远程 shell 从一般候选提升为首版明确需要的模块；其他领域的完整功能边界、平台矩阵和实施顺序仍待后续收敛。

目标体验是选择设备后打开终端，远端 tmux 持有工作会话；网络连接断开时，该远端会话和其中程序可以继续运行，miopunch 恢复可用连接后重新接入原会话。沿用当前有效授权检查，不把重新接入解释成绕过已发生的权限撤销。保持会话存活由 tmux 承担，网络联络和重连由 miopunch 承担，避免另造终端会话持久化系统。[tmux 官方说明](https://github.com/tmux/tmux/wiki/Getting-Started)

这里保留的是远端 shell 工作会话，而不是保证底层网络连接不会断开；不改变 ADR 0009 对已终止连接的处理。范围是网络中断后的重新接入，不包含远端主机重启、tmux 服务退出后的进程恢复，也未选定离线输入缓存或重放规则。tmux 所在目标环境和安装交付方式待后续确定，不因旧版存在 WSL／SSH 接线便自动冻结当前平台方案。

本轮已核对归档 `internal/shelltarget/tmux_unix.go` 的创建或附加会话入口及 `tmux_command.go` 的历史 WSL／SSH 路径，作为复用参考；未运行历史测试，未实现新 Rust／Browser 业务模块。

### 功能范围收敛：停止追加本轮候选

用户否定随后提出的远程文件管理、指定目录备份、远程唤醒、远端下载等新增建议，也未采纳该轮手机摄像头／麦克风扩展建议，要求就此收起。它们不进入初版范围；此前对远端共享的一般兴趣不等于已选定某项硬件共享能力。

初版继续围绕已确定的三个方向：指定设备组或两台设备之间的剪贴板共享与文件传递；指定端口转发及浏览器访问内网页面的服务访问；借助 tmux 保留工作会话的远程 shell。具体平台支持和各模块的边界后续再收敛，本轮没有新增实施授权。

### 首版功能范围：五个独立业务模块

用户最终将首版范围明确列为五项，不再只以三个宽泛领域表示：

1. **剪贴板同步**：一对一，开启后自动同步；以文末用户最终确认的范围为准。
2. **文件传递**：设备之间传递文件。
3. **端口转发**：支持 TCP 和 UDP，转发指定端口的服务。
4. **浏览器访问服务**：在浏览器中访问指定内网“地址:端口”的服务，承接此前内网页面的目标场景；作为独立模块，与端口转发分别表达。
5. **远程 shell**：支持同时使用多个会话，基于 tmux 保留远端工作会话，应对断线和网络波动，连接恢复后重新接入。Windows 提供端采用 WSL + tmux；Android 仅作为终端客户端。

五项共用组网底座，各自保持清楚的业务模块边界，可位于同一个库。遵循 KISS 和易用性优先；列表确定功能范围，不表示每个端都具备相同的系统能力。浏览器服务访问的具体协议和站点兼容范围、各模块的平台分工及实施细节仍需后续确定与验证。此前未采纳的扩展不进入此清单；本轮只记录确认结果，不启动实现或任务拆分。

### 恢复服务能力与授权讨论：先以两台设备为范围

用户开始回应服务权限问题，提出不同节点需要声明自己在不同服务上提供的能力，目前可以先考虑两台设备。随后指出端口转发必然涉及 ACL，担心设计复杂。服务能力与授权讨论由此前暂缓转为恢复讨论；两设备是当前讨论的收敛范围，不自动撤回剪贴板可在指定设备组内使用的既有方向。

节点提供什么能力，与哪些对端获准使用这些能力，需要在后续模型中表达清楚；本轮尚未确定授权由提供端还是网络管理员配置，也未选定 ACL 形式、存储／传播机制或固定转发目标的限制。此前避免“应用声明一套规则、管理员再配置一套限制”的重复配置体验仍是约束。端口转发的固定已开放目标与请求端任意指定地址两种范围，会导致不同的授权复杂度，应先讨论产品边界，不将简化建议直接写成既定权限政策。

### 先确定统一 ACL 理念与权力归属

用户指出类似权限会出现在全部业务模块，要求先讨论统一 ACL 的理念和基本工作方式，包括由谁控制、管理员与分布式机制如何相处、针对特定节点的限制，以及分组或等级是否需要。用户要求在 KISS 下形成直接的使用方式。此前针对端口提出的固定目标和“一个对端到一个服务”简化建议未获确认，不能据此提前限制浏览器访问或定下授权模型。

后续应首先区分授权控制权（谁能制定或修改规则）与规则的保存、传播和执行方式。管理员制定规则与分布式保存／执行可以同时成立；节点自行授权也可以采用分布式传播。两者不是互斥选项。当前网络成员与管理员任免权限已有基线，不能把服务 ACL 的控制权默认为已经包含在日常管理员权限里，也不能把“分布式”解释为对端自行宣称获准即可使用服务。

用户尚未选择管理员统一授权或服务提供端授权，也未选择组的控制权、权限等级、默认允许／拒绝、规则冲突和撤销语义。本轮继续概念讨论，不创建实现或任务拆分。

### ACL 控制方式的澄清：管理员可远程修改，目标节点执行

用户明确三项要求：服务能力受平台限制；管理员需要能修改这些权限，人在外地也应能操作；端到端加密下，访问检查在实际提供服务的节点执行，不能把执行位置解释为必须在该节点本地配置。此前“仅服务提供端决定分享、网络管理员只管理成员”的助手建议未被采纳为权限基线。

因此，服务能力声明表达节点在当前环境中能提供什么；授权管理员可以通过管理端远程修改服务访问规则；目标节点验证并执行适用于自己的有效规则。管理员授予访问权限不能凭空创造平台接口或绕过操作系统许可。用户不需要到每台目标设备重复配置一遍，仍避免应用和管理员各维护一套重复 ACL。具体哪些 ACL 变更归日常管理、哪些需要创世逐项确认，以及规则冲突处理，尚待确定。

已有分布式管理记录的保存、转交、补齐和收到后生效原则提供设计依据，但服务 ACL 的签名记录与传播执行尚未实现。目标暂时离线时，远端修改已保存与目标已经生效是不同状态，不能声称离线目标立即获知规则。

用户还提出朋友只为传文件临时接入的需求，不希望因此永久加入或访问其他服务。这重新打开此前暂不支持临时成员的范围问题：现有 precode 到期只阻止新兑换，不会自动终止已取得的成员资格。临时来宾身份、限时服务授权或单次业务会话之间的具体选型尚未确定，不能将其中一种默认为已经接受。用户认为可能需要简单等级，但不希望权限模型复杂；固定身份预设与分组语义继续讨论，不冻结新角色层级。

### 已确认三种身份、节点自身服务管理与专用来宾邀请

用户确认来宾、普通成员、管理员三种节点身份足够，来宾可以使用专门的邀请链接或二维码；朋友分享文件等场景可以临时调整涉及节点的 ACL。节点本身也必须能修改自己对外声明的服务，与此前确认的管理员远程修改能力同时存在。该方向见 [ADR 0017](../adr/0017-guest-access-with-scoped-invitations.md)。

三种身份是简化后的产品基线，创世凭证保管继续独立。服务能力仍受平台限制，规则在目标节点执行；临时分享应只覆盖本次需要的节点与服务。谁可以替哪些节点授予临时权限、管理员限制与节点自身修改的冲突优先级、来宾邀请结束和恢复规则仍需继续确定，本轮没有选择“管理员拒绝优先”或其他冲突算法。

### ACL 的 KISS 收敛：同一套有效规则，暂缓并发冲突设计

用户说明当前主要是个人使用，两处修改同一规则的冲突可以先不处理复杂设计。用户确认管理员限制应优先得到遵守，同时明确落到节点自身就是一套规则，不需要再设置两套规则之间的运行时优先级。

据此，管理员的远程配置入口与节点本机配置入口修改同一套 ACL；管理员设定的限制直接体现在节点验证并保存的有效规则中，临时分享按这套规则执行。这里不引入管理员 ACL 与节点 ACL 的重复配置、交集计算或多层优先级引擎，也不为来宾邀请另开绕过现有规则的通道。规则传播仍沿用目标收到并验证后生效的边界。

并发写入的合并、顺序与冲突算法暂不展开，未默认采用最后写入获胜或时间戳裁决。本次讨论只确定统一规则及使用方式，不启动实现。

### 默认访问方式：主动开启后向成员开放，来宾按邀请限定

用户确认默认规则：节点支持某项能力不等于已经开启它；主动开启服务后，默认向本网成员开放。来宾只获得专用邀请授予的访问范围，需要限制某个成员时再修改同一套 ACL。Shell 具有独立的开启选择，开启意味着成员具备连接资格，具体目标和会话仍按服务范围处理。

这一规则简化的是服务访问资格，不将所有业务自动变成全网同步，也不替代具体业务操作：剪贴板仍按此前确认的指定组或双机范围工作，文件由用户选择目标传递。管理员及本机已经保存的明确限制继续由同一份有效规则执行，开启操作不隐式抹掉这些限制。此决定已补入 ADR 0017，运行代码尚未接入该模型。

### 来宾邀请：一份邀请对应一台设备，允许重连

用户确认首版来宾邀请的默认方式：一份邀请对应一台来宾设备，首次成功接入后绑定其节点身份；原分享授权仍有效时，同一设备断线后可以继续原来的分享，其他设备不能再次使用同一份邀请。邀请另一台设备时另发一份，日常使用无需设置次数。此规则针对专用来宾邀请，不修改既有普通邀请／precode 的可选次数语义。

此处的设备绑定按已有节点身份理解，不引入硬件指纹或承诺辨别持有同一密钥的物理副本。具体邀请格式、有效期、分享结束和恢复细节仍待后续收敛，本轮只记录决定。

### 来宾有效期：到期清退成员；断线语义待对齐

用户提出“断线……或者管理员生成的本身带有效期，例如超过一小时就踢掉这个成员”。当前来宾讨论中，明确的是管理员生成的邀请可以限定来宾成员资格时长，到期需要自动清退已加入的来宾、终止其访问，不能仅让未使用的邀请过期。一小时是举例，未冻结默认值，也未确定从签发还是首次接入开始计时。

“断线”是否指用户主动退出，或包括瞬时网络中断，仍需与此前已确认的同一来宾身份可断线重连规则对齐；此时不选择立即断线即清退，也不把它默认为无条件保留。前一轮助手提出的分享完成自动清退、统一默认时长等完整生命周期建议尚未整体获得确认。普通成员与普通 precode 的既有生命周期保持独立，未扩展成所有成员自动到期。

用户随后确认断线与退出的区分：主动退出即结束来宾资格；短暂网络中断允许同一来宾身份在原有效期内重连，不因重连延长有效期；到期自动清退并停止访问。关闭应用或浏览器页面仍不自动等同于主动退出网络，沿用既有生命周期区分。该确认解决了上一段的断线歧义，尚未选择默认时长、计时起点，或分享完成后是否自动提前结束资格。

### 来宾邀请与资格共用一个截止时间

用户认可从创建邀请开始计时，邀请链接与已接入的来宾资格共用同一个截止时间；晚加入或断线重连都不重新计时。例如 15:00 创建有效一小时的邀请，15:40 加入仍以 16:00 为截止时间。用户强调不必过于严格，保持简单；本轮不继续展开时钟精度和边界条件，也未决定额外宽限时长。一小时仍是示例，不作为已确认的统一默认值。

### 来宾界面：仅围绕本次分享

用户认可来宾从邀请直接进入受邀功能，例如文件传递页，只看到分享者、本次操作和有效时间；不进入完整网络设备列表、其他服务和管理入口。权限仍在服务端按有效 ACL 执行，不能只隐藏界面。此处确认的是来宾的使用入口和界面范围，不据此宣布底层已经实现网络拓扑或管理历史元数据的完全隔离；必要信息的协议范围仍待实现前明确。

### 来宾邀请的授权范围与日常 ACL 修改

用户明确生成邀请时就选定涉及的节点、服务和时间，来宾取得的访问范围由这次邀请限定；不是先授予整个节点的所有服务再由来宾自行选择。选定的时间沿用创建时确定的单一截止时间，首次成功接入仍绑定一个来宾节点身份。

用户同时明确日常服务权限修改不需要创世确认，管理员按其已有管理权限远程操作，节点在其自身服务的管理范围内操作。管理员任免等既有创世操作的逐项确认规则保持。该决定补入 ADR 0015／0017 和领域术语，先前将服务 ACL 是否需要创世确认列为未决的问题由此收敛；服务条目的具体粒度仍待讨论。

### 服务授权粒度：沿节点服务逻辑保持简单

针对将 NAS 网页、数据库等进一步拆成具体服务项的追问，用户要求沿节点已有逻辑按服务处理，不要复杂化。当前统一授权与邀请以“节点 → 服务”为对象，沿用节点的服务声明，加上本次需要的有效时间；不再增加一套通用资源层级或服务内部等级模型。

这没有把助手此前提出的固定地址服务实例方案全部确认为实现要求，也不表示一个端口转发服务可以无条件访问任意地址。各模块怎样表达自己提供的服务范围，留到模块设计时确定，本轮不继续细化参数模型。

### 首版平台范围：Windows、Linux、Android、浏览器／PWA

用户确认首版按以下范围考虑：Windows 与 Linux 原生客户端，Linux 同时支持无界面运行；Android 原生客户端；浏览器／PWA 作为独立节点。各端按实际平台能力声明能提供和使用的服务，继续沿用统一的成员身份、角色和 ACL 规则，不能把相同权限资格当成相同操作系统接口或后台能力。

此段确认交付平台范围，不表示五个业务模块已在所有平台完整实现或验证，也尚未确定具体框架、最低系统版本、安装分发与后台运行接线。README 已同步首版平台方向，运行代码没有变更。

### 共享 UI 技术栈核查：研究支持方向，框架仍待确认

用户要求通过 GPT-6.1 Sol、high reasoning 子代理核查 Vue 3 + TypeScript + Vite 共享界面及 Tauri 2 安装版外壳，关注工程实践和实际产品适配。三项研究分别检查架构、原生平台与浏览器能力，汇总见[技术栈适配研究](2026-10-20-shared-ui-stack-fit-research.md)。

用户进一步澄清，不同平台编写相应适配代码是正常前提。后续评估应关注适配能否满足功能与生命周期要求，不把存在平台代码本身当作框架不适用的理由；这一澄清不单独确认具体框架。
