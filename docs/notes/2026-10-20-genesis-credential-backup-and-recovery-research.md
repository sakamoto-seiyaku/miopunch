# 创世凭证的多设备保管与恢复备份：缺陷、痛点及业内方式

日期与外部资料查阅日期：2026-10-20。状态：研究与讨论建议，**不是产品决定、ADR、实现规格或任务领取**。

本次按用户要求由一个研究子代理调查。只读当前领域定义、ADR、静态源码和第一方公开资料，仅新增本报告；没有读取真实密钥、运行备份或私有 actor 证据，没有构建、部署或操作 Plane。产品文档与在线规范可能变化，以下描述对应本次查阅内容。

## 先给结论

**“指定设备各自加密保存创世凭证，日常解锁使用，再留独立恢复备份”是可行、已有成熟参照的方向。** 用户不必反复输入私钥。主要难点不是再增加几种确认方式，而是让用户在设备损坏后确实找得到、解得开、恢复得对，并理解泄露后的权限边界。

最需要留住四个事实：

1. **多副本降低丢失风险，也增加泄露入口。** 当前任何一份完整根凭证都具有相同创世权力；撤销设备成员、删除本机副本、改备份密码均不能让别人已保留的根副本失效。沿用现有 ADR 时，换根意味着新网络及迁移。
2. **“加密文件＋用户自己设置的密码”不是唯一成熟方式。** Signal、Element 使用软件生成的高熵恢复秘密；Bitwarden 提供自选口令的独立加密导出。前者减少弱口令问题，后者仍依赖口令质量和密码派生成本。两者都需要妥善保管，不能同时承诺“丢光材料仍可找回”和“没有任何额外保管方”。
3. **文件与密码分开放是取舍，不是对所有人的唯一规则。** 分开可以降低一次泄露取得全部材料的风险，但也增加找不齐的概率。完整纸质应急包放安全地点、密码管理器保存恢复秘密等都是实际产品采用的安排，关键是失窃、火灾、账户锁定时会一起失去哪几份。
4. **恢复创世凭证不等于恢复整个网络或业务数据。** 当前 64 字节只有根私钥与 canonical `Create` 哈希，没有管理历史、准入秘密、业务文件，也不含现有恢复 API 所需的联系成员身份。

前两项权限边界来自本项目 [CONTEXT](../../CONTEXT.md)、[ADR 0001](../adr/0001-network-identity-genesis-credential.md)、[ADR 0007](../adr/0007-signed-management-authority-mapping.md) 与 [ADR 0008](../adr/0008-genesis-recovery-credential-pins-create.md)；产品参照见第 4 节。上述结论没有改变这些基线。

## 1. 当前项目到底保存与恢复什么

[日常使用与备份讨论](2026-10-03-shared-web-client-ui-direction.md)已确认本地保护、用户解锁、指定多设备保管及外置备份方向；TOTP、扫码和节点弹窗是候选交互。加密备份格式、OS 保护、凭证交付和这些验证接线均未实现。

[SavedGenesisCredential](../../src/native_network.rs) 当前把 **32 字节 Ed25519 根私钥＋32 字节 canonical `Create` 哈希**拼成 64 字节文件。后者用于钉住原始历史，不是另一份解密密码。当前 demo 使用原始文件与临时提权窗口，不能当作已交付的加密恢复产品。

| 恢复层次 | 需要哪些材料或条件 | 得到了什么，以及没得到什么 |
| --- | --- | --- |
| 找回创世凭证 | 完整、可信的根私钥与 `Create` 哈希；若备份加密，还需正确的解密秘密 | 可以证明同一根权力和原始历史锚点；还没有取得管理图或业务数据 |
| 恢复网络管理能力 | 上述凭证；可信途径取得的联系成员身份；真实可达且能提供合法管理历史与当前准入秘密的成员 | 通过受限会话证明根权、核对签名历史，再给新设备授管理员权；不会自动撤销旧管理员，也不证明拿到了全网最新状态 |
| 恢复业务内容 | 实际业务副本或备份，及相应解密材料和授权 | 恢复其覆盖的数据；根签名能力不能重新生成已经丢失的文件或消息 |

这里的第二层是现有实现：[`NativeNetwork::recover`](../../src/native_network.rs)只准备新设备，明确没有历史、准入秘密或访问权；[`restore_management` 所用恢复协议](../../src/genesis_recovery.rs)在绑定双方节点身份和当前 TLS 会话的证明后取回管理材料。**根凭证备份不含 `contact EndpointId`；能否找到灾后仍可用的合法联系成员，仍是用户恢复体验的一部分。** 如果所有相关历史副本都消失，当前入口不能仅凭 64 字节重建它们。

源码中的 `create_backup` 是另一个**完整节点备份**入口，包含 checkpoint 后的数据库及节点私有持久材料，并用 `backup.version` 标识；不要把它与 root-only 恢复凭证混称。完整节点备份也不是未来尚未定义的“所有业务数据备份”。

## 2. 缺陷与使用痛点

下表把项目已确定的权限结果、规范支持的安全性质及产品推断分开表达。“可缓解办法”均是候选，不是新增决定。

| 用户场景 | 实际结果或盲点 | 可缓解办法 | 仍保留的限制 |
| --- | --- | --- | --- |
| 加密恢复文件被复制，密码是生日、常用短密码 | 攻击者可在自己的机器离线尝试；客户端界面的输错锁定无法约束这份复制品 | 随机盐、适当成本的口令 KDF、认证加密；优先比较软件生成恢复秘密与用户口令两种体验 | KDF 提高每次猜测成本，不把弱密码变成高熵秘密；没有天然的服务端限流 [A][B] |
| 手机坏了，恢复密码已经忘记 | 若另一台保管设备仍可解锁，可重新导出；只剩加密文件则可能永久无法解开 | 让用户保存恢复秘密，允许从仍可用设备重做备份；导出后马上试读一次 | 不依赖第三方的离线备份不能凭空重置忘记的解密秘密；Signal 明确承认此边界 [C] |
| “手机＋电脑＋网盘”都在同一账户或同一地点 | 看似三份，可能因火灾、盗窃、同步删除、云账户锁定一起不可用 | 至少保留一条能独立取回的路径，例如另一地点纸件或不依赖该账户的存储 | 多设备数量不等于失效独立性；这属于威胁与生活习惯相关的判断 |
| 文件放网盘、密码放密码管理器 | 通常便利，但密码管理器若只可经丢失手机解锁，或网盘／邮箱密码只在该管理器里，就形成恢复循环 | 沿“所有日常设备都没了”走一次取回流程；确认管理器自身的应急入口 | 分开保存只在分开的两边灾后都可访问时有意义；不是多套一层密码即可解决 [D][E] |
| 下载成功就认为备份完成 | 文件可能没离开原设备、复制不全、二维码打印后扫不出、密码记错；多年后才发现 | 导出后从实际外置副本解密核对网络；提供简短的“检查恢复备份”入口 | 试读验证凭证与格式可用，不等于网络恢复演练成功；认证加密能发现损坏，不能修复丢失字节 [B] |
| 改了备份密码，以为旧密码失效 | 新文件可用新密码；已被复制的旧文件仍可用旧密码还原同一根凭证 | 界面准确写“重新加密／重新导出”，解释旧包仍有效 | 当前不支持保持原网身份撤销某一根副本；确实泄露后的边界是新网迁移，不是改导出密码 |
| 撤销丢失设备，或把创世权限“交接”给新设备 | 可以撤销成员或清除手中旧机；无法远程证明它没有保留根凭证 | 正常换机先验证新机可用再清除旧机；区分成员移除与根凭证泄露 | 只要完整 root 已复制，其他节点无法从根签名辨别是哪台设备产生；多副本不等于可分别撤销的授权 |
| 依赖设备安全存储，重装、重置或换平台 | 安全存储不必随系统备份迁移；保护越绑定本机，越可能在重置后无法解开 | 独立导出跨平台恢复包；把平台不可迁移属性作为恢复设计输入 | Apple 某些保护类不备份、不同步，移除／重置口令会使其不可用；不能笼统承诺系统账户恢复就能找回 [F] |
| 浏览器保存了创世凭证，误以为和安装版一样持久 | 清站点数据、无痕窗口结束或存储驱逐可能丢本地副本 | 明确浏览器的保管状态，允许外置导出；持久存储申请可降低自动驱逐 | 持久存储仍不能阻止用户清除；也不自动获得安装版同等的硬件密钥保护 [G] |
| 导出二维码，随手截图发聊天或相册 | 明文凭证码等同交出最高权限；加密码仍是可长期复制、离线猜测的密文 | 默认区分“恢复备份码”和“本次确认码”；由可信应用本地扫描，减少明文剪贴板、日志和临时文件 | 二维码只是编码载体；照片、同步、打印件也是额外副本，删除本地图片不证明所有复制品消失 |
| 多年后只有老恢复文件 | 原 root＋`Create` 哈希在同一网络内不会因成员／准入秘密变化自然过期；但老软件、KDF 参数和格式支持可能变化 | 自描述且有版本的包、保留算法与参数、以后提供兼容读取；检查时按目标平台实际试读 | 旧完整节点快照、旧网凭证和同网静态根凭证必须区分；参数过高也可能让低内存设备打不开 [A][B] |

来源：[A] [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html)说明 Argon2 的内存／时间成本及参数选择；本报告不据此固定本项目算法或参数。[B] [age v1.1.0 格式](https://c2sp.org/age@v1.1.0)提供带随机盐、工作因子、头部认证和认证加密的独立文件实例，并建议读取者对工作因子设上限。[C] [Signal 设计说明](https://signal.org/blog/introducing-secure-backups/)。[D] [1Password Emergency Kit](https://support.1password.com/emergency-kit/)。[E] [1Password 恢复码](https://support.1password.com/recovery-codes/)。[F] [Apple Keychain 保护类](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web)。[G] [Mozilla 浏览器存储文档](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)。表中项目权限与数据范围以第 1 节源码和 ADR 为依据；同地点、同步删除和循环依赖是由这些依赖推导的失效情景，并非产品事故统计。

### 2.1 本地解锁、可导出备份与硬件保护要分清

“用指纹解锁”和“根私钥永远不离开硬件”是不同保证。Android Keystore 可把密钥操作放进隔离环境、限制使用条件；设备被攻破时，攻击者仍可能在设备上使用密钥，保护目标也包含防提取。硬件支持还取决于算法、参数与具体设备，不能直接假定当前 Ed25519 根在所有目标平台都能以同样方式托管。[Android Keystore 官方说明](https://developer.android.com/privacy-and-security/keystore)

如果平台密钥只负责解开应用中的根凭证，则 root 解密后仍可能进入应用内存；这与硬件直接完成根签名的性质不同。另一方面，**一个真正只存在于不可导出硬件、且事先没有其他副本的根，无法再从该硬件任意导出恢复包**。可以预先备份或以其他密钥保护可导出材料，但必须明确哪一层不可导出。这里是工程取舍，未选择具体平台方案。

### 2.2 TOTP、扫码或弹窗能确认使用，不能替代根凭证

TOTP 由共享秘密和时间生成短码；验证端也需要相应秘密。它可以作为允许受保护组件使用 root 的额外用户验证，但普通 TOTP 短码不是完整密钥，不是离线备份的解密密码，也不能让新设备无须配置就自动具备验证能力。[RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html)

若只是界面在签名前检查一次验证码，绕过界面或已经取得原始 root 的人仍能签名。真正的约束要由控制密钥使用的可信组件承担；网络节点最后仍验证根签名。TOTP 验证还应处理时间偏差、重复使用与尝试限制，且不天然绑定具体操作或抗钓鱼。扫码／节点弹窗也要区分确认当前操作与分发根凭证；不必因此强制双设备共同授权。[NIST SP 800-63B 的 OTP 与本地激活秘密说明](https://pages.nist.gov/800-63-4/sp800-63b.html)

## 3. “文件与密码”怎样保管才准确

没有对所有用户都最好的存放组合。可用“同一事故是否会同时拿走／泄露全部材料”判断，而不是规定必须存在两个抽屉。

| 安排 | 得到的便利或保护 | 主要代价 |
| --- | --- | --- |
| 加密文件放云盘，解密秘密放独立可恢复的密码管理器 | 不必记住新密码；单独取得文件通常不足以解密 | 要能在所有旧设备丢失后分别恢复两边账户；若同云账户或同一已解锁设备掌握两边，独立性减少 |
| 文件在可复制存储，恢复秘密纸质另存 | 抵御仅窃取数字文件的攻击，减少云账户共同失效 | 人要找齐两份，纸可能丢失、损坏、抄错 |
| 把完整应急资料放同一份纸质包并锁在安全地点 | 家属或本人灾后容易找到全部材料，减少组合失败 | 取得完整包的人可能得到全部创世权力，必须依赖其物理保管 |
| 只依赖两台日常设备 | 换机方便，少一次额外保存操作 | 同地点损坏、共同账户／软件故障或两台同时无法解锁仍可能失去全部凭证；不能称为独立灾难备份 |

这是针对本项目的风险推导，不是存放方式的市场占比调查。1Password 官方就建议在至少一份打印的 Emergency Kit 写上账户密码；同时给出安全地点、个人云存储、可信亲属等选择。它说明现实产品会在“集中应急资料以免遗忘”和“减少一次失窃取得全部材料”之间取舍，而非一律要求密码与资料分开。[1Password Emergency Kit](https://support.1password.com/emergency-kit/)

**密码也可以放在加密的密码管理器里。** 不需要把“密码本身不再加密”当规则；真正需要停止的是无限递归的恢复依赖：最后总要有一项用户仍能取得的凭据、已解锁设备、可信保管人或物理应急材料。对于无外部恢复方的模式，全部设备和全部兜底材料一同丢失时，产品应承认不可恢复。

## 4. 六组第一方参照：相似体验，不同依赖

以下是具体产品与格式的对照，不声称它们构成统一行业标准。尤其“恢复码”这个名称可能指服务器重置授权、随机解密密钥或完整私钥的编码，不能只按字面移植。

| 产品／格式 | 实际做法 | 对本项目可借鉴之处 | 不能直接类比的条件 |
| --- | --- | --- | --- |
| **Bitwarden 加密导出** | `Password protected` 用用户口令和配置的 KDF 生成保护密钥，可导入其他 Bitwarden 账户；`Account restricted` 依赖原账户加密密钥，只能回原账户，该密钥轮换会使旧导出打不开。[官方文档](https://bitwarden.com/help/encrypted-export/) | 明确区分可独立恢复的导出与“看起来加密但依赖原账户”的包；导出名称须表达恢复能力 | 软件仍要兼容格式；凭证根与 Bitwarden 可轮换的账户 key 不是同一权限模型。不能把依赖本机 OS key 的密文直接称为跨设备恢复备份 |
| **1Password Emergency Kit／恢复码** | Emergency Kit 是登录地址、邮箱、Secret Key、设置码和密码填写位置的 PDF，**不是 vault 数据副本**。另一条恢复码通道是 256-bit 密钥加邮箱验证，由服务器交付可解密材料，支持替换作废旧码。[Kit](https://support.1password.com/emergency-kit/)、[恢复码安全设计](https://support.1password.com/recovery-code-security/)、[使用与替换](https://support.1password.com/recovery-codes/) | 做成普通人可保存的应急资料；清楚区分说明／钥匙与数据备份；可用软件生成秘密减少自选弱口令 | 在线账户、邮箱、服务器参与，以及可替换恢复码的授权结构不在本项目 root-only 备份里。不能承诺抄到 root 的人受同样在线身份校验限制 |
| **Apple iCloud Advanced Data Protection** | 提供已信任设备、设备口令及恢复联系人／28 字符恢复密钥路径；启用 ADP 前引导建立替代恢复方法。恢复联系人单独不能读数据；其材料要与 Apple 持有的部分合并。[启用与恢复](https://support.apple.com/en-gb/108756)、[联系人安全机制](https://support.apple.com/guide/security/account-recovery-contact-security-secafa525057/web) | 日常由设备承担密钥；灾前配置兜底，避免灾后首次处理恢复；用户无需日常输入长密钥 | Apple Account、受信任电话号码、平台设备及服务端流程是实际依赖。联系人给一个短码就能恢复的体验，不能简化成“给 miopunch 加一段 UI” |
| **Signal Secure Backups** | 可选的自动端到端加密备份，以设备生成的 64 字符恢复密钥保护；引导保存到密码管理器或手动保存并确认。没有该 key，Signal 不能解密或代找回。[当前支持页](https://support.signal.org/hc/en-us/articles/9708267671322-Signal-Secure-Backups)、[设计说明](https://signal.org/blog/introducing-secure-backups/) | “软件生成，用户保存”是成熟替代方案；日常隐藏密钥，首次确认有助发现没保存 | 服务承担备份存储；这里的 key 解锁真实聊天档案，本项目 64 字节根凭证并不包含管理图或业务内容。自动备份也不等于全部媒体永久保留 |
| **Element／Matrix** | 有已验证设备时可用其取得／更换恢复 key；全无设备时用恢复 key 恢复数字身份与加密历史。两者都无只能重置数字身份，并会失去历史访问。Matrix 规范定义服务端加密 secret storage，也保留用户口令派生方案。[Element 恢复情景](https://docs.element.io/latest/element-support/device-verification/how-to-ensure-you-have-a-recovery-key/)、[Matrix secret storage](https://spec.matrix.org/latest/client-server-api/#secrets) | 与“现有设备帮你接回，独立恢复秘密兜底”最相近；明确让用户核验恢复 key 真能工作 | 有 homeserver 账户、存储与既有设备验证体系；重置身份后继续使用账户不等于保留本项目绑定 root 的原网身份。删服务端备份也不抹掉已复制密钥 |
| **age 独立加密文件** | `--passphrase` 可接受口令，也能自动生成强口令；规范有版本标记、随机盐、scrypt 工作因子、认证头和认证加密载荷。[工具说明](https://github.com/FiloSottile/age#passphrases)、[稳定格式](https://c2sp.org/age@v1.1.0) | 展示无需云账户也能存在的可移植密码文件；不要只想到“把 64 字节随便 AES 一下” | 它是文件加密工具，不提供原网成员发现、管理图／业务恢复或泄露后根权限撤销。引用格式不是决定采用 age 或 scrypt |

助记词、长恢复码或随机词组通常是在表示高熵秘密，具体熵取决于生成方式与长度；用户自己想几个词并不自动得到同样性质。**“一次生成”也不等于“用一次就失效”。** 本项目的完整根凭证在未更换网络身份时可反复使用。要实现能单独作废的恢复凭据，需要另行设计可撤销的授权或密钥包装结构，不能照搬 1Password 的产品名称就宣称已支持。

## 5. 保持简单的两个候选，供下一轮场景讨论

共同部分可以保持用户已经认可的体验：日常由已指定设备保管凭证，危险操作通过用户确认允许使用；另一台保管设备作为可选恢复路径，不把至少两台设备作为开始使用门槛。界面无需同时展示全部 TOTP、扫码和通知机制。

| 候选 | 用户要做什么 | 好处 | 主要代价 |
| --- | --- | --- | --- |
| **A：加密恢复包＋软件生成的恢复秘密** | 一次导出包；保存生成的高熵恢复码／词组到密码管理器或纸件；当场从副本试读 | 减少弱口令、复用口令与“临时想一个密码”的负担；恢复时无须记忆 | 仍要保管秘密；若包与恢复秘密分开，需要灾后能取得两边；恢复码并非可单独撤销的根授权 |
| **B：加密恢复包＋用户自选备份口令** | 选择并确认足够强的口令，保存包和口令；当场试读 | 符合“文件＋密码”的熟悉心智，可通过密码管理器生成和记录口令 | 容易选弱、复用或遗忘；依赖 KDF 成本与目标平台能力；口令换了也不能消灭旧包 |

若把全部可信恢复材料做成一份实体应急包，用户也可以只保管这一件东西；这不是必须再加一层密码的数学问题，而是取得这份材料的人将拥有多大权力的问题。此方案需用户明确接受物理保管的边界，不在本报告中替用户选择默认值。

无论选择 A 或 B，产品需要区分三种可理解结果：**“凭证备份已检查”“正在联系原网络恢复管理”“业务数据是否有副本”**。这些是结果表达建议，不代表要给普通用户展示密码学术语或把研究表变成首次使用检查清单。

当前最值得继续的场景仍是：**手机创建，电脑成为另一保管设备；手机坏了，由电脑接回新手机；再假设电脑也不在，尝试独立备份。** 第一条检验日常是否顺畅，第二条会暴露恢复材料、密码管理器、联系成员及历史保存是否真的独立可得。无需先引入多签、强制双设备或社会恢复。

## 6. 对前面对话需要修正的说法

| 原说法 | 更准确的表述 |
| --- | --- |
| “最终保险就是加密文件＋备份密码” | 这是一个可行方案；也可由软件生成高熵恢复秘密。并非必须让用户再创造和记住一个密码，更不代表备份只须保存这两样就能恢复整个网络 |
| “密码本身不需要再加密” | 不必递归增加密码层；密码可以安全保存在密码管理器。重点是它的恢复入口不能又依赖已经丢失的设备或同一不可访问包 |
| “两者应分别保存” | 分开可降低一次泄露取得全部材料的风险；集中放进受物理保护的完整应急包也有成熟参照。应依据用户能否在灾后找齐材料选择 |
| “两台设备各自保存，基本不会莫名丢失” | 能显著缓解单台损坏，但不排除共同地点、账户、同步及解锁机制的共同故障；还要区分凭证、管理历史和业务数据 |
| “所有设备坏了，用这两样恢复” | 在包完整、秘密正确、格式可读时可恢复创世凭证；现有管理恢复仍需找到合法成员及可验证历史，业务数据另需副本 |
| “TOTP 确认后就能使用创世权限” | 可作为授权使用设备内 root 的交互候选，前提是验证结果确实约束持钥组件；它不替代根签名、不自动解密独立备份，也不约束已经取得 root 的人 |

本报告确认技术与产品参照的可行性，没有替用户选择恢复秘密的默认形式、设备副本数量、存放位置、首次备份强制性、根轮换、具体 KDF／格式或最终危险操作确认方式。

## 7. 后续追问：TOTP 怎样恢复，最高权限怎样备份

同日用户进一步询问 TOTP 恢复机制及其他软件的最高权限备份。补充仍是第一方事实与类比，没有选定产品方案。

### TOTP 恢复的是长期秘密或验证入口

TOTP 由长期共享秘密及当前时间计算短验证码；长期秘密、算法、位数与时间步长等参数相同，设备就能继续生成相同的有效验证码。记录某一次六位验证码不能代替备份长期秘密。[RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html)

常见首次设置二维码编码的是带 `secret` 等参数的配置 URI；它与某一次临时验证码不同。保存原配置相当于保存生成验证码的能力，不能把其截图当作无敏感性的普通设置图片。[Google Key URI Format](https://github.com/google/google-authenticator/wiki/Key-Uri-Format)

Google Authenticator 提供 Google 账户同步；在新设备登录对应账户可同步。未用账户同步时可从旧设备导出二维码给新设备，因此这条手动路径需要旧设备仍在。Microsoft Authenticator 也提供备份恢复，但平台、账户类别不同：其支持页明确同设备类型限制，普通第三方 OTP 账户恢复后可继续产生代码，工作／学校账户等可能需要重新登录登记。不能把某个认证器的云恢复能力当作 TOTP 算法本身具备的功能。[Google 官方迁移说明](https://support.google.com/accounts/answer/1066447?hl=en)、[Microsoft 官方恢复说明](https://support.microsoft.com/en-us/authenticator/restore-account-credentials-from-microsoft-authenticator)

网站另给的备用恢复码通常是另一条认证入口。例如 Google 账户的一次性备用码，用后失效，重新生成一组会使旧组失效；它用于在不能完成通常第二步时登录，而不是由该码还原原 TOTP 秘密。登录后可按服务提供的流程重新配置验证器。此行为依赖服务维护和校验恢复码。[Google 备用码](https://support.google.com/accounts/answer/1187538?hl=en)

对本项目而言，TOTP 用来确认是否允许使用已保存 root；只有 TOTP 生成秘密或云端认证器备份，不能恢复另一份独立的创世私钥。反过来，重新配置验证因素可以作为持有 root 或其他既有授权入口的候选体验，但当前尚未设计该流程。

### 三个更接近高权限的参照

| 参照 | 恢复／应急材料 | 与本项目的实际差别 |
| --- | --- | --- |
| Tailscale Tailnet Lock | 多个指定设备各持自己的 lock signing key；初始化输出长 disablement secrets，可存密码管理器或打印保管 | 签名 key 集合可更新，各设备 key 可撤销；disablement secret 用于解除 Tailnet Lock，并非还原 signing private key，且仍有协调服务与管理员权限要求。不能把它当作同一 root 的多个副本 [官方文档](https://tailscale.com/docs/features/tailnet-lock) |
| 1Password | Emergency Kit 保存账户资料、Secret Key、设置码及密码填写位置；另一条 recovery-code 路径需恢复码加邮箱验证 | Kit 不是 vault 数据本身；服务端参与的恢复码也不同于永久有效的完整 root。保管体验可以借鉴，权限机制不同 [Emergency Kit](https://support.1password.com/emergency-kit/)、[恢复码安全设计](https://support.1password.com/recovery-code-security/) |
| Trezor 钱包备份 | 软件／设备产生的词序列表示恢复密钥所需的随机材料，持有完整备份可恢复钱包访问；具体格式有 BIP39 或 SLIP39 等 | 这是直接恢复密钥能力的参照；词序列不天然是“加密私钥”。本项目还需保留 canonical Create 哈希，不能直接许诺某种固定字数即可承载完整 64 字节凭证 [备份含义](https://trezor.io/guides/backups-recovery/general-standards/how-to-use-a-wallet-backup)、[格式区别](https://trezor.io/learn/security-privacy/personal-security-standards/understanding-trezor-wallet-backups-12-20-or-24-words) |
