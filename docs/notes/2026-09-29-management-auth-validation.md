# MIOPUNCH-23: signed genesis authority and StrongRemove validation

This is the implementation result for [MIOPUNCH-23](http://192.168.4.22:2080/work/projects/aa58cd82-2afc-404b-a097-58ef553c7ca4/issues/c2cc9a0d-7834-4369-b844-14fa8fb5ad70). It fixes the narrow record and authorization mapping for later implementation; it does not claim durable membership, root recovery bootstrap, or network protocol admission.
The accepted mapping decision is recorded in [ADR 0007](../adr/0007-signed-management-authority-mapping.md).

## Reproduce

Use the locked Rust 1.96+ workspace. Run `cargo test --locked --test management_auth` for the six real Ed25519 signed-record scenarios. Run `cargo check --locked --workspace` and `cargo test --locked --workspace` for the affected combination and full suite. The tests construct p2panda-core `Header<ManagementExtension>` values, pass their encoded bytes through the same `ManagementAuth::accept` entry point used for receipt, and replay the retained raw headers through that entry point. `Header::decode` checks the signature before the signed action/dependencies are mapped into `GroupsOperation`.

## Chosen record and identity mapping

- The **network ID** is the genesis Ed25519 verifying key. This root key is an authority identity separate from each device's Ed25519 node identity. Restoring its signing key on another device preserves the network identity. A new root key produces a new network.
- A trusted `NetworkAnchor` pins both that root public key and the hash of the one canonical signed `Create`. The `Create` must be signed by the root, target its group, have no causal dependencies, and initialize exactly the root virtual `Manage` entry and one separate first device administrator. An alternative `Create`, changed root, or forged signature is rejected. The root entry is filtered out of `nodes()` and must never be treated as an online member, connection peer, or rotation confirmation participant.
- The signed header extension carries version 1, a 128-bit author log ID, group ID, typed action, and causal dependencies. `Access::Read` is the ordinary member role and `Access::Manage` the daily administrator role in this slice; conditions and group members are excluded. The root signs high-privilege actions as the virtual root actor. A daily administrator can add and remove ordinary members. Appointing/demoting an administrator or removing a still-privileged administrator requires a root-signed action; an administrator cannot self-exit while still privileged. An ordinary member may self-exit under p2panda's own rule.
- Append-only log continuity is checked per `(author public key, log ID)` using the header's sequence and backlink. The previous operation of the same log must also be in the new operation's causal dependency ancestry; a consecutive backlink alone would let sequential demotion and reappointment appear concurrent to StrongRemove. Each restored root-key device must allocate a fresh random log ID and start at sequence zero, while causal dependencies still reference the network's shared management graph. The tests accept a restored device's first root-signed action without an unavailable old-device log tail, reject reuse of the old log ID, verify contiguous same-log backlinks, and reject a correctly chained but causally stale reappointment. Random log-ID allocation and durable log-head storage belong to the later persistence integration.

The root key and canonical Create hash must come from a trusted invitation or already verified state. A device with only the root credential but no history must fetch the pinned Create and recovery material through the later restricted root-proof flow; merely knowing a public key or supplying a new `Create` cannot join this graph. The current volatile wrapper retains accepted raw headers and graph operations, including filtered operations, for replay. No pruning occurs here.

## Causal policy seam and observed result

The local [p2panda-auth patch](../../vendor/p2panda-auth/UPSTREAM.md) adds one checked process entry. The policy receives the same causal predecessor group state that upstream `validate` reconstructs, including a temporary StrongRemove rebuild when a newly received operation refers to earlier graph tips. It runs before the operation enters the graph. `GroupCrdt::process` and the default StrongRemove resolver retain upstream behavior. The application checks every local, received, and replayed signed action through this entry and commits the new view only on success.

The priority failure case starts with a daily administrator B approving ordinary member T. The root demotes B while B concurrently removes T, with both operations depending on that approval. Receiving the removal first or the demotion first yields the same effective view: B remains a regular member, T remains a member, and B's removal stays in the operation graph but is filtered by StrongRemove. Replaying each accepted history yields the same result. Once the root reappoints B from the joined heads, a new B-signed removal works. This shows the authorization policy does not replace the upstream conflict rule or convert local arrival into finality.

## Limits handed to later tickets

This ticket verifies small in-memory operation graphs and signature/header mapping. It does not durably commit raw headers, assign log IDs on device creation, resume after a crash, authenticate the root credential over a live control session, recover the canonical anchor from another member, or drive connection closure from effective authorization changes. The database/replay and restricted root-proof tickets own those boundaries. In particular, no caller should use the unguarded upstream `GroupCrdt::process` for miopunch management records; `ManagementAuth::accept` is the validation boundary.
