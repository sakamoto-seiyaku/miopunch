## 1. 为什么重新讨论

这次希望全面复盘项目已有的设计和定位，而不只是为当前 POC 增加功能。

iroh 带来的启发主要包括按稳定身份连接、多路径 QUIC 切换、灵活组网、relay 和浏览器客户端所带来的低使用门槛。讨论初期尚未决定语言与重写；用户现已明确按 Rust 重新开发，现有 Go 代码仅供参考。iroh 的具体复用及改造范围仍在讨论，尚未启动实现。

用户愿意投入充分的前期学习、调查和设计时间。目标是 KISS、优雅和对使用者友好；避免方向未清楚就投入实现，也避免脱离小网络场景追求通用性。

之前研究笔记中由助手提出的“优先定位为远程操作产品”未被确认为本轮方向。远程 shell 等属于网络上承载的应用，不是当前讨论主体。

参考：[此前 iroh 独立研究](2026-09-27-iroh-independent-research.md)。该文件保留调查时的判断，不应把其中建议当作本轮最终共识。

## 2. 使用场景与设计取向

以下为已明确的讨论前提：

- 网络规模不会特别大，大部分节点在线是常见情况。
- 用户上手简单、实际使用体验优先；复杂网络的连接优化服务于这个目标。原有解释与诊断能力仍有价值，但不应把掌握网络机制变成使用前提。
- 希望用户没有 VPS 也能组网并访问内网服务；不以项目方有财力持续运营官方联络/中继等服务器为前提。
- 希望以端到端加密保护通信。具体安全契约仍需随连接模型明确。
- 必须先建立网络，之后节点加入网络、按 ACL 和授权参与活动。
- 重点仍包括中国大陆实际环境下的 UDP 穿透及去中心化。
- 用户观察到的 UDP 限速使 TCP、路径质量和多路径切换值得重新研究；尚无统一网络条件下的对比结论，不将个别体验扩大为全国网络的统一属性。
- 管理员希望从 Android、Windows、Linux 等平台进行管理，接受为此安装软件。
- 浏览器也是希望支持的客户端运行方式，可以临时使用，也可以探索长期使用。
- 希望尽量不依赖专门的中心服务；允许节点之间协助联系、转交消息和中继。
- 协议设计应围绕常见场景，参考成熟实践，对真实失败情况作出明确取舍。
- 常见管理者是同一个人在自己的多个设备上操作；普通并发冲突可以采用合适的现成自动处理规则，不再要求一律由用户手动裁决。
- 设备身份迁移暂不进入设计范围：有可用备份则恢复，否则重新入网。创世凭证保留在用户手中，其他管理员不可用时仍须能恢复管理能力。

这里没有决定具体的节点数量上限、传输支持矩阵、性能目标或平台实现方案。

## 3. 浏览器与网页服务器的定位

浏览器是标准客户端的一种交付和运行形式，不是特殊的中心管理门户。

公共或私人服务器可以提供网页。打开网页，相当于取得并运行网页客户端；该服务器在这个角色下仅分发客户端，不因此承担账号、鉴权、组网控制或数据中继职责。

浏览器端的入网、身份、权限和信任规则，期望与其他客户端基本一致。

后续讨论进一步确认：资格可以统一，连接能力可以不对称；浏览器以对等客户端为目标，不只是另一台原生客户端的遥控界面。2026-09-29 用户明确接受浏览器第一阶段只有中继连接：先有一个浏览器能够从公网访问的公共或自建 relay，再考虑通过 WebRTC 等方式扩展直连。这项前提只约束浏览器初期能力，不改写原生节点的直连能力，也不要求采用官方设施。决议见[明确浏览器与原生客户端的能力边界](http://192.168.4.22:2080/work/projects/aa58cd82-2afc-404b-a097-58ef553c7ca4/issues/9efdcabb-c8d1-4982-a72d-b3f44b406e64)。

浏览器停止运行沿用断开与离网分离的既定语义：停止通信不自动撤销成员资格；身份材料仍在时可恢复，材料丢失则按已有备份恢复或重新入网规则处理。浏览器持久存储、休眠恢复、可信客户端分发和 p2panda 浏览器接入仍需验证；不能从 iroh 的浏览器能力推断整个产品已可直接运行。[iroh 浏览器能力说明](https://docs.iroh.computer/languages/wasm-browser)确认现有中继连接与端到端加密基础；[页面生命周期说明](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)说明页面可能被冻结或丢弃，不能将网页当作保证常驻的后台进程。

## 4. 创世权限、管理员与 ACL

### 已澄清的权限模型

网络有唯一的创世权限，必须绑定可验证的凭证；这个权限不必绑定一个固定节点。

日常不依赖创世节点或创世凭证持续在线。网络可以有多个管理员节点。

重大变更使用创世权限，体验类似 sudo：在管理员节点发起操作时，额外验明身份，再执行需要提权的操作。

这里不存在单独的“超级管理员”角色，也没有确认一套最高权限持有者相互任免的角色体系。讨论中的“两层”应理解为日常授权操作与需要创世权限验证的重大操作，不应重新解释成两级管理员。

例子：手机丢失后，可以在另一个管理员节点完成所需验证，撤销丢失手机的身份或权限。无需找到最初创建网络的那台设备。

### 尚未选择的机制

- 创世凭证的具体形式、存储、备份、恢复和更换。
- 提权验证如何绑定具体操作，怎样防止验证结果被用于其他操作。
- 二次确认、第二设备确认、双因素验证各自是否需要，以及如何使用成熟机制实现。
- 日常管理员权限的边界、ACL 表达和重大操作清单。

用户不以密码学背景参与讨论，当前表达主要是体验与权力归属的直觉。后续应把直觉转化为明确的授权语义，并研究成熟协议，不直接凭直觉设计密码算法。

### ACL 的对象与执行范围：后续澄清

本轮讨论的 ACL 限制通过 miopunch 访问的目标节点本地服务，不限制 miopunch 自身用于组网、同步与建连的通信通道。

每个节点可以同时访问别人和提供自己的服务。此前讨论过目标节点主动开放什么，以及某个成员获准访问哪些节点、协议与端口，并以两者同时允许来说明访问范围。2026-09-28 用户明确不接受由应用和管理员分别维护两套重复访问配置，且先暂停 ACL 设计。因此下述例子仅保留语义讨论沿革，不作为双配置模型的实施依据；统一配置和执行方式尚未决定。

例子：目标只开放 80，某成员获准访问 80 和 4322，实际只能访问 80。访问限制需要由目标执行，不能只依赖发起方自觉遵守。

最新澄清：ACL 的共同语义是源节点访问目标节点的某种协议和端口。可以通过可选 TUN 虚拟网卡接入，也可以不装虚拟网卡、通过代理或端口转发访问。入口不同不改变服务权限；具体地址模型、数据转发方式和 ACL 语法仍未定稿。

底层通过 TCP、UDP 或中继建立连接，不改变业务 ACL 中协议和端口的含义。例如经 UDP/QUIC 承载 TCP 8080 服务，服务 ACL 仍检查 TCP 8080，不检查外层传输端口。

## 5. 高权限决定的生效与传播

### 已同意的取舍

节点收到并验证撤销决定后立即生效，不等待所有节点确认。

离线或暂未收到决定的节点允许保留旧状态。这是明确接受的传播窗口，不能把一次本地成功显示成全网同时完成。

撤销等决定不能因为发起节点离线而丢失。其他已收到的节点需要能够保存、转交和补同步有效决定。

多个合法的提权操作没有冲突时都可执行。后续已放宽早先“有冲突一律让用户解决”的要求：普通冲突可以使用成熟组件的确定性自动处理规则，具体规则仍需与撤权及创世恢复要求对照。不为本项目引入拜占庭共识或全网逐项投票机制。

### 当前倾向的机制，细节待推演

- 传播具体决定及其他节点能够验证的授权证明；不传播创世凭证中的秘密。
- 决定的有效性不取决于由哪个节点或哪种渠道转交。
- 为小网络保存可验证的权限变更记录，重连时补齐遗漏。
- 重复收到同一操作不会重复产生副作用。
- 删除成员之外，还需保留撤销依据，避免旧成员表重新引入已撤销成员。
- 不能单凭消息晚到就认定它更新；需要表达决定之间的替代关系。
- 必须明确冲突处理规则，不能把消息到达先后误当作权限优先级；保留必要的解释与人工修正能力，不要求每次冲突都中断等待人工。
- 撤销对已有连接上能力的影响应遵循撤销范围，例如取消管理权不应留下继续执行管理操作的通道。

记录格式、替代关系、冲突判定、冲突期间的行为、历史保留与压缩，均未定稿。“不做拜占庭共识”也不意味着忽略重复消息、崩溃、重启和权限校验。

## 6. 多渠道交流与信任规则

MQTT 只是交流途径之一，不应决定信任和信任传播规则。

已有节点互联、节点间接转交、MQTT 或其他能够联系到对方的渠道，都可以提供投递机会。新增渠道不应要求重写入网授权与成员信任规则。

同一次申请通过多条渠道或多次重试送达，仍应被识别为同一次申请。

传播高权限决定、递送加入请求和返回授权结果，可以复用可用的联系途径。帮助转交消息的节点不因此获得审批权。

消息能间接送达，不代表该路径已适合承载全部业务流量，也不代表中间节点默认同意长期转发。

首次联系、重新找到换地址后的成员、入网前允许的消息范围、各渠道的可靠性差异和路径选择，仍需研究。当前没有选定一个统一渠道协议。

## 7. 入网方式与 precode

### 两种体验都保留

人工申请后由管理员批准，以及管理员提前生成 precode 允许自动入网，两种方式都可以存在。

precode 是预授权邀请，发出时不绑定具体申请节点身份。不能把它改成必须提前获知目标设备公钥的邀请，来回避实际需求。

两种流程期望最终形成可验证的成员授权，遵循相同的成员与信任传播规则；具体统一方式尚未设计。

### 同步给管理员是合理的

对于小型且多数节点在线的网络，将预授权记录传播给所有已确认、具有相应权限的管理员，是合理的候选机制。

这种同步用于知晓邀请、保存信息、协助投递和传播结果，并不表示每个管理员都能独立兑换每张邀请码。送达确认也不等于再次审批。

同步材料如何表达、是否需要包含秘密或仅验证材料、失效与撤销如何传播，待后续设计；没有决定明文复制原始 code。

## 8. 有限次数 precode：最终澄清

**用户明确确认：次数限制依靠某个特定节点处理，其他节点不处理兑换。**

每张有限次数 precode 有一个指定处理节点。它是该码的唯一核销者，不是全网永久中心，也不是更高一级管理员。指定方式尚未决定，生成节点担任只是讨论中提出的简单默认候选。

其他节点可以转交申请、保存记录、验证和传播授权结果，但不能自行扣减该码的次数或批准它的兑换。

```text
新节点
  -> 任意可用的联系途径 / 转交节点
  -> 该 precode 的指定处理节点
       -> 验证申请、有效期、剩余次数
       -> 记录申请节点身份与兑换结果，扣减次数
       -> 出具成员授权
  -> 返回结果，并向相关节点传播
```

### 次数与节点身份

次数按照该 precode 接纳的不同申请节点身份计算，不按网络消息发送次数计算。

同一张码、同一节点、同一次入网的重试，应取回已有结果，不重复占用名额。身份是可验证的节点身份，不是设备名称或 IP 地址。

绑定发生在兑换时。去重绑定负责处理同一申请的重复，指定节点统一核销负责防止不同申请者重复消耗最后一个名额；两者共同完成次数限制。

结果与计数需要可靠保存。讨论中的实现方向是先持久保存结果，再回复成功；具体原子性和崩溃恢复方式未定。

### 时间限制

用户同意使用有效期并允许少量时钟偏差，参考 RFC 7519 的有效期校验思路。尚未决定采用 JWT，也未确定具体容差。

结合唯一核销者，最终有效期判断应由该码的指定处理节点完成。它检查创建时确定的截止时间；更换转交渠道不会重置有效期。

这是在“由实际受理的管理员验时”基础上，随唯一核销职责得到的当前整理，未涉及可信时间服务、时钟回拨等细节。

### 兑换后的生命周期与可用性代价

当前倾向是把已完成的成员授权与 precode 的剩余次数、到期状态分开；晚收到的授权结果不应当作一次新的兑换。成员自身的到期、撤销和重新加入规则还需定义。

指定节点联系不上时，该码暂时不能兑换。已完成的授权仍可由其他节点保存和传播，已有成员不因兑换节点离线而失去整个网络。

当前没有设计自动核销接管。其他管理员生成新码属于新的预授权，不意味着旧码自动失效或旧配额自动转移。

## 9. 不要重新引入的误解

| 已修正的理解 | 本轮澄清 |
| --- | --- |
| 先把项目定为远程 shell 产品 | 应用在网络之上；当前复盘的是网络定位与设计 |
| 易用性意味着不必先建网 | 用户明确要求先建立网络 |
| 浏览器是特殊的中心管理入口 | 浏览器是客户端形态，网页服务器可以只负责分发 |
| 创世权限要求固定创世机器在线 | 权限绑定凭证，不必绑定节点 |
| 需要额外的超级管理员角色 | 重大操作类似 sudo 验证，不新建角色层级 |
| 去中心化要求所有管理员投票 | 授权验证、异步传播；普通冲突允许使用成熟的自动处理规则 |
| precode 必须提前绑定目标设备 | precode 发出时不绑定申请身份 |
| 所有管理员收到邀请记录就能各自核销 | 有限次数码只有指定节点处理，其他节点不兑换 |
| 同步记录本身就能严格限制全网次数 | 在本轮方案中由指定节点统一核销来保证 |
| 多种联系渠道需要多套信任机制 | 渠道改变投递方式，不改变信任与授权规则 |
| 首次联络只需要讨论最小通讯录 | 联络线索属于可持久复制的网络状态；不能遗失已有记录保存、第三方转交与离线补齐的主线 |

## 10. 下一轮待研究问题

1. 网络身份、创世凭证与节点身份之间的具体关系；提权与恢复如何使用成熟机制实现。
2. 管理员授权范围、重大变更范围和 ACL 最小表达。
3. 有效决定的替代、撤销与冲突关系；哪些状态足以支持验证与补同步。
4. precode 指定处理节点如何确定；申请重试、结果丢失和核销节点重启的语义。
5. precode 原始凭据、同步记录与成员授权各自携带什么；到期、撤销、重新入网怎样区分。
6. 联络线索如何随邀请携带、更新；多渠道怎样共同完成首次联系与恢复联系。
7. 浏览器客户端实际的连接能力、身份存储与长期使用限制。
8. 大陆网络中 UDP/TCP、直连/中继和多路径切换的实测差异，以及如何服务于当前小网络场景。

创世恢复能力仍在范围内；跨设备保持旧身份的复杂迁移流程不在当前范围内。两者不能混为一谈。

后续方法倾向：先推演少数具体交互场景，再对照成熟实践；不急着选算法、字段或创建通用框架。本文尚未形成实施任务。

## 12. 当前用于比较组件的小场景

用户同意暂以此常见场景衡量候选组件：手机 P 是管理员，服务器 S 长期在线，平板 T 已入网但数日没有运行客户端。对本场景而言，客户端停止与平板关机都视为节点离线。

期间 P 调整 T 对 S 的 ACL，例如取消 TCP 80、允许 TCP 8080。S 收到有效变更、保存并生效；P 随后离线。T 再次启动后，以原身份从可联系的节点补齐规则，S 按已知有效规则执行服务访问限制。

当前只比较授权记录的保存、验证、传播、补齐和应用。假定需要通信的节点之间已有可用连接，打洞、传输和网关故障不进入此次比较。

浏览器临时入网仍是后续场景；这个基线是老成员返回，不要求重新入网或依赖 precode。

用户明确允许通过场景评估回头调整此前的设计。候选日志、状态模型等不因已经讨论过就成为不可改变的约束；修改具体共识时仍需说明取舍。

详细场景与基于资料的初步比较见[组件复用调查](2026-09-27-ssb-ebt-local-first-reuse-research.md#13-当前比较场景老成员返回并补齐服务-acl)。尚未运行候选实现。

## 13. 底层连接需求的最新补充

用户要求重新研究 TCP，并纳入 TCP 伪装类候选，不能只围绕 UDP 打洞选择整个连接栈。专用 relay 可以存在，同时希望普通节点能够协助中继。普通节点转交控制记录，与为两个节点中继业务连接，是不同能力。

本轮研究把底层真 TCP、TCP/TLS/WebSocket 上承载 QUIC、保留数据报语义的 FakeTCP 分开比较；尚未决定三者都实现，也未承诺某一种在大陆网络中必然更好。

这一阶段曾建议将 libp2p 的多 transport、TCP/QUIC 打洞与 circuit relay，和 iroh 的统一 QUIC 会话及自定义载体进行对照。最新讨论进一步明确允许 fork/补丁，并补查了维护风险，当前方向见下一节。p2panda 的持久记录与同步仍可单独评估，不因需要它就先锁定整个连接层。

具体复用范围、路径切换差异与普通节点中继的边界，见[传输适配调查](2026-09-27-transport-fit-research.md)。本次只记录讨论与资料判断，没有修改运行代码或实施架构变更。

## 14. 允许维护上游改造版本

用户明确：面向大陆复杂网络，需要考虑改造连接栈；fork iroh 或其他库、维护补丁是可接受的选项。不能把“上游没有现成功能”直接当成排除依据。必须说明为了什么需求改哪里，以及哪些部分由自己长期维护。

当前研究主线调整为：以 iroh 为基础，梳理去官方服务依赖、无必需专用服务器、普通节点协助建连/中继，以及 TCP/伪装/路径策略的改造边界。尚未创建 fork、修改依赖或启动实施。

必须区分“不依赖官方服务器”与“不要求专门部署服务器”。前者可以主要通过配置完成；后者需要让发现、外部地址观察、首次通信和中继等角色由可用节点或可选渠道承担。部署自己的固定 relay 不等于完成后一目标。授权不由中继裁决，也不需要因此改写传输密码协议。

libp2p 不再因现成功能多就被默认列为优先采用项。Shipyard 在 2026-08-24 公告将于 2026-09-30 结束相关工作，并停止向 Go/JS libp2p 贡献，是必须计入的维护风险；但不能从该公告推出整个 libp2p、所有实现已经停止维护。[官方公告](https://ipshipyard.com/blog/2026-the-end-of-ipfs-at-shipyard/)

具体源码发现与初步补丁边界见[传输适配调查第 7 节](2026-09-27-transport-fit-research.md#7-后续修正允许-fork-及去中心化改造边界)。

## 15. 联络渠道与 Rust 新实现的最新边界

用户再次澄清：首次联络不应预设一个中继节点 R。MQTT、已有节点转交或其他渠道都可能用于交换建连消息，不同渠道的交互方式和能力可以不同。消息渠道不必承载 QUIC 包或业务流量。

因此不将“先经 R 建立端到端 QUIC，再复用 QNT 打洞”作为总流程；它只是候选策略之一。允许为建连前的外部协商、探测和连接编排，对 iroh 进行必要乃至较大的流程改造。助手此前提出把完整连接编排放在上层 miopunch，用户最新澄清希望将它封装进 iroh fork 内部，见下一节。

用户已明确采用 Rust 全新开发，现有代码仅供参考，而不是逐文件翻译 Go 或保持旧模块/API 的迁移。旧实现中的实验场景、失败经验和行为可作为研究材料，但不自动成为新架构的约束。当前仓库和现行规格不因这一讨论被删除或改写。

此前为保留 Go 而考虑的 Rust FFI/双语言运行时成本，不再作为新核心复用 iroh/p2panda 的默认阻碍。Rust 方向并不意味着决定整套采用这些库。当前仍处于讨论阶段，没有创建 Rust 工程、fork 或实施任务。

## 16. iroh fork 的职责与对外兼容目标

用户进一步澄清：可以直接以 iroh fork 为连接库进行改造，对外接口尽量保持不变，必要时只增加接口；p2panda 尽量不修改，需要时做接入适配。项目名与仓库名尚待讨论，不应由命名反推分层。

此处“传输层”包含完成连接所需的整套机制：使用 MQTT 或其他渠道交换 NAT 信息、探测、打洞、连接建立、数据传输和路径维护。上层不必自己逐步驱动 gather/offer/answer/punch，再调用 iroh；这些流程应封装在改造后的连接库内部。库内部仍可细分渠道适配、协商、探测与传输模块，并不等于把所有实现集中到一个文件。

用户认为现有 miopunch 的连接流程已经较完整，iroh 尚未接入这套流程。源码对照确认当前 UDP 主流程已有快照采集、offer/answer 交换、打洞决策、尝试执行和 PathResult 交付；它是 Rust 改造的重要参考，不应把所有设计都推倒从头讨论。多渠道、伪装和跨路径连续性仍需对照新需求，不把当前 UDP 基线扩大为新需求全部完成。

当前候选划分是上层产品及 p2panda 使用尽量兼容的 Endpoint/Connection 等接口，下层 fork 在内部吸收现有流程经验并复用 iroh 的传输机制。新增接口优先用于渠道配置/注册、策略输入和诊断，不要求上层掌握全部建连步骤。成员、创世权限与业务服务 ACL 不应写死到这个连接库中。

这是当前架构讨论方向，尚未创建 fork 或修改运行代码。接口兼容与上游节点的线协议互通是两项不同目标，后者仍需单独讨论。

用户最新强调：目标是深入修改 iroh 项目内部，不是简单加外层或仅做适配。原生 relay 是希望最终具备并深入理解的能力，当前应优先走读 iroh 的架构、建连步骤和 relay 的作用，再判断明确的新需求怎样嵌入。不能将“去中心化”误解为先删除 relay，或忽略它已经提供的能力。

基于固定源码的流程与改造落点见 [iroh 内部走读](2026-09-27-iroh-internal-redesign-walkthrough.md)。已定位建连前协商、地址获取、路径分类、停止探测条件与换网恢复等内部落点；属于候选设计，尚未实施。

## 17. 回到定位：体验优先、无 VPS 门槛、可选择连接资源

用户希望先暂停继续细化实现，整理定位与统一叙述，再继续研究具体改法。Tailscale 可作为成熟体验的参照，不以全面超过某个商业产品作为本项目成立的条件。项目和 relay 的最终定位尚未定稿。

最新明确的意图：

- 项目方没有持续运营官方服务器的财力，不应把这类运营能力作为产品默认前提。
- 用户没有 VPS，也应有组网和内网服务访问的使用路线；希望通信端到端加密。
- 支持有 relay 和没有 relay 的情况；中继不是排除项，也不预设每次连接都必须经过它。
- 重点改进包括更充分的 NAT 穿透策略、TCP 及相关中继/载体，面向大陆及其他复杂网络，争取更多直连机会。用户举出的 UDP 限速等是需求来源，不代表已获得统一环境的性能结论。
- 用户体验应放在第一位。原设计较重解释和打洞机制，未来应避免要求普通用户先理解这些机制才会用。
- 允许探索借助第三方设施或云服务封装形成中继的方案，但架构不能按某个厂商写死。Cloudflare 等只是用户提出的候选方向，尚未核实具体产品、能力、成本或服务限制。

与上轮“默认是否使用公共设施”的关系：用户没有选择完全拒绝公共/第三方服务，而是希望灵活利用可用渠道，又不要求自己租 VPS 或项目方运营必需服务。默认采用哪些资源、如何配置/分发、资源消失后的退化方式，仍是未解决的产品问题，不能被接口抽象替代。

当前可供讨论的主线是：让用户简单地建立自己的私有网络，通过可用联络渠道完成协商，利用直连或中继路径维持安全通信，并在后台改善连接。这里的主线与术语尚非冻结定义。

质量优先已获用户确认：若已有获准使用且效果更好的中继，即使直连可用也可以选择中继；高级用户可以设置明确偏好或限制。先使用可用路径、再继续争取改善，是这一方向下的候选流程，具体时序、指标与阈值尚未定稿。用户随后确认，信令默认可协助转交，业务数据中继由用户明确启用；面向个人与小团体，不应扩大为复杂节点角色或资源运营体系。具体带宽/流量限制仍待讨论。

后续先用“消息协商后直连”“经原生 relay 建连并继续优化”“使用普通节点或其他设施中继”等少量具体故事检验统一描述。暂不增加正式接口、最终字段或通用插件框架，也不把无 VPS 误写成在任意拓扑下保证连通或免费获得无限中继带宽。

用户进一步明确资源来源可以包括公共 MQTT、公共 STUN、自选旁路渠道、已部署节点和代理；不需要先假设项目方运营官方服务。用户尤其看重标准基础与明确工程取舍，以及设备跨地点、移动或跨运营商时，仍拥有同一个属于自己的安全私有网络。当前候选主线据此围绕稳定节点身份与授权、可变联络和数据路径整理，见上述主线草案；具体标准、代理能力和默认资源选择尚未定稿。

后续已明确安全底线：保留 iroh 节点间端到端保护，旁路私密信令也应避免被知道 topic 的订阅者解密；接受必要元数据可见。邀请引导材料、成员授权、信令保护与 QUIC 会话密钥需区分，不自行发明密码协议。邮件排除，不以完整 ICE 为实施目标。详情及旧代码用途核对见[主线草案第 7 节](2026-09-27-product-mainline-draft.md#7-加密顺序与邀请材料的澄清)，尚未选择具体新信令安全方案。

## 18. 接回 EBT 与持久状态同步的主线

在讨论已入网成员如何首次联系时，助手提出“各节点保存最小成员通讯录”。用户指出没有必要先施加这种细粒度限制，并再次引用[《Scuttlebutt 的开发历程》](https://bd.ailishi.ai/blog/scuttlebutt-development/index.html)，提醒接回讨论早期的 EBT 等研究。因此撤回“只保存最小通讯录”的提议，不将它视为用户确认过的约束。

此前已讨论的方向继续有效：节点保存可验证记录，由其他节点转交，原作者离线后记录仍可存在，离线成员返回后可以补齐。第 5 节的撤销传播与第 12 节的 P/S/T 场景就是具体需求，不应在切换到连接层话题后丢失。

当前将其整理为“本地可验证的网络状态”：通讯录或联系线索是其中一部分，成员与授权记录等也需要保存和同步。节点能力、历史及其他信息纳入哪些范围，按实际需求、授权和有效性继续讨论；用户拒绝最小字段限制，不等于决定全网无差别复制所有信息、永久保留历史或维持全连接拓扑。

EBT 是复制进度、第三方供给与补齐机制的参考，p2panda 是此前已研究的记录/存储/同步复用候选。它们不替代首次联系、NAT 穿透或端到端私密信令保护，也不自动决定我们的成员与服务 ACL 语义。当前没有决定重写 EBT 或将 EBT 与 p2panda 两套实现同时引入。

这次修正已同步进入[产品主线第 4.1 节](2026-09-27-product-mainline-draft.md#41-本地网络状态与持久同步)，并与[既有组件调查](2026-09-27-ssb-ebt-local-first-reuse-research.md)关联。后续讨论以这条连续主线为基础，不再从一个独立、受限的通讯录方案重新开始。

## 19. 2026-09-28：暂停 ACL，按实际场景推进

用户认可需要通过场景检验复杂度，但进一步明确：

- ACL 可以先不讨论；不会做成应用声明一套访问规则、管理员再配置另一套限制的重复配置体验。此前语义上的分类不应自动扩展为两套系统。
- 产品会提供若干初始可用的联系入口，来源可以是公共服务器、用户自行部署设施或旁路渠道。正常流程以有实际可用的引导途径为前提，不继续反复讨论一个完全没有入口的假设世界。
- 面向的是普通用户。高级配置的使用者可视为具有部分开发能力，不应把他们能处理的复杂度转嫁给日常用户。
- 先把具体状态和 case 中的操作、系统流程与结果写清楚，再从中整理架构职责。

用户对节点自主声明与网络授权的区分表示大致认可，但未冻结字段、存储模型或全部规则。前轮架构批评中的具体建议也不是一揽子已确认要求。

首个推演见[场景草案](2026-09-28-network-scenario-walkthrough.md)：已入网手机离线后返回，借产品已有入口联系在线成员，建立安全连接并从副本补齐记录。该文是讨论用流程，不是已实现或已通过测试的报告。

随后用户修正首例的两处跳步：用户只需打开客户端并恢复网络，不必先选择 B 的服务才能启动组网；“联系 B”必须展开 B 自己怎样先接入联络途径，不能预设 NAT 后的 B 已有可被直接访问的公网端点。MQTT/IRC 主要递送打洞与建连信息；形成直连或可用中继上的安全数据连接后，再承载批量信息交换。用户认可不等待所有节点上线、入口可用不等于节点连接成功、无需全网同步完成才一概开始使用。场景草案已按双端过程修正，具体协议和调度仍未冻结。

用户进一步指出不同途径在重连中的地位不同，并用 BT/Kad 等网络类比成熟的恢复过程：先尝试已知优先级高的 relay 或可直达地址，失败后通过其他信令途径取得线索、协调打洞，再有长期稳定入口兜底。本轮不应继续从零发明整个引导过程。此方向已纳入场景草案第 0 节；有界并行、退避与可联络维护是待确认的实现建议，不把类比扩大成必须采用 DHT，或将官方公共服务当成永久可用承诺。

随后用户明确接受已说明的官方公共 relay 限制，并确认产品不绑定官方设施：用户可以禁用官方 relay，选择自建服务或产品支持的插件/扩展途径。官方设施不应成为不可关闭的隐式回退；可用资源先受用户策略约束，再进入恢复和质量比较。具体默认资源、扩展接口或运行时插件机制尚未定稿，也不能把单独禁用 relay 等同于关闭所有官方寻址等辅助服务。

## 20. 常态运行不要求全互连

用户接受 A-B-C 部分互联可以支撑正常组网，并强调仍会尽力争取互联和打洞，不能把这一共识解释成只有业务请求时才尝试连接。较远、暂未相互访问的节点对可以没有直接连接，也不要求每对节点持续保活或承载流量。

A 需要访问 C 时，可以先使用已启用且可用的中继，再通过已有节点、旁路或其他可用途径协调打洞。整个过程应统一、流畅地由连接实现维护，不由用户或业务逐项编排。只有部分节点对有持续业务也是正常情况，不要求所有成员之间都有大流量连接。

此项与已有共识一起应用：中继资格仍须用户明确启用；A-C 保持端点间保护；直连成功不意味着必须换掉质量更好的获准中继；已有部分连接仍可支持记录传播。主动探索与业务需求的具体调度、空闲连接回收及更多中间节点的路由机制尚未确定。具体过程见[场景草案第 2 节](2026-09-28-network-scenario-walkthrough.md#2-常态运行部分互联按需增强)。

随后推演承载业务的 B 中继失效。用户明确接受：有 A-C 直连或经其他 D 的可用路径时尽量切换并维持原连接，没有现成路径则通过可用信令和中继继续协调；最终仍不行，就接受原连接失败。只要原连接仍能存活并恢复传输，上层继续使用；原连接失效后的业务恢复不由组网层统一包办。此处使用“连接连续性”避免与控制记录一致性混淆，具体超时尚未定稿，见[故障场景](2026-09-28-network-scenario-walkthrough.md#3-承载路径故障尽量保留原连接)。

## 21. 过期成员名单不能阻断恢复

用户明确接受以下场景：A 离线期间 C 合法加入，A 原先认识的 B 已离线；A 返回时可以发现并验证自己尚不认识的 C，把 C 作为恢复网络的第一个联系对象。不要求旧联系人或审批者恰好在线。

这使长期引导除“已知节点重新寻址”外，还需要支持“发现本地名单未记录的合法成员”。引导入口只提供候选线索，成员资格仍通过授权材料验证，不采用首次见到公钥即信任的规则。具体发现方式及验证材料如何与成熟安全握手结合，仍待选型核对。见[场景草案第 4 节](2026-09-28-network-scenario-walkthrough.md#4-本地成员名单过时只剩新成员在线)。

## 22. 场景对应的复用与改造调查

用户同意启用子代理，明确指定 GPT-6 Sol / xhigh，分别研究 iroh 行为与 fork 缺口、p2panda 复用范围、两者集成职责与循环依赖。汇总见[实现职责对照](2026-09-28-implementation-responsibility-map.md)。

本轮源码发现包括：p2panda wrapper 可能在缺少地址记录时先于 iroh 返回错误；iroh RelayMap 不是远端 relay URL 白名单；p2panda 已有地址簿、发现、日志补齐与摄取组合，但 topic/NetworkId 不能替代本产品成员准入。这些是相对已确认场景的接入缺口，不是对上游项目作漏洞定级。

研究建议优先复用现成模块并做具体接入修改，而不是重写全套控制网络。它不改变此前深度 fork iroh、保持外部连接接口、p2panda 尽量少改的方向；具体实施仍待小实验验证，没有修改运行代码或启动正式实现。

研究后用户指出，不能直接跳到验证，设计仍有不少未闭环事项。当前已得到的是产品行为约定和组件调查，不是一份完整可实施设计。先梳理未决事项与依赖，再针对不能仅靠讨论回答的问题选择明确的小实验。助手通过 ask-matt 建议使用 wayfinder 组织决策、对单项使用 grill-with-docs；这只是流程建议，尚未正式启用、创建决策票或迁移现有文档。
