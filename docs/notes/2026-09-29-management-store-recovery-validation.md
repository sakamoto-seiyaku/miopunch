# MIOPUNCH-24: complete management records and crash recovery

This records the narrow implementation result for [MIOPUNCH-24](http://192.168.4.22:2080/work/projects/aa58cd82-2afc-404b-a097-58ef553c7ca4/issues/eaaa6657-4966-442c-951b-a242bff84bd7). It uses the signed action, author log, and canonical Create mapping fixed by [ADR 0007](../adr/0007-signed-management-authority-mapping.md). The runnable seam is `ManagementStore::open` → `ingest` → `apply_ready` → `close` → `open`, exercised against a file-backed SQLite database and the real Ed25519 and StrongRemove implementation.

## Commit and replay contract

1. `ingest` decodes and verifies the signed header, checks its network and version, and requires the complete body whenever the signed payload size is nonzero. It verifies body hash and length using p2panda-core. An absent required body or wrong body leaves no row and cannot claim the operation hash. A signed operation with zero payload and no body is complete. SQLite commits the full raw header and optional body together; this return means **durable ingest only**.
2. `apply_ready` selects a pending operation only when its causal dependencies and same-log backlink are already in the committed authorization graph. Selection does not remove or mark the row. It applies the exact signed record through `ManagementAuth::accept_record`, then writes `applied_order` and the full serialized Groups state in one SQLite transaction. That commit is the local authorization application point. A deterministically rejected signed record is marked rejected in durable storage so it cannot block later valid history. Only an applied record can be supplied by hash through `get_record`.
3. On startup, the pinned network anchor must match the database. The store reads applied rows in committed order, replays their complete signed bytes through the same verifier, and checks the persisted Groups member view. Pending rows remain available for later dependency arrival. No operation or authorization history is pruned. Replaying history emits no external effect; `apply_ready` reports only newly committed applications. The connection or application layer must attach its own durable effect/outbox contract when it later consumes authorization changes.

The interruption checks cover: after ingest commit, after a ready row is selected, before the Groups transaction commits, and just after it commits. Before that commit, recovery applies the pending row once; after it, recovery sees one applied row and applies none. Repeated delivery remains idempotent, and out-of-order arrivals converge when their dependencies arrive. Since the returned ingest hash only proves durable receipt, a transport-level “Done” is never used as a local application completion marker. Application completion is `applied_order` plus the matching Groups snapshot, for this network and this local source history only; it says nothing about global latest state.

## Reproduce and limits

Run `cargo test --locked --test management_store` for the file-backed restart, missing/wrong body retransmission, legal no-body record, out-of-order duplicates, and a rejected signed record followed by valid history. Run `cargo test --locked --lib management_store` for the three process interruption points. `cargo check --locked --workspace` and the workspace suite cover integration with the current Rust baseline. The tests use temporary database files and no network service.

The patch is a small local SQLite adapter using the same SQLx stack already present in p2panda-store; it does not change upstream p2panda-stream ingestion, Orderer, or Groups processors. It demonstrates the completeness and atomic replay contract to carry into that later integration. It does not add transport sync, network-wide completion, multi-process writers, production connection effects, or backup/restore of the canonical anchor. The anchor must come from trusted invitation or previously verified state, as in ADR 0007.
