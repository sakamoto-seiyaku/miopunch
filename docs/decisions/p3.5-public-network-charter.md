# P3.5 公网实验可达性纲领

## 文档状态

- 本文档定义 `P3.5` 的目标、边界、约束与关键原则。
- `P3.5` 位于 `P3` 与 `P4` 之间，定位是“为真实网络实验补齐最小可达性能力”，而不是进入完整产品化阶段。
- 本文档不展开实现细节，不替代后续 OpenSpec change。
- 本文档不包含具体数据结构、字段名、函数签名、探测算法或配置 schema；这些应在后续 change 的 `proposal / design` 中收敛。

## 背景

- `P0` 到 `P3` 主要解决了实验台、打洞内核、连通性增强与传输层抽象问题，但真实网络实验仍暴露出若干“可达性前置条件”没有收敛。
- 在实际公网验证中，系统 `DNS` 故障或环境异常会迫使测试过程退回到手工输入 `STUN / MQTT` 的 `IP` 形式，这既不稳定，也不利于复现。
- 真实网络调试还需要显式限制地址族；否则在双栈环境下，`IPv4` 与 `IPv6` 的路径会互相干扰，增加问题定位成本。
- 在中国大陆 / 非中国大陆分流场景下，不同 `STUN` 观测面可能返回不同的公网地址与端口；如果不把这种差异纳入主线考虑，就无法稳定表达“当前应该沿哪一类公网视角继续打洞”。
- `P3.5` 关注的是“让公网实验能更稳定地跑起来并可解释”，不是在这一阶段完成最终对外发布所需的全部工程收敛。

## 核心决策

- `P3.5` 聚焦公网实验的可达性补强，而不是重新定义 `P3` 的传输层目标，也不是提前进入 `P4` 的发布阶段。
- 地址族选择采用短选项表达，语义等价于 `curl -4 / -6`：
  - `-4`：仅约束 `P2P/打洞` 链路使用 `IPv4`（不改变 signaling 的联网行为）。
  - `-6`：仅约束 `P2P/打洞` 链路使用 `IPv6`（不改变 signaling 的联网行为）。
  - 默认 `auto`：沿用现有双栈策略。
- 内置 `DNS` 仅服务于“公网实验期间的 `STUN / MQTT` 地址解析”，不扩展为全局网络栈语义：
  - 用户显式要求使用内置 `DNS` 时启用。
  - 系统 `DNS` 不可用或失效时，回退到内置 `DNS`。
- 默认策略为 `auto`：仅当系统解析失败时才触发内置 `DNS` 回退；同时允许显式关闭回退或强制启用内置 `DNS`，以便复现实验。
- 内置 `DNS` 必须可通过 CLI 与配置文件固化与覆盖；内置默认 resolver 列表应覆盖常见公共 DNS（例如：`1.1.1.1`、`8.8.8.8`、`223.5.5.5`、`119.29.29.29`）。
- `P3.5` 不引入 `DoT/DoH`；内置 `DNS` 默认使用传统 DNS over `TCP/53`（不依赖 `UDP/53`），优先减少污染/劫持对实验可复现性的干扰。
- 提供内置默认 `STUN / MQTT` 名单，来源以 `gonc` 的现有可用集合为基线，减少公网实验中的手工输入与环境依赖。
- 当用户显式提供 `STUN` 服务器列表时，仅使用用户输入的列表；不再使用内置 `STUN`，也不再做 `cn/global` 分组与仲裁。
- `STUN` 内置名单按 `cn` / `global(!cn)` 分组采样；`exchange` 最终只产出 **一个**“已选定的 candidate 视角/分组”，后续 attempt/punching 只沿该视角执行。
- `cn/global` 视角的选择顺序必须固定为：`可用性` → `NAT feature 难度` → `STUN RTT` → `成功次数` → `默认 global`。
  - `NAT feature`（类型/行为/规律性）的优先级永远高于 `cn/global` 本身；只有当 `NAT feature` 难度打平时才进入 `RTT` 仲裁。
  - `STUN RTT` 使用 `STUN binding request` 自身的往返时延作为最小指标；不要求额外 `ping`。
  - `RTT` 打平阈值为 `30ms`；差值小于阈值视为打平，继续按后续规则决策。
- `P3.5` 保留显式人工覆盖能力；内置名单、内置 `DNS` 与分域观测只是辅助实验，不取代显式指定。
- `P3.5` 不要求新增私有中继、专用协调基础设施或完整产品级安全包装；当前重点仍是联通性与可解释性。

## 目标

- 降低真实网络实验对手工输入 `IP`、临时改配置与环境修补的依赖。
- 为公网实验提供最小且明确的地址族控制能力。
- 让 `DNS` 异常不再成为 `STUN / MQTT` 交换实验的硬阻塞点。
- 让中国大陆 / 非中国大陆分流场景下的 `STUN` 结果差异进入主线语义，并能支撑后续的路径选择与问题分析。
- 让上述选择过程具备可观测性，能够在日志、事件或实验产物中说明“用了哪种地址族、哪类 `DNS`、哪类 `STUN` 视角”。

## 非目标

- 不在 `P3.5` 设计最终面向用户的完整配置体系、交互体验或稳定 API。
- 不在 `P3.5` 承诺精确的地域识别、最优线路选择或全面的网络质量调度。
- 不在 `P3.5` 引入新的 `relay / fallback` 架构、完整加密方案或发布级安全模型。
- 不在 `P3.5` 推进 `IPv6 NAT66 / 受限 IPv6` 的 `UDP6 punching(mode0..4)` 泛化；该方向需要更多真实样本与单独 change 推进。
- 不在 `P3.5` 完成 `P4` 需要的全部真实网络矩阵验证与开源发布收敛工作。

## 约束

- `P3.5` 的新增能力不能破坏既有 `P0 / P1 / P2 / P3` 的实验台基线；新行为应通过新增验证路径表达，而不是回改旧的基准场景。
- 地址族选择、`DNS` 来源与 `STUN` 观测面相关决策必须可观测、可记录、可复盘。
- `debug` 日志级别下必须输出完整的 `cn/global` 观测与仲裁证据；更低日志级别可逐级减少细节，但必须至少记录最终选中的视角与关键原因。
- `P3.5` 应优先服务“公网实验能跑、能解释、能复现”，避免在此阶段过度设计产品层抽象。
- 内置能力的存在不应阻断显式配置；实验人员仍应能够清晰指定要使用的地址族、`DNS` 与服务端集合。

## 验收口径

- 需要形成与 `P3.5` 目标相匹配的真实网络验证路径，至少覆盖：
  - 显式限制 `IPv4-only`
  - 显式限制 `IPv6-only`
  - 内置 `DNS` 的显式使用或回退触发
  - 中国大陆 / 非中国大陆 `STUN` 观测差异下的路径选择证据
- 验收重点是“实验是否可执行、结果是否可解释、关键决策是否被记录”，而不是在这一阶段追求完整产品化体验。

## 与 P4 的边界

- `P3.5` 负责把真实网络实验所需的最小可达性前置条件补齐。
- `P4` 再负责更完整的公网实验矩阵、对外发布前文档与接口收敛、以及更长期的安全性与可运维性问题。
- `P3.5` 不提前把 `P4` 的发布门槛、最终配置体系与产品语义写死。

## 开放问题

- 如何定义“系统 `DNS` 已失效、应回退到内置 `DNS`”的边界，后续需要在 change 中继续收敛。
- 内置默认 `STUN / MQTT` 名单如何维护、更新与钉死版本，后续需要结合实验节奏确定。
- 中国大陆 / 非中国大陆 `STUN` 观测面的判定与仲裁依据应如何表达，后续需要结合真实网络证据进一步收敛。
- 当本地与对端同时存在多种公网观测结果时，交换阶段应保留哪些最小语义，后续需要在 change 中定义。

> 具体的接口形式、配置表达与运行时判定逻辑，应在后续 OpenSpec change 的 `proposal / design` 中继续收敛。
