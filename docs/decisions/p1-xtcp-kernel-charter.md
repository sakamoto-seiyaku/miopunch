# P1 XTCP 内核纲领

## 文档状态

- 本文档定义 `P1` 的目标、边界、约束与关键原则。
- 本文档不展开实现细节，不替代后续 OpenSpec change。
- 后续实现前，应基于本文档与 `docs/roadmap.md` 创建并收敛对应 change。

## 背景

- `P0` 已提供单 VM 的 NAT 实验台与回归用例集合，可稳定复现代表性 NAT 场景并导出观测产物。
- `P1` 需要以 `frp xtcp` 为起点，提炼一个“可独立运行、可独立测试、可独立演进”的 NAT traversal 内核。
- `P1` 的第一目标是“建链可复现 + 失败可解释”，而不是追求完整功能或更高吞吐。

## 核心决策

- `frp/` 以 `git submodule` 引入并固定版本，仅作为参考实现与行为对齐基线（不 vendor，不作为运行时依赖）。
- `P1` 采用“直接从 `frp` 复制/抽离代码”的落地方式，以最小改动形成可独立构建与测试的内核；避免大规模重写与重构。
- 对复制进来的上游文件，必须保留原始版权与许可证头部，并记录来源版本（commit/tag）。
- 仓库对外开源以 `GPLv3` 为默认选择；复制自 `frp` 的代码与衍生文件继续遵循其上游许可证要求（例如保留 `Apache-2.0` 头部与归因文件）。
- `P1` 不引入 `fallback/relay`；直连失败就失败，必须可观测、可定位、可复盘。
- `P1` 只聚焦“连通性内核”：`discovery`、`signaling`、`classification`、`hole punching`。
- `P1` 的 `control plane` 与 P2P 数据面均支持 `KCP / QUIC`（`TCP` 仅作为默认基线，不计入该选择；不含 `fallback relay`）；`P1` 不实现额外的“加密/压缩”包装逻辑。
- `control plane` 协议优先选择“最小可用子集”，能跑通并可回归即可；不足之处后续通过 refactor/change 演进补齐。
- `P1` 不引入复杂组网语义：仍以“中心协调 + 两端数据面”作为主流程。
- `P1` 采用 `Linux-first`：必须在 `P0` VM 实验台内可重复运行；真实环境验证作为独立测试线。
- `P1` 不实现 `IPv6` 与端口映射辅助（`UPnP / NAT-PMP / PCP`），但接口设计不得阻塞后续 `P2` 扩展。

## 目标

- 产出一个最小 NAT traversal “内核库”与最小 CLI，能够在 `P0` 实验台中跑通代表场景并稳定回归。
- 支持基础 `STUN` 发现、必要的 NAT 行为判定信息记录、信息交换与 UDP 打洞。
- 可观测性硬约束：对每次建链尝试输出阶段化时间线与关键网络条件，失败可定位到具体阶段与原因。
- 测试优先：允许测试代码多于功能代码；目标是尽可能完整的单元测试覆盖与可复现的集成回归。

## 非目标

- 不在 `P1` 引入 `UPnP / NAT-PMP / PCP`、双栈策略与 `IPv6`（这些属于 `P2`）。
- 不在 `P1` 做面向性能的拥塞控制与调度优化（例如 `HY2` 风格调度；这些属于 `P3`）。
- 不在 `P1` 引入 `fallback/relay`（直连失败就失败；可观测性必须覆盖失败路径）。
- 不在 `P1` 做 `overlay / mesh`、多跳转发与弱中心化 relay 体系。
- 不在 `P1` 做 `TCP` 打洞、`VPP` 数据面、用户态协议栈与伪装链路实验。
- 不在 `P1` 承诺“自动化一键全矩阵跑完”的完整流水线（但要保留清晰入口与可脚本化接口）。

## 可观测性约束

- 每次尝试必须输出阶段枚举：`discovery`、`signaling`、`punching`、`confirm`、`transport`。
- 阶段事件必须可机读（例如 `json` 事件流或可解析的结构化日志），以便集成测试断言“失败发生在哪一阶段”。
- 错误必须携带：失败阶段、关键条件（候选地址/端口、对端信息、超时与重试次数）。

## 测试与验收

- 单元测试：协议编解码、状态机、超时/重试策略、候选地址选择与判定逻辑。
- 集成回归：复用 `P0` 实验台，在代表性 case 上验证成功/失败路径，并断言观测产物与阶段化诊断信息完整。
- 真实环境验证：独立于 `P0`，用于确认虚拟实验台之外的表现；不作为 `P1` 的唯一验收依据。

## 开放问题

- 从 `frp` 复制/抽离的最小范围如何界定（仅 `xtcp/nathole` 还是需要带上部分 `msg/transport` 适配层）。
- 如何记录与维护上游来源：固定 commit + 复制清单 + 变更补丁策略（尽量保持可 diff）。
- `control plane` 的最小协议形式与消息编码选择（为后续演进保留兼容空间）。
- `NAT` 行为信息的采集范围：`P1` 仅记录最小可用信息，还是直接对齐更完整的 `RFC 4787` 表达。
